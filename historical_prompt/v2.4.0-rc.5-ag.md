Two defects in *Insights → Fields*, and nothing else:

* **Bug A** — applying a mapping that was identical to the automatically detected one turned the *Detected*
  status from blue to grey.
* **Bug B** — saving a Column Mapping Profile while one worksheet was open overwrote/duplicated the mapping
  values of the other worksheets, empty values included.

Both were traced to their actual causes rather than their symptoms, and both are fixed in the data model, not in
the indicator's or the dialog's presentation. No interface redesign, no change to the profile workflow beyond
its scope, no version bump.

## B. Bug A — the Detected status

**Exact root cause.** The indicator was a pair of **state flags**:
`val isDetectedMapping get() = activeProfile == null && appliedMapping == null`. `applyMapping()` wrote the draft
into `appliedMapping` whenever the draft was not word-for-word one of the saved profiles — which is the normal
case, and true even when the draft was exactly what detection had produced. So the flag became "an override
exists" the moment the user pressed **Apply mapping**, and the chip went grey although the effective mapping had
not changed at all. The indicator described the *click* instead of the *mapping*.

**State lifecycle involved.** `ColumnMappings.detectedProfile(table)` → the draft (`startMapping`) → **Apply
mapping** (`appliedMapping`) → `refreshInsights` → the catalog → the Fields chip; plus the persisted mapping
(`WorkbookMapping`) restored on open. The defect was in the third step, but it poisoned the fifth and sixth as
well: a stored "applied" mapping that meant detection produced a grey chip after every restart.

**How semantic equality is implemented.** `MappingEquality.sameColumns(a, b)` compares the two maps **by
meaning**. `canonical()` keeps only assigned fields — `header.isBlank()` is "not assigned", so a blank can
neither create nor hide a difference — and compares each header through `ColumnMappings.normalize` (trimmed,
lower-cased, inner whitespace collapsed), which is exactly how `ColumnMappings.resolve` compares headers when the
catalog is built. An equivalent mapping in a different object, a different key order, different spacing or
letter case is therefore the same mapping, while a field present on one side only is a difference.
`isDetectedMapping` is `sameColumns(effectiveMappingColumns, detectedMappingColumns)` for the worksheet on
screen, where `effectiveMappingColumns` is the inspected worksheet's entry, or its detected columns when it has
no entry.

**Why an equivalent mapping stays blue after Apply mapping.** `applySheetMapping` stores **no entry** when the
columns mean the worksheet's detected headers: there is no override, so the effective mapping *is* detection, the
chip is blue, and nothing is written to `workbook-mappings.json`. The rule holds twice over — the state never
creates an entry that means detection, and `isDetectedMapping` would still report blue if an older file
contained one (a restored entry that means detection is dropped). `appliedProfile()` returns null,
`activeProfile`/`appliedMapping` are null, and `mappingSourceLabel` says "Detected from this workbook's
headers", so the chip and the sentence can never disagree.

**Why genuinely changed mappings go grey.** Any assignment that differs — a different header, a field added, a
field removed, a detected field cleared — changes `canonical()`, so an entry is stored for that worksheet,
`isDetectedMapping` is false, and the label says "Manual mapping, not saved as a profile" (or names the profile).
Restoring the detected assignments and applying again removes the entry, and the blue comes back; picking
**Detected** clears it the same way.

## C. Bug B — one worksheet's mapping leaking into the others

**Exact root cause.** The workbook had **one** mapping. `WorkbookCommentsUi` held `activeProfile` /
`appliedMapping` (workbook-wide), `appliedProfile()` returned it for every worksheet, and
`WorkbookCatalogBuilder.build(profile)` resolved **every** table with that single profile. `saveProfile()`
therefore did three things at once: it stored the definition, made it the workbook-wide mapping
(`activeProfile = trimmed`), and rebuilt the catalog with it (`refreshInsights(profile)`) — so every other
worksheet was re-resolved with the inspected worksheet's header names.

**How the wrong values were propagated.** `ColumnMappings.resolve(table, profile)` matches by header name, so on
`DATA` (a different header row) most fields became `HEADER_MISSING` → `UNMAPPED`: `DATA`'s own detected mapping
was replaced by something that mapped (almost) nothing. The same single mapping was also the **base of the next
worksheet's draft** (`startMapping` → `state.appliedProfile()`), so switching to `DATA` showed `LIST`'s header
names in the Fields rows — the empty ones included — exactly as reported. Nothing was shared by mutable
reference (the maps and `ColumnMappingProfile` are immutable): the sharing was **semantic**, through a
workbook-wide state holder, which is why it reproduced even when no assignment had been changed.

**Which of the prompt's failure modes applied.** #2 (a worksheet-specific map replaced by a global one), #3 (a
profile built from the current worksheet interpreted workbook-wide), #4 (empty values treated as valid global
assignments — a field the inspected worksheet does not map simply vanished from the profile, unmapping it
everywhere), #6 (profile-saving captured the current worksheet's state as the workbook's) and #9 (profile
creation invoked application/persistence for unrelated worksheets). #1/#7 (shared mutable objects) and #5/#10
(non-unique keys) did **not** apply: the structures were immutable and keyed by name. The real gap was that no
worksheet identity existed in the mapping state at all.

**Exact correction.**

* `SheetMapping` + `Map<String, SheetMapping> sheetMappings` is the mapping state, one entry per worksheet
  identity; `withSheet`/`withoutSheet` return new maps and new values, and an entry with no columns is removed.
* `WorkbookCatalogBuilder.build(…, profile = null, sheetMappings)` resolves each table with its own entry, else
  its own detection. The normal build passes `profile = null` ("no workbook-wide mapping").
* `refreshInsights()` has **no** profile parameter any more, so no caller can hand it a widening mapping.
* `applyMapping`, `selectProfile`, `saveProfile`, `deleteProfile` and `startMapping` all act on
  `state.mappingSheet` only. `saveProfile` stores the definition and applies it to that worksheet.
* `deleteProfile` **detaches** the name (`detachedFrom`) and keeps the columns of the worksheets that used it,
  instead of re-mapping anything.

**How workbook and worksheet identity are enforced.** Every entry is keyed by `SheetScope.keyOf(partPath, name)`
— the worksheet's package part (`xl/worksheets/sheet5.xml`), or `name:<display>` when the analysis could not read
the path — the same identity `CatalogEntry.id`, `SheetScope` and `CatalogEntry.locationLabel` already use, so a
renamed worksheet keeps its mapping and two sheets can never collide. The workbook is the outer scope: the store
is keyed by the workbook's SHA-256, and a build drops results that belong to another workbook.

**How empty values are isolated.** `applySheetMapping` filters blank headers before it decides anything
(`filterValues { it.isNotBlank() }`), so a blank is never an assignment: it cannot be stored, cannot make an
entry mean detection, and `MappingEquality` ignores it on both sides. An empty value in `LIST`'s draft therefore
changes `LIST`'s entry (or nothing) and is never written into another worksheet's entry — each entry holds only
the columns of its own worksheet.

**How profile creation is prevented from mutating unrelated worksheets.** `saveProfile` writes the profile to the
store and calls `applySheetMapping(columns, trimmed)`, which touches only `mappingSheetKey`; a non-null
`profileName` is recorded on **that** entry alone. Another worksheet applies the profile only when the user picks
it while that worksheet is open (`selectProfile`), which is the existing explicit workflow.

**Test coverage and results.** `WorksheetMappingIsolationTest` — 12 tests over three worksheets (`LIST` =
Japanese headers with a field detection cannot fill; `DATA` = English headers, a different set; `NOTES` = a
mixture), all passing. Every assertion checks the **values** the catalog resolves per worksheet
(`catalog().mappings[sheet].columns`, plus `CatalogEntry.state`/`text`), not the UI:

| Scenario | Result |
|---|---|
| Baseline: each worksheet on its own detected headers (タイトル / Title / 書名) | pass |
| Save a profile on A without changing anything → B and C unchanged; A stores nothing (it means detection) | pass |
| Change one mapping on A → B and C unchanged | pass |
| Change several mappings on A (Title + Default order) → B and C unchanged, only A has an entry | pass |
| Clear a mapping on A → B and C still map their own Title | pass |

detection`.

## G. Remaining issues

1. **No device/emulator pass.** The chip's colour, the buttons and the dialogs are compiled and their state and
   model are unit-tested; nothing was tapped through. A Compose UI-test module would let a tap assert the chip
   itself — worth adding if this screen keeps growing.
2. **Profiles are still reusable, but not applied across worksheets in one action.** Deliberate: applying one to
   several worksheets would need an explicit multi-worksheet operation, which this task was told not to add. In
   practice a profile is picked per worksheet.
3. **A v1 file's columns become a manual mapping** (not "the profile it named") on those worksheets, because a
   v1 file never recorded which worksheet they belonged to. The columns are kept; the profile name is not
   re-attached.
4. **Two worksheets with the same display name** (possible only across different package parts) are keyed by
   part path, so they stay distinct; a workbook whose analysis could not read part paths falls back to
   `name:<display>`, where two identically named sheets would share an entry — the workbook reader treats that
   as unreadable, and the UI shows the sheets as separate choices.
5. **Not addressed (out of scope, unchanged):** the Images/Catalogue worksheet picker is still session state, and
   a `General`-formatted column still cannot be declared a "measurement" for the two-decimal rule.
