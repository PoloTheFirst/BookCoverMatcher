# BookCoverMatcher v2.5.0-dev.5 — PP-OCRv6 Recognition Dictionary Reconciliation

## 1. Objective

Continue the incomplete native OCR migration in the existing BookCoverMatcher repository.

**Primary objective:** Investigate and resolve the character-dictionary mismatch between the PP-OCRv6 Medium ONNX recognition model and the dictionary currently extracted from its `inference.yml`.

The current native implementation successfully executes real PP-OCRv6 Medium detector and recognizer inference through ONNX Runtime. However, recognition output cannot safely be decoded into text because the recognizer's output class count does not match the available dictionary.

This task must establish the **exact, model-compatible character-to-class mapping**, not merely find a dictionary with a matching number of entries.

Do not proceed to JNI/Kotlin integration until the mismatch is resolved and actual text decoding is verified.

### The unresolved mismatch

The current model output contains **18,710 classes**.

The dictionary extracted from the model's own `inference.yml` contains:

- 18,705 entries according to the current configuration inspection.
- 18,704 entries in the extracted dictionary file.

The current decoder consequently reports a mismatch similar to:

`recogniser outputs 18710 classes but the dictionary maps 18706 (18704 characters + blank + space); refusing to decode`

The precise count and indexing convention must be independently re-verified during this task.

A separate dictionary containing 19,053 entries was downloaded from a manga fine-tune. It has already been rejected because it belongs to a different model configuration. Do not reuse it unless compelling primary-source evidence proves exact compatibility.

**Never truncate logits, pad the dictionary with guessed characters, silently ignore output classes, or substitute a dictionary from another model.**

## 3. Mandatory investigation

Perform a forensic investigation of the exact PP-OCRv6 Medium recognition model and its vocabulary.

Do not assume that the current `inference.yml` is complete or that its dictionary is necessarily the exact vocabulary used during ONNX export.

### 3.1 Establish the exact model identity

Inspect and record:

1. The exact ONNX model filename.
2. Its source repository and model release.
3. The model revision, commit, tag or downloadable artifact version, if available.
4. The model's file hash.
5. The original Paddle recognition model/configuration, if obtainable.
6. The ONNX export script and export configuration, if obtainable.
7. Any vocabulary, dictionary, metadata or postprocessing files shipped alongside the model.
8. Whether the exported ONNX file differs from the published Paddle inference artifact.

Use primary sources wherever possible:

- Official PaddleOCR repositories.
- Official PP-OCRv6 model repositories and release artifacts.
- Original model configuration files.
- Original export scripts.
- Official model metadata.
- Reproducible inspection of the actual ONNX graph.

Secondary mirrors may be used to locate artifacts, but their contents must be independently verified.

Do not assume a model name alone proves that two artifacts are identical.

### 3.2 Inspect the ONNX graph and output head

Investigate why the recognizer outputs 18,710 classes.

Inspect:

- Final recognition head dimensions.
- Final projection/convolution/linear layer output channels.
- Graph output shape and symbolic dimensions.
- Relevant initializers and tensor shapes.
- Any output-head transformations or postprocessing embedded in the graph.
- Whether the final class count includes CTC blank or other special tokens.
- Whether the model has an embedded or externally associated character mapping.

Determine whether the 18,710 classes represent:

- A vocabulary including the CTC blank class.
- A vocabulary excluding the CTC blank class.
- A vocabulary including additional special tokens.
- An exported head whose dimensions do not correspond to the published dictionary.
- Another model-specific indexing convention.

Do not infer the answer solely from the tensor dimension.

Where possible, inspect the corresponding original Paddle model and compare the recognition head dimensions against the ONNX graph.

### 3.3 Recover the exact dictionary

Search for the actual vocabulary used to train/export this exact recognition head.

Investigate:

- Official model package contents.
- Repository history and previous revisions of `inference.yml`.
- Associated dictionary files.
- Export scripts and their dictionary-loading behavior.
- Training configuration and vocabulary generation.
- Character encoding and normalization.
- Special-token handling.
- Whether the dictionary is stored inline, in a separate file, or generated during export.
- Whether a published dictionary has been accidentally omitted or truncated in the distributed package.

Check whether the discrepancy is caused by:

1. Missing dictionary entries.
2. Different dictionary revisions.
3. A mismatch between Paddle and ONNX export configurations.
4. Different handling of whitespace.
5. Additional special classes.
6. Incorrect extraction or parsing of the inline dictionary.
7. Incorrect assumptions in the existing Rust decoder.
8. Another demonstrable model-export issue.

Do not stop after finding a file with 18,710 entries. Its ordering and semantics must also be verified.

### 3.4 Verify the exact class-to-character mapping

This is the most important requirement.

Establish a definitive mapping:

`ONNX output class index -> exact character or special token`

The mapping must be verified against the model's actual training/export configuration or another authoritative artifact.

Document:

- Whether class 0 is CTC blank.
- The exact first and last vocabulary indices.
- Whether spaces are included in the dictionary or appended separately.
- Whether any other special tokens exist.
- Whether duplicate characters are present and how they are handled.
- The exact character count.
- The exact total class count.
- The ordering of all characters.
- The source and evidence supporting the mapping.

Do not use Unicode sorting, alphabetic sorting, deduplication, normalization, or any other transformation that changes the original order unless the original export pipeline explicitly performs that transformation.

If the correct vocabulary cannot be recovered, report the blocker honestly. Do not fabricate a complete mapping.

## 4. Candidate dictionary acceptance criteria

A candidate dictionary is acceptable only if all of the following are satisfied:

1. It is tied to the exact PP-OCRv6 Medium recognizer or its demonstrably identical training/export configuration.
2. Its provenance is documented.
3. Its ordering is verified.
4. Its special-token and CTC blank conventions are verified.
5. Its class count agrees with the actual ONNX output.
6. The correspondence between output indices and characters is supported by primary-source evidence or reproducible model/export inspection.
7. It passes deterministic tests.
8. It produces plausible text on real model inference samples.

A matching entry count alone is insufficient.

A dictionary from another PP-OCR model, language-specific fine-tune, manga fine-tune or unrelated recognition model must not be accepted merely because its dimensions fit.

## 5. Correct the implementation only after establishing the mapping

Once the exact mapping is established:

1. Update the dictionary extraction or generation process.
2. Preserve the original vocabulary ordering.
3. Implement the correct CTC blank and special-token conventions.
4. Update `rec::decode_output` to use the verified mapping.
5. Keep strict shape validation.
6. Reject any future mismatch with a descriptive error.
7. Ensure the decoder handles repeated CTC classes and blank separation correctly.
8. Ensure confidence calculation and character selection are numerically stable.
9. Ensure the output is decoded as valid Unicode, including Japanese, Traditional Chinese, Simplified Chinese and English.
10. Document the vocabulary source, revision, hash and extraction procedure.

If the correct vocabulary is embedded in an official configuration, preserve its exact contents and ordering rather than manually recreating it.

If a generated dictionary file is needed, make the generation reproducible and document its source artifact and hash.

Do not introduce a manually patched dictionary without a reproducible explanation of every additional or missing entry.

### Important decoder constraints

- No silent truncation.
- No dictionary padding.
- No guessed characters.
- No ignored output classes.
- No fallback to a different vocabulary.
- No automatic substitution of unknown characters with unrelated symbols.
- No false claim that a successful tensor inference means OCR text recognition works.
