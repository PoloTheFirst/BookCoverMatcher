## 5. Mandatory Pacman animation requirement — at least 60 FPS

### 5.1 User requirement

The Pacman contribution graph must be visibly animated at **at least 60 FPS on a device that supports a 60 Hz or higher display refresh rate**.

A scheduler configured for 60 FPS is not sufficient proof.

The effective, visibly presented animation must achieve the target. Do not claim 60 FPS based on:

- A timer interval.
- A frame counter incrementing.
- Generated SVG strings changing.
- Frames being generated but not presented.
- A high theoretical refresh rate.
- A successful build or unit test.

### 5.2 Investigate the complete pipeline

Inspect the current implementation from source animation to actual display:

1. Original SVG and SMIL timing.
2. Animation timeline sampling.
3. SVG parsing and frame generation.
4. Rasterization or vector drawing.
5. Frame caching.
6. Animation scheduling.
7. Coroutine and lifecycle behavior.
8. Compose state updates and recomposition.
9. Android rendering and display presentation.
10. Actual visible frame changes.

Identify the current bottleneck and measure the existing effective FPS before making changes.

Do not assume the previous 15–20 FPS implementation is still present.

### 5.3 Implementation target

Aim for:

- At least 60 visibly presented frames per second on a 60 Hz display.
- A frame interval near 16.67 ms when the display refresh rate is 60 Hz.
- Higher refresh rates where the device and rendering implementation support them.
- Smooth Pacman movement with the original animation duration and overall motion preserved.

Requirements:

- Use an appropriate display-synchronized animation mechanism, such as a Choreographer/frame-clock-driven approach, where compatible with the existing Compose architecture.
- Avoid a simple fixed-delay coroutine loop if it causes scheduling drift or misses display frames.
- Avoid parsing the entire SVG on every frame.
- Precompute or cache appropriate animation data and reusable rendering resources.
- Sample the original animation timeline at appropriate intermediate times.
- Preserve original movement timing; do not accelerate Pacman merely to increase the frame count.
- Avoid unnecessary allocations, bitmap creation, SVG parsing, and Compose recompositions.
- Do not update Compose state if the displayed frame has not changed.
- Keep animation work bounded and cancellable.
- Pause when the graph is not visible.
- Resume when visible.
- Respect lifecycle and navigation changes.
- Prevent duplicate loops.
- Avoid retaining an Activity, View, or other lifecycle-bound object unintentionally.
- Avoid excessive CPU, GPU, or memory use.
- Keep the dark graph background and text palette consistent in every frame.
- Preserve the corrected graph dimensions and heat-map row count.

Do not introduce a WebView merely to obtain a higher frame rate.

If the existing SVG animation renderer cannot achieve 60 FPS, investigate a more efficient renderer or animation representation. Explain the trade-offs before introducing a dependency or substantial architectural change.

### 5.4 Frame timing and source resolution

The source animation may have a lower nominal frame rate or discrete motion steps. Inspect its actual temporal resolution.

The objective is smooth display updates, not meaningless duplication of identical frames.

If the source timeline permits meaningful intermediate sampling, sample it accurately.

If the source only defines discrete changes, do not fabricate motion or alter the animation's intended path. Report that limitation and explain whether it prevents genuine 60 FPS smoothness.

### 5.5 Runtime measurement

Use a real running emulator or physical device.

Record:

- Device model/emulator identifier.
- Android version.
- Display resolution and density.
- Supported display refresh rate.
- Actual active display refresh rate during the test.
- Measurement duration.
- Measurement method.
- Total visible frame presentations or validated frame changes.
- Effective FPS.
- Frame-time distribution, where available.
- Dropped or missed frames, where measurable.
- CPU and memory behavior.
- Whether the target is sustained.

Measure actual rendering/presentation where possible, not merely animation callbacks. Use Android frame-timing or rendering instrumentation where appropriate, and explain the limitations of the chosen measurement.

Perform a sustained test long enough to expose performance degradation, not merely a brief startup measurement.

Test:

- Graph visible.
- Graph hidden.
- Navigation away and back.
- Repeated expansion/collapse if supported.
- App background and foreground.
- Android light mode.
- Android dark mode.
- Device refresh-rate changes where supported.

The report must distinguish:

- 60 FPS configured.
- 60 animation callbacks per second.
- 60 generated frames per second.
- 60 visibly presented frames per second.

Only the last one satisfies the requirement.
