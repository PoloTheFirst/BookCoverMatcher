**Outcome, stated plainly: OneDrive folder access now works against a real Microsoft account — root listing,
folder navigation, download, save and offline open — for the first time in this project.**

The reason it never worked is one defect, and it was found by running the real flow, not by inspection: the silent
token request was built in a shape MSAL 8.6.0 refuses, so **no Graph access token was ever issued on any device**.
Interactive sign-in succeeded, the account was cached, and the very next call threw a plain
`IllegalArgumentException` — which the app classified as "the connection to OneDrive failed, so nothing was saved.
Try again when you are back online", while the device was online.

## 8 · Root cause, with evidence

`MsalOneDriveAuth.accessToken()` built the silent request like this:

```kotlin
pca.acquireTokenSilent(
    AcquireTokenSilentParameters.Builder()
        .forAccount(account)
        .withScopes(scopes)
        .withCallback(object : SilentAuthenticationCallback { … })   // (1) forbidden here
        .build(),
)
```

Two independent faults, both confirmed against the **shipped** artefacts of MSAL 8.6.0 (AAR bytecode from the Gradle
cache, and the matching `msal-8.6.0-sources.jar`):

1. **A callback must not be supplied to the synchronous call.** `acquireTokenSilentInternal` begins:
   ```java
   if (acquireTokenSilentParameters.getCallback() != null) {
       throw new IllegalArgumentException("Do not provide callback for synchronous methods");
   }
   ```
   …and then installs its own callback before dispatching. The device trace matches exactly:
   `IllegalArgumentException@PublicClientApplication.acquireTokenSilentInternal:2140`.
2. **An authority must be supplied explicitly.** With the callback removed, the next attempt failed at
   `validateAcquireTokenSilentParameters`, whose source is:
   ```java
   final String authority = parameters.getAuthority();
   final IAccount account = parameters.getAccount();
   final List scopes = parameters.getScopes();
   final SilentAuthenticationCallback callback = parameters.getCallback();
   validateNonNullArg(authority, NONNULL_CONSTANTS.AUTHORITY);   // ← null: we never set one
   validateNonNullArg(account, NONNULL_CONSTANTS.ACCOUNT);
   validateNonNullArg(callback, NONNULL_CONSTANTS.CALLBACK);
   validateNonNullArg(scopes, NONNULL_CONSTANTS.SCOPES);
   ```
   `forAccount(…)` only stores the account — it does **not** set the authority — and the builder's method is
   `fromAuthority(String)`. The device trace again matches:
   `MsalArgumentException@MsalUtils.validateNonNullArg:138|validateAcquireTokenSilentParameters:1849`.

The fix is therefore:

```kotlin
pca.acquireTokenSilent(
    AcquireTokenSilentParameters.Builder()
        .forAccount(account)
        .fromAuthority(account.authority)   // IAccount.getAuthority()
        .withScopes(scopes)
        .build(),
)
```

**Why it was invisible:** the throwable is a plain `IllegalArgumentException`, not an `MsalException`, so
`failureOf()` classified it `UNKNOWN`; `AuthFailure.UNKNOWN` mapped to `RemoteFailure.Unstable`, whose sentence is
*"The connection to OneDrive failed, so nothing was saved. Try again when you are back online."* Sign-in succeeded,
the account was cached, and every listing then failed with a message about the network. That is precisely the
symptom reported since crash-fix-1, and no amount of error-wording work could have revealed it, because the wording
was not the defect — the request was.

**Secondary defect fixed:** `AuthFailure.UNKNOWN` now maps to a new `RemoteFailure.AuthUnexpected`
("*…hit an unexpected error… this build needs updating*"), which names neither the network nor Microsoft. Only
`Offline` and `Unstable` may mention connectivity, and a test asserts that.

**Why no test caught it:** every OneDrive test fakes the auth layer or the HTTP client; MSAL's parameter validation
only runs on a device with an account. The trace added in crash-fix-5 is what produced the two stack frames that
identified it — the argument for keeping that trace.
