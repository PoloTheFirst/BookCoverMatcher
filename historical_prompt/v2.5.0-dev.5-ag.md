## 1. Implementation summary

Delivered:

1. **A feasibility verdict built from real artifacts** (not assumptions): the official PP-OCRv6 *medium* ONNX exports
   exist, their exact byte sizes and post-processing parameters were read from the models' own `inference.yml`, and
   the recognition dictionary (18,704 characters) was extracted from that file rather than guessed from a name.
2. **A Rust crate that is real, builds, and is tested**: `native/ocr` (`bc_ocr`), dependency-free, `cargo test`
   **13/13 green**, cross-compiled with NDK r27d to `libbc_ocr.so` for **aarch64-linux-android (300.4 KB)** and
   **x86_64-linux-android (326.2 KB)**, Android API 26.
   Implemented so far: the PP-OCR `CTCLabelDecode` index space + greedy CTC decoder (`dict`), and the geometry the
   recogniser's accuracy depends on — PaddleOCR's corner-ordering rule, quad orientation, affine solve and bilinear
   perspective crop (`geom`).
3. **Reproducible tooling and documentation**: `tools/fetch-ppocrv6-models.ps1` (size-checked download + dictionary
   extraction) and `native/ocr/README.md` (toolchain, exact build commands, model provenance, what is missing).
4. **The ONNX Runtime integration decision, with evidence**: `ort` 2.0.0-rc.15 exposes `api-17…api-31`,
   `load-dynamic` and `nnapi`; the app already ships ONNX Runtime **1.20.0**, so the only arrangement that cannot
   put two runtimes (or conflicting symbols) in one process is `api-20` + `load-dynamic` against the existing
   runtime. That is recorded for the next stage instead of being tried blindly.

Not delivered, deliberately: detector/recogniser inference, ONNX session layer, JNI exports, Kotlin wiring, model
packaging, accuracy/latency/memory measurement, NNAPI behaviour, and the removal of `chrome-lens-py`/Chaquopy.

**Why stop here rather than ship a half-working engine:** the release instructions forbid leaving the app without
OCR and forbid retaining two competing production paths without a documented reason. A native engine that has never
executed a model cannot replace a working one; it can only be added beside it until it is verified. This report is
that documented reason, with the remaining work specified precisely enough to finish without rediscovery.

## 3. Existing Python OCR architecture (Stage A baseline)

Traced end to end before touching anything:

* `app/src/main/python/lens_bridge.py` — the only Python file. Wraps the unmodified `chrome_lens_py` package
  (pinned `chrome-lens-py==3.8.2`, MIT), runs one `asyncio` loop per call on the calling thread, and returns an
  **envelope** dict: `{ok, text, block_heights, block_count, detected_language, translated_text, image_width,
  image_height, word_count, library_version}` or `{ok: False, error_code, error_message, error_detail}`. Text is one
  block per line; `block_heights` is the comma-joined geometry the app uses as its "is this the title" proxy.
* `online/ChromeLensPyBridge.kt` — implements `OcrTextSource` (`availability()` + `recognise()`); the only code that
  touches Chaquopy types. Python `dict` → Kotlin `Map` via `asMap()` (item lookup, not `getattr`), then
  `OcrResultParser` owns every mapping rule.
* `online/OcrTextSource.kt` — the contract to preserve: `OcrText(text, blockHeights, detectedLanguage,
  translatedText, wordCount, blockCount, libraryVersion)`; blank text is a *successful* empty scan; plus
  `OcrFailure`/`OcrException`/`OcrAvailability` and `OcrErrorMessages` for user-facing wording.
* `online/PythonRuntime.kt` — Chaquopy start-up and its failure reason; `OcrResultParser`, `OcrQueryExtractor`
  (OCR → search query), `OnlineSearchLog`.
* Build: Chaquopy 17.1.0 plugin, `pip { install("chrome-lens-py==3.8.2") }`, `abiFilters arm64-v8a, x86_64`,
  `minSdk 26`, build host needs CPython 3.12.
* **Dependency audit:** `chrome-lens-py` is the *only* Python consumer. Nothing else in the app imports Python, so a
  successful migration would let Chaquopy, `lens_bridge.py` and the `pip` block go — but only after the native path
  is proven (§9.1 Stage D). Until then they stay, and this release therefore removes nothing.

Not part of OCR and therefore untouched: OpenCLIP/ONNX Runtime matching (`libs.versions.toml`
`onnxruntime = "1.20.0"`), workbook parsing, wishlist, and reverse-image discovery (SauceNAO/IQDB).

## 4. Rust integration architecture (designed; session layer pending)

```text
Compose UI ── OnlineSearchController ── OcrTextSource (unchanged contract)
                                             │
                              ChromeLensPyBridge (today)      RustOcrTextSource (next stage)
                                             │                         │
                                     Chaquopy/Python            JNI: NativeOcr.nativeRecognise(rgba, w, h)
                                                                       │
                                                               libbc_ocr.so (bc_ocr)
                                                                       │
                                    dict ✓ · geom ✓ · det/rec/order (pending) · ort sessions (pending)
```

Decisions recorded for the next stage:

* **Owned bytes, never a pointer.** Kotlin passes an immutable `ByteArray` of decoded RGBA plus width and height;
  Rust copies it into its own buffer. No address of a `Bitmap`, `ByteBuffer` or worker thread crosses the boundary,
  and no native call terminates a thread — cancellation is "discard the result", keyed to the scan id.
* **Serialized inference.** One engine instance, one in-flight recognition at a time (a `Mutex` around the two
  sessions), which is the safe default §7.3 asks for.
* **Structured output.** `OcrLine { text, score, quad }` per detected line plus a reading-order rank; the JSON that
  crosses JNI is *derived* from that structure, never the other way round, so query generation keeps seeing lines.
* **Decoding stays on the platform** (`BitmapFactory`), so the crate needs no image codec and cannot decode the same
  bytes twice; EXIF orientation is therefore handled by the existing capture path.

## 5. ONNX Runtime compatibility findings

| Question | Finding |
|---|---|
| Runtime the app already ships | `com.microsoft.onnxruntime:onnxruntime-android:1.20.0` (used by OpenCLIP) |
| `ort` versions available | up to `2.0.0-rc.15` (the crate tracks ONNX Runtime 1.31 by default) |
| API-level features | `api-17` … `api-31`, each cumulative; `api-20` matches a 1.20 runtime |
| Linking strategies | default `download-binaries` + `copy-dylibs` (would add a *second* ORT to the APK) or `load-dynamic` (links nothing, resolves `libonnxruntime.so` at run time) |
| Chosen strategy | **`api-20` + `load-dynamic`**, so the crate uses the process's existing 1.20 runtime and cannot create a second one or clash symbols |
| Consequence | the Kotlin side must touch `OrtEnvironment` (or otherwise ensure `libonnxruntime.so` is loaded) before the first native call; this is a wiring requirement, not an assumption — it is untested |

The supplied example's `ExecutionProviderDispatch::new("NNAPI")?` does **not** exist in this crate version: execution
providers are registered through `ort`'s session builder (`Session::builder()?.with_execution_providers([...])`) and
`nnapi` is an opt-in cargo feature. Nothing was invented and nothing was enabled.

## 7. Dictionary and language support verification

* **Extracted**, not guessed: `PostProcess.character_dict` from the recognition `inference.yml`, in file order,
  verified as **18,704** single-character entries, which already span Latin, kana and CJK (**no** `en_dict.txt`).
* `Charset::class_count()` = dictionary + blank + optional space = 18,706 when `use_space_char` is true; **the true
  value must be read from the ONNX output width** (18,704 → no space class, 18,705 → space class) before the first
  inference. That check is implemented as a rule (`class_count`) but has **not** been run against the graph, because
  no session was created.
* Index shift is unit-tested (`index_space_is_shifted_by_the_blank_class`), including the optional trailing space —
  the mistake that would otherwise mis-map *every* character.
* **Language results: Not Run.** Japanese, Traditional Chinese, Simplified Chinese and English have not been
  recognised, because no inference has been executed. No accuracy number is claimed anywhere in this release.

## 8. Detector implementation status

**Not implemented.** Captured specification for the next stage (from the model's own config, §6):

1. decode → RGBA→BGR, resize with ratio preserved so `max(h, w) = limit_side_len` (736), pad to a multiple of 32;
2. normalize with the ImageNet means/stds above, CHW layout, `f32`;
3. run the det session → probability map `[1, 1, H, W]`;
4. threshold at 0.2, extract regions, score each by the mean probability inside it, keep ≥ 0.45, at most 3000;
5. unclip by 1.4 (rectangle offset), clamp to the image, restore coordinates by the preprocessed scale;
6. emit `Quad`s in source-image space (through `geom::Quad::ordered`), dropping anything `!is_valid()`.

The container/contour step is the one design choice left open: no OpenCV is available in the crate, so the plan is
8-neighbour connected components + convex hull + min-area rectangle via rotating calipers, documented as an
approximation of `cv2.minAreaRect`.

## 9. Recognition implementation status

Partially implemented and tested: **decoding** (`dict`) and the **crop/rectification** that precedes it (`geom`).

Still missing: the 48×320 BGR preprocessing (ratio-preserving pad, `/255`, `(x/255-0.5)/0.5`), output head
selection (the graph must be inspected for a CTC head vs a second NRTR head before decoding — the configuration
declares `MultiLabelEncode` with `gtc_encode: NRTRLabelEncode`, so *two* heads are plausible and the CTC one must be
picked by name/shape rather than assumed to be `output[0]`), batch composition, and the trailing-pad trim.
