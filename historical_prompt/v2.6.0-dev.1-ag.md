## 3 · Architecture inspection findings (deliverable 1)

Single-module Android app, **no DI framework**: every controller is constructed in
`MainViewModel(app: Application)` with the application context, and composables receive the
`MainViewModel`. A new monitor/source must follow that shape (a constructor parameter with a
default, as `WorkbookCommentsController` already does for its cache and message channel).

```
Compose UI (ui/*)  ──▶  MainViewModel (single UiState StateFlow)
                          ├─ camera / ort / autoscan
                          ├─ WorkbookCommentsController  (file → parse → UiState)
                          ├─ data.WorkbookLibrary        (files/workbooks + library.json)
                          ├─ OnlineSearchController      (opt-in; HttpJsonClient)
                          └─ WishlistRepository          (files/wishlist + records.json)
```

Relevant, verified facts:

| Area | Actual implementation |
|---|---|
| `core/` purity | `ARCHITECTURE.md` requires plain JVM (no `android.*`). Verified by inspection: `core/**` has no Android imports; `data/**` and `online/**` are the Android-aware layers. |
| Storage | Everything under `filesDir` / `cacheDir`: `books`→`workbooks/`, `comments/`, `mappings/`, `wishlist/`, `index` (in `cacheDir`), preferences via `SharedPreferences`. |
| Saved-workbook index | `library.json` in `files/workbooks`, written by `WorkbookLibrary.writeAll` as temp file + rename. |
| Secrets | `core/secret/AesGcmSecretBox` (plain-JVM AES-256-GCM envelope) + `data/SauceNaoKeyStore` (AndroidKeyStore-held key, ciphertext in its **own** `SharedPreferences` file). This is the precedent a OneDrive token store must reuse. |
| Networking | `online/HttpJsonClient` is the only socket user. `HttpURLConnection`, HTTPS only, 10 s connect / 20 s read, **buffered** bodies with a hard byte cap (`readLimited`), no custom headers, no streaming sink, no `Retry-After` parsing. |

### 3.1 The saved-workbook model as it actually is

`data/WorkbookLibrary.kt`:

```kotlin
data class SavedWorkbook(
    val id: String, val displayName: String, val originalName: String, val format: String,
    val fileName: String, val sizeBytes: Long, val sha256: String, val importedAt: Long,
    val lastOpenedAt: Long?, val pinned: Boolean,
    val sheetCount: Int? = null, val commentCount: Int? = null, val imageCount: Int? = null,
)
class WorkbookLibrary(private val dir: File) {
    companion object { const val SCHEMA_VERSION = 1; val SUPPORTED = setOf("xlsx", "xlsm") }
}
```

Operations: `list()` (pinned → lastOpened → imported → id), `byId`, `fileOf`, `import(input,
originalName, now)`, `rename`, `setPinned`, `touch`, `remove(id): Pair<Boolean,Boolean>`,
`bytes()`, `setSummary(id, sheets, comments, images)`.

`import` already does everything a OneDrive download needs **except streaming from a network sink
it cannot cancel**:

1. reject non-`.xlsx/.xlsm` by name (`SUPPORTED`);
2. write to `import.tmp` hashing with SHA-256 and counting bytes;
3. reject size `<= 0`;
4. verify the **ZIP signature** (`0x50 0x4B`) by reading 4 bytes of the temp file;
5. reject identical bytes as `ImportResult.AlreadySaved` (by sha256);
6. allocate a unique id from the sha256 prefix, rename `import.tmp` → `<id>.<ext>`;
7. append the entry and `writeAll` (temp + rename); a failed index write deletes the copy.

`ImportResult` = `Added` / `AlreadySaved` / `Rejected(message)`.

### 3.2 The schema-1 read path (the migration hazard)

`readAll()` (verified, lines 233–265):

```kotlin
val root = MiniJson.parse(file.readText(...)) as? Map<*, *> ?: return emptyList()
if ((root["schema"] as? Double)?.toInt() != SCHEMA_VERSION) return emptyList()   // ← strict equality
```

and the whole body is wrapped in `try { … } catch (e: Exception) { runCatching { file.renameTo(
File(dir, "library.json.bad")) }; emptyList() }`.

Two consequences that decide the migration design:

* bumping `SCHEMA_VERSION` to 2 **without** a schema-1 branch makes every existing library read as
  **empty** (silently — not even quarantined, because it is not an exception);
* a schema-1 file must therefore be **parsed deliberately**, not thrown at a `when` that falls
  through to "unsupported", and a *malformed* document must keep the existing quarantine behaviour
  instead of being overwritten by the first later write.

## 4 · Existing workbook import / open / Rescan flow (deliverable 2)

There are **two independent entry paths** today, and they must not be confused.

### 4.1 Picked file → scan source (Home / Search)

```
OpenDocument()  → MainViewModel.onWorkbookPicked(uri)
                    ├ WorkbookFiles.stage(app, uri)   copies to cache/workbook/current.xlsx,
                    │                                 hashing it (SHA-256) while copying
                    ├ openWorkbook(file).close()      fail-early: ZipFile + requireWorkbook()
                    └ UiState.workbook = WorkbookUi(name, sizeText); staged = StagedWorkbook(...)

"Workbook comments" (More) → openWorkbookComments() → comments.open(staged.file, staged.sha256, name)
```

`staged: StagedWorkbook?` is `MainViewModel`'s single in-memory source; `StagedWorkbook(file,
displayName, sizeBytes, sha256)` is the one currency the scanner accepts.

### 4.2 Saved-workbook library (More → Saved workbooks)

```
"Import" (WorkbookLibraryScreen:80-87) → OpenDocument() → MainViewModel.importWorkbook(uri)
        ├ library.import(contentResolver.openInputStream(uri), displayName)   [§3.1]
        └ toast Added / AlreadySaved / Rejected → refreshSavedWorkbooks()

Row "Open" → openSavedWorkbook(id)
        ├ library.byId → fileOf → isFile? else "The saved copy is missing; import the workbook again."
        ├ library.touch(id)
        ├ comments.open(file, entry.sha256, entry.displayName, importedAt = entry.importedAt)
        └ watchSummary(id)  → waits for the first parse, then library.setSummary(...)

Row Rename / Pin / Remove → library.rename / setPinned / remove
        Remove also runs CommentImageCache(commentsDir).remove(entry.sha256) and never touches the
        original imported file.

Home/Search "Saved" → openSavedWorkbookPicker() → SavedWorkbookSourceDialog
        → useSavedWorkbook(id)
             ├ openWorkbook(file).close()   (the same fail-early validation)
             ├ staged = StagedWorkbook(file, entry.displayName, size, entry.sha256)
             └ picker closes, toast "Scanning source: …"
```

`SavedWorkbookSourceDialog` reads `ui.savedWorkbooks`, so **any entry added to the library appears in
the picker automatically** — the "no second library" requirement is already satisfied by construction.

### 4.3 Rescan (the one place Phase 5 must intervene)

`ui/WorkbookCommentsScreen.kt:216-222` binds `onClick = controller::reload`. `reload()`
(lines 213–228) re-scans `source` with the **old** hash:

```kotlin
val state = _ui.value
if (state.sha256.isBlank()) return
job = scope.launch {
    apply(withContext(Dispatchers.IO) { scan(file, state.sha256, state.workbookName) }, state.sha256)
}
```

**Verified hazard:** `state.sha256` is also the `CommentImageCache` key (`cache.write` / `cache.read`).
If a Phase 5 update replaces the bytes of `source` in place and then calls `reload()`, the new
workbook is parsed but cached **under the old hash**, and `UiState.comments.sha256` still describes
the old bytes. The safe sequence after a replacement is `comments.open(file, NEW_sha256, name,
importedAt)` — a full re-open with the new hash — not `reload()`. `open()`'s early-return guard
(`open && sha256 == sha256 && !loading`) then correctly treats it as different bytes.

`WorkbookCommentsController` stays **Graph-free** (prompt §4.6): `MainViewModel` hands it a `File`
and a hash, exactly as today.

### 4.4 Where a Rescan can be started from

Only from inside the preview (`CommentsHeader`), and it is reachable for every origin: a library
entry, a Home-picked file, or a Home "Saved" entry all end in `comments.open(...)`. The controller
does not know — and must not learn — which library entry the open file belongs to; `MainViewModel`
holds that mapping (open `sha256` ↔ library entry) and is the right owner of a remote check.

## 6 · Microsoft Graph and authentication recommendation (deliverable 4)

### 6.1 Recommendation: **MSAL for Android** (`com.microsoft.identity.client:msal`), behind our own gateway

Evidence gathered for the decision:

| Question | Finding |
|---|---|
| Latest stable | **8.6.0** (`repo1.maven.org/…/msal/maven-metadata.xml`: `<release>8.6.0</release>`, updated 2026-10-21) |
| Licence | **MIT**, declared in the artifact's own POM (`<licenses><license><name>MIT License</name>`), confirmed by the upstream README ("Licensed under the MIT License") |
| Personal accounts | First-class (README: "Microsoft Personal Accounts … using industry standard OAuth2 and OpenID Connect") |
| Public client | Yes — no client secret anywhere; PKCE is MSAL's default for a public client |
| Token cache | MSAL keeps its own Keystore-backed encrypted cache, so **no custom token file** is needed on the happy path |
| Cost | **11 transitive artifacts** (gson, nimbus-jose-jwt, httpcore5, opentelemetry-api, androidx.appcompat / browser / constraintlayout, `com.microsoft.identity:common`, kotlin-stdlib, coroutines) — the real price of this decision (§13) |

Against a hand-rolled OAuth/PKCE client: the prompt says not to write custom OAuth merely to avoid a
dependency, and this codebase's own HTTP layer (`HttpJsonClient`) has no capability for an
interactive browser round-trip, redirect interception, token refresh or an account cache. Writing
that by hand would be new security-sensitive code with no test culture behind it, while MSAL's flow
is Microsoft-maintained. **Decision: MSAL 8.6.0**, with one build-time check — MSAL's own `minSdk`
must be confirmed from the AAR before adopting this version (project floor is `minSdk 26`). If it is
higher, the fallback is the newest MSAL that satisfies 26, **not** a hand-written flow.

MSAL is wrapped in `OneDriveAuth` so no composable and no repository touches MSAL types: the rest of
the app sees `suspend fun accessToken(): Result`, `suspend fun signIn()`, `fun signOut()`, and
`val account: StateFlow<AccountState>`.

### 6.2 Graph surface actually used (read-only)

| Operation | Request | Notes |
|---|---|---|
| Root listing | `GET https://graph.microsoft.com/v1.0/me/drive/root/children?$select=id,name,folder,file,size,eTag,lastModifiedDateTime&$top=200` | `@odata.nextLink` for pagination |
| Child listing | `GET /me/drive/items/{folderId}/children?$select=…&$top=200` | same shape |
| Metadata probe | `GET /me/drive/items/{itemId}?$select=id,name,size,eTag,cTag,lastModifiedDateTime,parentReference` | change detection |
| Content | `GET /me/drive/items/{itemId}/content` | **302 → pre-authenticated URL** (see below) |

Only `Files.Read` (delegated) is requested. No `Files.ReadWrite`, no `Sites.*`, and no write verb is
ever issued — "never modify the original" is structural, not a policy.

**Verified-important detail for Phase 3:** `/content` answers with a 302 to a pre-authenticated
download URL, and the bearer token must **not** be forwarded to that target. `HttpURLConnection`
re-sends request properties across a redirect, so `GraphHttp` must either follow the 302 manually
with a credential-free second request, or prove by test that the token is not leaked. That is both a
correctness and a security task and it is in the test matrix (§14).

### 6.3 Failure taxonomy (maps 1:1 onto the prompt's §7 messages)

`RemoteFailure` → `OFFLINE` (preflight only) · `AUTH_REQUIRED` / `AUTH_EXPIRED` · `THROTTLED`
(429/503 + `Retry-After`) · `NOT_FOUND` (deleted/moved) · `TIMEOUT` · `UNSTABLE` (stalled read or
repeated transport error) · `NO_STORAGE` (ENOSPC) · `INVALID_WORKBOOK` (post-download validation) ·
`SERVER_ERROR` · `CANCELLED`. Each maps to one user-facing sentence from prompt §7; nothing collapses
into "something went wrong".

## 9 · Schema 1 → schema 2 migration design (deliverable 7)

### 9.1 Model change (names follow the existing style — camelCase Kotlin, short JSON keys)

`SavedWorkbook` gains **one** nested, nullable block, so a local entry writes nothing new and every
existing construction site keeps compiling:

```kotlin
enum class WorkbookOrigin { LOCAL, ONEDRIVE }

data class RemoteOrigin(
    val itemId: String,        // Graph driveItem id — the identity of the remote file
    val path: String,          // display only, e.g. "Catalogue/2026/covers.xlsx"
    val eTag: String?,         // change detection
    val lastModified: Long?,   // remote mtime (epoch ms), display + secondary comparison
    val sizeBytes: Long?,      // remote size, display + secondary comparison
    val syncedAt: Long?,       // last successful sync
    val checkedAt: Long?,      // last remote probe
)

data class SavedWorkbook(
    …,                                   // every existing field unchanged
    val origin: WorkbookOrigin = WorkbookOrigin.LOCAL,
    val remote: RemoteOrigin? = null,    // non-null iff origin == ONEDRIVE
)
```

### 9.2 `library.json` schema 2

```json
{ "schema": 2,
  "workbooks": [
    { "id":"…","name":"…","original":"…","format":"xlsx","file":"….xlsx",
      "bytes":123,"sha256":"…","imported":1700000000000,"opened":null,"pinned":false,
      "sheets":8,"comments":999,"images":165,
      "origin":"LOCAL" },
    { "…":"…", "origin":"ONEDRIVE",
      "remote": { "itemId":"01ABCD…","path":"Catalogue/covers.xlsx","etag":"\"{…},3\"",
                  "modified":1700000000000,"bytes":123,"synced":1700000000100,
                  "checked":1700000000200 } }
  ] }
```

`origin` is written explicitly (not inferred from a non-null `remote`), so a future origin cannot be
mis-read as local; `remote` is omitted for `LOCAL`. `MiniJson` already writes `Long`/`Int` natively
and parses numbers back as `Double`, which the existing `(map["bytes"] as? Double)?.toLong()` idiom
already handles — no JSON dependency is added.

### 9.3 Read path (`readAll`) — the mandatory part

```kotlin
val schema = (root["schema"] as? Double)?.toInt()
val entries = when (schema) {
    2 -> parseV2(root)
    1, null -> parseV1AsLocal(root)        // ← migration, in memory
    else -> return emptyList()             // unknown/future schema: leave the file alone
}
if (schema != 2) runCatching { writeAll(entries) }   // rewrite once, atomically, as schema 2
return entries
```

Rules the implementation must obey, each derived from the verified code:

1. **Schema 1 is read, never rejected.** A missing `schema` key means schema 1 (that is what an early
   file looks like) — not corruption.
2. **Migration is in-memory first, then one atomic rewrite** through the existing temp-file + rename
   path. If the rewrite fails, the schema-1 file survives and the next read retries; the library keeps
   working in the meantime.
3. **Every schema-1 field keeps its meaning**: `id`, `name`, `original`, `format`, `file`, `bytes`,
   `sha256`, `imported`, `opened`, `pinned`, `sheets`, `comments`, `images`. Only `origin = LOCAL` is
   *added*.
4. **A malformed document keeps today's behaviour** — quarantined to `library.json.bad`, read as
   empty — because a document that cannot be parsed cannot be migrated honestly.
5. **An unknown future schema is left untouched** (empty list, no write), so an older build cannot
   silently downgrade a newer file.
6. **A bad entry drops only that entry** (the existing `mapNotNull` behaviour), never the whole list.
7. **Sorting, ids, file names and `remove`/`rename`/`setPinned`/`touch`/`setSummary` are unchanged.**

### 9.4 Why migrate instead of "read both schemas forever"

A schema-2 writer that keeps emitting schema 1 cannot express a OneDrive origin, and two readers that
never converge drift apart. Migrate-on-read + rewrite-once is the smallest change that keeps a user's
library intact and makes the new data expressible.

## 10 · Folder browsing and Graph pagination design (deliverable 8)

### 10.1 Pure, testable browsing state (no Android, no Graph)

```kotlin
data class RemoteFolder(
    val id: String?,                 // null = OneDrive root
    val name: String,                // "" for root, rendered as "OneDrive"
    val displayPath: String,         // "OneDrive / Catalogue / 2026", display only
    val parentId: String?,           // null at root → "up" is disabled there
    val folders: List<RemoteItem>,   // folders only
    val files: List<RemoteItem>,     // supported workbooks only
    val nextPage: String?,           // opaque @odata.nextLink, or null
)

data class RemoteItem(
    val id: String, val name: String, val isFolder: Boolean,
    val sizeBytes: Long?, val eTag: String?, val lastModified: Long?, val path: String,
)
```

`RemoteWorkbookSource.listFolder(folderId: String?, pageToken: String?)` returns one page; the
browse state in `UiState.oneDrive` keeps a **stack** of `(folderId, name)` so "up" pops instead of
re-deriving a path from a string, and appending a page never duplicates a row (dedupe by `itemId`).

### 10.2 Filtering

Supported files are **`.xlsx` and `.xlsm` only**, decided by the same rule the library already uses
(`WorkbookLibrary.SUPPORTED` on the lowercased extension). Everything else is not listed as
importable; folders are always listed. A name with no extension, or `book.xlsx.tmp`, is not a
workbook.

### 10.3 Pagination

`$top=200` per request; the response's `@odata.nextLink` is stored verbatim as `nextPage` and sent
back as the whole URL on "Load more". The UI shows a *Loading more…* state and a **Load more** action;
a failed page keeps the rows already shown and reports the failure, never silently truncating. A
page that returns a token seen before is treated as an error, so a server-side loop cannot spin.

## 11 · Streaming download, progress, cancellation and safe replacement (deliverable 9)

### 11.1 The download primitive

```kotlin
suspend fun download(
    item: RemoteItem,
    sink: OutputStream,
    onProgress: (bytes: Long, total: Long?) -> Unit,
): DownloadOutcome            // Completed(bytes) | Failed(RemoteFailure) | Cancelled
```

* **Streams only.** One 128 KiB buffer (`WorkbookFiles.stage` and `WorkbookLibrary.import` already use
  that size) copied in a loop — the workbook is never held in memory, and there is **no
  application-level size cap**. `Content-Length` gives a determinate percentage when present and
  `null` (indeterminate) when it is not.
* **Cancellation** is cooperative: the copy loop checks `isActive` (or a cancellation signal), closes
  the connection and deletes the temp file. `HttpURLConnection.disconnect()` in a `finally` is what
  actually unblocks a stalled read.
* **Progress** at most every ~64 KiB or 100 ms, whichever is later, so the UI stays smooth without
  throttling the loop.
* **Failure mapping** per §6.3; an `IOException` is inspected for `ENOSPC`/`EFBIG` before being called
  a generic transport error, because "device storage is full" needs its own sentence.

### 11.2 Temporary file and commit

`files/workbooks/<id>.<ext>.part` beside the real file:

1. create the `.part` (never `<id>.<ext>`, so a partial file can never be mistaken for a saved
   workbook — `list()` reads `library.json` and `bytes()`/`fileOf()` use only recorded entries, so a
   stray `.part` is invisible to both);
2. stream into it, hashing SHA-256 on the way (the `MessageDigest` loop already in
   `WorkbookLibrary.import`);
3. on **any** failure or cancellation: delete the `.part` and change nothing else;
4. validate the finished file with **the existing rules** — non-zero size, `0x50 0x4B` ZIP signature,
   and `WorkbookImageExtractor.requireWorkbook(ZipFile(file))` (what `openWorkbook` does) — not a new
   validator;
5. commit through the existing pattern: rename the `.part` into `<id>.<ext>`; for an update rename the
   current file to `<id>.<ext>.old`, move the new file into place, delete the `.old` — and restore the
   `.old` if anything fails, so the previous copy is byte-identical until the new one is verified;
6. write the entry/metadata with `writeAll` (temp + rename); a failed index write rolls the copy back,
   exactly as `import` already does.

**First import** keeps `WorkbookLibrary.import`'s rules (extension, ZIP signature, non-empty,
identical bytes → `AlreadySaved`) but through a `File`-based variant, so nothing is ever buffered.

### 11.3 Remote update (Rescan-only) sequence

```
Rescan pressed
  → is this open workbook a ONEDRIVE entry?        (MainViewModel mapping; no Graph in the controller)
      no  → comments.reload()                      today's local path, unchanged
  yes → offline?        → local reload + "Offline: showing the copy saved on this device…"
      → token expired?  → local reload + "Your OneDrive sign-in expired…"
      → probe(itemId)   → NOT_FOUND → local reload + "This workbook is no longer in OneDrive…"
                        → TIMEOUT/THROTTLED/UNSTABLE → local reload + "OneDrive took too long…"
                        → unchanged (eTag equal)      → local reload + "Up to date." + checkedAt
                        → changed → ask "A newer version is on OneDrive (<size>, <date>).
                                          Update the saved copy? …"
                            decline → local reload, metadata untouched
                            accept  → download .part (progress + Cancel) → validate → replace
                                    → update metadata (eTag/size/modified/synced/checked/sha256)
                                    → comments.open(file, NEW_SHA256, name, importedAt)
                                    → toast "Updated from OneDrive."
```

Every "→ local reload" is `comments.reload()` (the bytes did not change, so the old hash is still
correct); only an accepted update re-opens with the **new** hash (§4.3). If any step before the
replacement fails, the local copy **and** its metadata stay as they were.

### 11.4 Change detection

Primary: `eTag` inequality (or `cTag`). Secondary, only when the `eTag` is absent: `lastModified` or
`sizeBytes` differing. A missing metadata pair never counts as "unchanged" — the answer is *unknown*
and the UI asks instead of guessing.

## 12 · Security and token-storage design (deliverable 10)

| Requirement | Design |
|---|---|
| Tokens never in `library.json` | The index holds only `SavedWorkbook`; `RemoteOrigin` stores ids/paths/etags/timestamps — **never** a token, an `Authorization` value or an account identifier |
| Keystore-backed protection | MSAL's cache is the primary store (encrypted, Keystore-backed). Anything we must hold ourselves goes through `AesGcmSecretBox` with an `AndroidKeyStore` key, in its **own** `SharedPreferences` file — `SauceNaoKeyStore`'s exact shape |
| The CALLER_NONCE lesson | `AesGcmSecretBox` documents why encryption must let the cipher choose the IV (`setRandomizedEncryptionRequired(true)` makes a caller-supplied nonce fail with `CALLER_NONCE_PROHIBITED`). New sealing code reuses that object instead of re-deriving the v2.5.0-dev.2 defect |
| Never logged | no token, header, code or client id reaches `showToast`, `OnlineSearchLog`, `Log.*` or an exception message. Errors carry a `RemoteFailure` value plus a fixed sentence; `GraphHttp` keeps the header out of its exception messages |
| Header not forwarded | the 302 from `/content` targets a pre-authenticated URL and must not receive the bearer token (§6.2) |
| Sign-out | clears MSAL's account and our `AccountState`; saved workbooks and their files stay |
| Failure isolation | an auth/Graph failure degrades to "local copy works, remote check unavailable"; it can never disable the library or block an offline open |
| Transport | HTTPS only (`HttpJsonClient` already refuses anything else; `GraphHttp` keeps that rule) |
| Backup | `android:allowBackup="false"` is already set, so tokens cannot leave the device through backup |

### 17.3 Design decisions (and why)

1. **The capability rule is extracted, not inlined.** `UsableNetwork.accepts(hasInternet, isValidated)`
   is pure, so "connected but not validated" is a real assertion on the JVM instead of a branch only
   an emulator could exercise. The Android class reads the two capabilities and delegates.
2. **Two members, two questions.** `isOnline` (flow) is what a screen draws; `isUsableNow()` is a
   *fresh* platform read for a preflight. A flow's cached value can be stale exactly when the user
   taps a button — the network may have dropped while the app was in the background before a callback
   arrived.
3. **A callback never decides the answer; it triggers a re-read.** `onAvailable`/`onLost`/
   `onCapabilitiesChanged` all call `refresh()`, which re-reads the default network's capabilities.
   That is what makes the *unvalidated → validated* edge (captive portal finishing its login) land
   correctly instead of being missed.
4. **Thread-safety without locks.** The callbacks arrive on a binder thread; `MutableStateFlow` is
   thread-safe and the state is always recomputed from the platform, so a burst of events cannot
   leave a stale value.
5. **Guards instead of crashes.** Registration and capability reads are wrapped. If the platform
   refuses (`SecurityException`), `isUsableNow()` answers **true** — "possibly online" — so a OneDrive
   attempt fails with the *real* reason (sign-in, throttling) instead of a false "No internet
   connection". A monitor that lied "offline" would send the user to fix a network that is fine.
   When registration is refused, the monitor still answers on demand, which is precisely why
   `isUsableNow()` exists alongside the flow.
6. **`close()` is idempotent and fails closed.** It unregisters only if it registered, and always
   drops the published state to `false`, so a released monitor can never look online to a late caller.
7. **`core/` purity kept.** The new interface lives in `core/net/` with **no `android.*` import**;
   `StateFlow` is a JVM type. This is the first coroutines import in `core/`, which is deliberate (the
   prompt asks for an observable state) and does not weaken the documented "plain Kotlin/JVM" rule.
8. **No call sites yet, on purpose.** The monitor is constructed and released by `MainViewModel` but no
   feature consults it until Phases 4–5. That keeps this phase reviewable on its own and prevents a
   half-wired gate from silently blocking a local path.

### 18.3 Design decisions (and why)

1. **Fields appended, not reordered, with defaults.** `origin = LOCAL`, `remote = null`. A schema-1
   entry and a locally imported workbook are then *the same thing by construction*, so no call site had
   to learn about OneDrive and no test had to be rewritten.
2. **Migration in memory first, file second.** `readAll` parses before it writes, so a failed rewrite
   cannot cost the user the entries: they are returned anyway and the rewrite is retried on the next
   read. This is the difference between "the library did not upgrade yet" and "the library is empty".
3. **The migration rewrites only when *every* object parsed.** If the file holds a record this build
   cannot read, the rewrite is skipped and the file stays at schema 1. Deleting a record the app does
   not understand — during a migration the user never asked for — would be data loss dressed up as an
   upgrade. The valid entries are still returned and still work.
4. **`replaceIndex` closes a real data-loss window.** The previous writer did
   `target.delete(); tmp.renameTo(target)`. `File.renameTo` reports failure by returning `false`, not by
   throwing, so a failed rename left the library with **no** index at all — the user's whole visible
   list, gone. It now uses `Files.move(…, ATOMIC_MOVE)` (one step, `java.nio.file` is available from API
   26, which is this app's `minSdk`), and only if that is unsupported does it fall back to
   rename-to-backup → rename-into-place → restore-on-failure.
5. **A newer schema blocks writes, not just the migration.** Reading a schema-3 file as empty is
   harmless; *rewriting* it as schema 2 would destroy a library a newer build wrote. `writeAll` refuses
   while the flag is set, and `import` reports the real reason instead of a disk error.
6. **Unknown values degrade, they do not hide.** `origin: "dropbox"` reads as `LOCAL` rather than
   dropping the entry, and an `ONEDRIVE` entry with no usable `remote` block also reads as `LOCAL` —
   it could never be checked or refreshed, so pretending it is OneDrive would only create a row that
   cannot work.
7. **`setRemote` is the single writer of the OneDrive origin.** It changes the origin and the remote
   block and nothing else: copy, id, file name, display name, pin, recency and counts are preserved, so
   a later remote failure can never damage what the user already has. It exists now because without it
   the schema-2 `remote` block would have no write path and could not be tested; Phases 3–5 build on it.
8. **One schema, one file.** No second index, no sidecar, no migration flag file: `library.json` stays
   the only authority, exactly as `ARCHITECTURE.md` says.

### 19.5 A bug found by that verification (and fixed)

The first version declared the `.env` as `inputs.file(...).optional()`. Two problems, both caught
because the placeholder test asserted the **generated content** rather than the exit status:

1. Gradle 9 rejects a missing `@InputFile` outright — `Input file does not exist … Property 'dotEnv'` —
   so **a fresh clone could not build at all**;
2. even had it been accepted, an absent optional file contributes nothing to the fingerprint, so adding
   or deleting `.env` would have left the task `UP-TO-DATE` with a **stale** configuration — silently
   producing placeholders after the owner adds a real `.env`.

The input is now a SHA-256 **digest** of the file — or the literal `"absent"` — through the build
script's existing `sha256OfFile` helper: presence and content are both inputs, and only a digest is
recorded. The three-way test in §19.4 (present → absent → present) is what proves the fix.

### 20.3 The runtime configuration design (what changed from §19)

§19 deliberately kept the generated configuration out of the APK. That was right for hiding `.env`, but
wrong for MSAL: a public client cannot sign in without its client id and redirect URI. The design is now:

| Artefact | Packaged? | Why |
|---|---|---|
| `.env` (root) | **never** | Machine-local; git-ignored, untracked, and no build step copies it into the app |
| `app/src/main/res/raw/msal_config_default.json` | **yes** | MSAL reads it as `R.raw.msal_config_default`. Generated, git-ignored. Contains only the **public** client id, redirect URI and fixed flags |

### 20.5 Authentication and token cache

* **Public client, PKCE, personal accounts only.** `PublicClientApplication.createMultipleAccountPublicClientApplication(context, R.raw.msal_config_default)`; scopes `Files.Read` and `User.Read` only; authority derived from `PersonalMicrosoftAccount` → `login.microsoftonline.com/consumers`.
* **Sign-in** (`signIn(activity)`) starts the interactive flow on the main thread with `AcquireTokenParameters`; closing the page is `onCancel` → state `SignedOut`, never an error.
* **Token acquisition** (`accessToken()`) runs on `Dispatchers.IO`: cached account → `acquireTokenSilent`. `MsalUiRequiredException` → state `Expired` + `TokenResult.Failure(INTERACTION_REQUIRED)`, which the Graph layer maps to `AUTH_EXPIRED` so the UI can say *"sign in again"* rather than *"sign in"*.
* **Sign-out** removes every cached account (`removeAccount`) and sets `SignedOut`. It never touches a saved workbook — the library has no link to the account.
* **Token storage is MSAL's encrypted cache.** No custom token file, no preference, no plaintext. `AccessToken` is a value class whose `toString` is `AccessToken(***)`, so an accidental interpolation cannot leak one; a test asserts this.
* **Nothing is logged.** No MSAL exception message is rethrown or printed (those can carry identifiers); failures are reduced to the app's own `AuthFailure` codes. `AuthState` carries a username at most — never a token.

### 21.2 Architecture: where each thing lives

The rule was *the ViewModel owns immutable `UiState`; decisions live in a tested object; the composable
only draws*.

* **`OneDriveNavigation`** (pure, no I/O) — enter a folder, go up, replace/append a page. Two properties
  matter: a folder is entered by **id** (never by name), and an appended page is de-duplicated by id
  because OneDrive can repeat an item across a page boundary.
* **`OneDriveBrowse`** (immutable) — the path stack plus the loaded folders/files/`nextPageToken`. It holds
  `RemoteItem` values, so the id a request uses and the name the user reads travel together and nothing
  ever builds a URL from a filename.
* **`OneDriveSession`** — the only place that touches the network: connectivity preflight, `listFolder`,
  `SafeWorkbookDownload`, then `WorkbookLibrary.import` + `setRemote`. It returns `OneDriveListing` /

### 21.7 Known limitations, deviations and deliberate omissions

1. **The Compose layer has no UI test.** The rules it branches on are tested; the composable itself only
   compiles. This matches every other screen in this project (no Compose UI-test dependency was added,
   because adding one is a dependency decision, not a Phase 4 decision).
2. **`OneDriveImportOutcome.Failed.detail` is defensive code.** The download validator already applies the
   library's extension and OOXML rules, so a file the library would reject on its own terms is normally
   rejected earlier — the test asserts the message-less path. The field stays because a genuine library
   rejection (e.g. storage unavailable at write time) should show the library's sentence, not a generic one,
   and that path cannot be forced without making `WorkbookLibrary` an interface (which the phase boundary
   forbids).
3. **Duplicate imports can link an existing entry.** If the identical bytes are already saved as a *local*
   entry, importing them from OneDrive records the OneDrive source on that entry (origin becomes
   `ONEDRIVE`). This is deliberate — it is what makes a later remote check (Phase 5) possible without
   duplicating the file — but it does change an entry the user created locally. An entry that already
   points at a *different* OneDrive item is never changed.
4. **`remote.sizeBytes` is the size OneDrive reported**, not the number of bytes written. That is the right
   value for Phase 5's comparison, and it is why a test asserts 4096 for a fixture whose package is 871
   bytes.
5. **No request cancellation over the wire.** `Cancel` cancels the coroutine and the `.part` is deleted, but
   the in-flight HTTP read is abandoned rather than aborted at the socket level (Phase 3's `GraphHttp` keeps
   it simple). On a slow link the connection may linger until the read times out.
6. **Retry re-lists the current folder instead of resuming a download.** A failed download returns to the
   browser with its sentence; the user taps the file again. Resuming a partial transfer is not attempted
   (it would need `Range` support and a second validation path).
7. **The account label is shown, not hidden.** `Signed in as <name>` is drawn from MSAL's display name. No
   token, id token or tenant id is stored in `UiState`, logged, or put in a report; `.env` values never reach
   `UiState` at all.
8. **One operation at a time.** A download blocks navigation and a second import; there is no queue. This is
   intentional for a phone-sized screen, and it is what makes cancellation unambiguous.
9. **Both `signInToOneDrive` and the dialog accept an `Activity?`.** MSAL needs one to launch the browser;
   the dialog obtains it from `LocalContext` with a small `ContextWrapper` walk. If the composition is not
   hosted by an Activity (never the case here) the sign-in is reported as signed-out instead of crashing.
10. **Nothing of Phase 5+ was started.** No rescan-triggered remote check, no metadata comparison, no update
    /replacement flow, no background sync, no automatic refresh on open, no upload, no write-back, no remote
    deletion. `Rescan` still does exactly what it did before this phase.

### 22.3 The comparison, exactly

`RemoteChangeDetector.compare(savedETag, savedCTag, savedLastModified, savedSizeBytes, item)`:

| Evidence (in order) | Condition | Answer |
|---|---|---|
| ETag | both sides have a non-blank ETag | equal → `UNCHANGED`, different → `CHANGED` (decides alone) |
| cTag | no ETag pair, both sides have a non-blank cTag | equal → `UNCHANGED`, different → `CHANGED` |
| Last-modified | no tag pair, both times known | different → `CHANGED`; equal → then size decides *change* only |
| Size | as above, or as the only pair | **different** → `CHANGED`; equal → no conclusion |
| — | nothing comparable | `UNKNOWN` |

Notes that matter:
* An ETag is **never** compared with a cTag (Phase 3 merged them; that would report a change on every probe
  of a cTag-only file). The test `anETagIsNeverComparedWithACTag` pins it.
* Equal sizes are **not** evidence of sameness, so a size-only pair answers `UNKNOWN`, not `UNCHANGED`.
* `UNKNOWN` is a distinct outcome in the UI: "Could not tell whether the OneDrive copy changed. The saved
  copy is unchanged." — it never counts as up to date, and it never triggers a download.

Failure outcomes are kept distinct end to end: `Missing` (probe found no such driveItem), `Failed(Offline)`,
`Failed(AuthRequired/AuthExpired)`, `Failed(Throttled(retryAfterSeconds))`, `Failed(Timeout)`,
`Failed(Unstable)`, `Failed(NotFound)`. Each has its own sentence from `RemoteFailure.message()`, and every
one of them still reloads the local copy, so Rescan keeps doing its local job while the remote side fails.


### 22.4 The replacement, and what is guaranteed at each step

`OneDriveUpdateSession.apply(...)` downloads through `SafeWorkbookDownload` (validated `*.part`), then asks
`WorkbookLibrary.replaceFrom(...)` to install it. The library's order is deliberate:

1. Copy the new bytes to `<file>.replacing` and hash them **first** — a full disk, a read error or a file
   that is not a ZIP leaves the user's copy untouched.
2. If the hash equals the saved one, only the remote metadata moves (`ReplaceResult.SameContent`); there is
   nothing to copy and the cache key must not change.
3. Copy the current file to `<file>.previous` — the bytes needed to undo steps 4–5 exactly.
4. Swap with one `ATOMIC_MOVE` inside the library directory (`REPLACE_EXISTING` fallback only if the
   platform refuses an atomic move). The entry's file reference never points at a partial file.
5. One `writeAll(...)` records the new `sha256`, size and remote version (`etag`, `ctag`, times, `syncedAt`,
   `checkedAt`) **and** clears the parse counts that described the old bytes. If it fails, the backup is
   moved back, so the index and the file cannot disagree.
6. The backup and the `.part` are deleted.

The entry keeps its id, display name, file name, import time, pin and recency: to the user it is the same
workbook, now at a new version. The new `sha256` is handed back to the ViewModel, which re-stages the
workbook and calls `comments.open(file, newSha, …)` — a new cache key, not a re-parse under the old one.

**Failure matrix** (each row is asserted in `OneDriveUpdateSessionTest` and/or
`WorkbookLibraryReplaceTest`):

| Situation | Old bytes | Library metadata | `.part` | Result |
|---|---|---|---|---|
| download failed / threw / `ENOSPC` | intact | unchanged | deleted | `Failed(...)` |
| cancelled | intact | unchanged | deleted | `Cancelled` |
| invalid workbook (HTML, not a ZIP) | intact | unchanged | deleted | `Failed(InvalidWorkbook)` |
| identical bytes returned | intact | version moved to the remote one | deleted | `SameContent` |
| install refused by the library | **restored byte for byte** | unchanged | deleted | `Rejected(message)` |
| index write fails after the swap | **restored byte for byte** | unchanged | deleted | `Rejected(index message)` |
| remote item gone | intact | unchanged (the check itself is not recorded) | none | `Missing` |
| user declines | intact | only `checkedAt` moves | none | — |

Nothing is ever deleted remotely, and nothing is deleted locally: a missing remote file leaves the saved
copy and its entry exactly where they were.

### 22.5 Cancellation and concurrency

* One field (`rescanJob`) and one counter (`rescanSeq`). `rescanOpenWorkbook` refuses to start while
  `remoteUpdate.canRescan` is false (a probe, a download, or an unanswered question) and while the job is
  active, so two checks cannot overlap.
* `cancelRemoteUpdate()` advances `rescanSeq` **before** cancelling, so even a result already on its way
  back is stale by the time it could commit; the coroutine additionally dies at its next suspension point
  (the download), which is before any install. A cancelled attempt therefore cannot replace anything.
* Every progress callback and every terminal branch compares `seq == rescanSeq` before touching `UiState`,
  so a superseded attempt cannot overwrite newer state.
* Cancellation is never reported as success: the message is "Update cancelled. The saved copy was not
  changed."
* Phase 4's import flow was left as it was — it already had this shape (cancel the job, clear the progress,
  delete the `.part`); the only shared-code change is that both flows now use one `SafeWorkbookDownload`.

### 22.9 Known limitations, deviations and deliberate omissions

1. **The ViewModel is not unit-tested.** The routing (LOCAL → `reload()`, ONEDRIVE → probe → question →
   install) is only verifiable by reading the code, because `MainViewModel` is an `AndroidViewModel` and this
   project has no Robolectric. Every piece it calls is tested; the wiring between them is not.
2. **The dialogs' layout is not tested** (no Compose UI-test dependency). Their state inputs are.
3. **No instrumented or manual run.** See §22.8. This is the honest state of a phase that cannot reach
   Microsoft's service from here.
4. **`cTag` is a new field inside schema 2, not a schema bump.** It is additive and optional: an older
   schema-2 index has no `ctag` key, parses to `null`, and the comparison then falls back to the ETag or the
   timestamp. Nothing is migrated, nothing is rewritten, and a schema-1 library still migrates exactly as
   before. The alternative — schema 3 — would have forced a migration for one optional string.
5. **A crash between the file swap and the index write can leave the file newer than the metadata.** The
   window is one atomic move plus one atomic write; the backup and the restore cover every *reported*
   failure, but a process kill in that window is not recoverable from the library alone. The state is
   self-healing: the next Rescan compares the stored (old) ETag with the remote (new) one, offers the update,
   downloads identical bytes and takes the `SameContent` path, which fixes the metadata without touching the
   file.
6. **A declined update is not remembered as "user does not want this".** Only `checkedAt` moves, so Rescan
   asks again next time. Remembering a refusal per version would need a new schema field and a new UX
   decision, and is Phase 6 territory at the earliest.
7. **`SameContent` does not re-open the workbook.** OneDrive's bytes matched ours, so only the metadata
   moved; the existing local parse is still correct and the screen is reloaded locally instead.
8. **The update download uses the Phase 3 `.part` file, not a second temporary file.** It is deleted on
   every path (asserted). Two updates cannot overlap, so one `.part` name is enough.
9. **Progress for a replacement with an unknown size is indeterminate**, exactly like the import flow: no
   percentage is invented.
10. **Nothing of Phase 6+ was started.** No offline/failure UX workstream, no Phase 7/8/9 work: no
    background sync, no auto-refresh on open, no upload or write-back, no remote deletion, no scheduling.
11. **No version bump, no changelog, no commit, no push, no tag** — as instructed. `.env`, its ignore rule

Two deliberate wording decisions, both documented in code:
* `Unstable` and `Timeout` read the **same** sentence in the rescan context. The brief groups them as "slow
  or unstable connection", and from the user's chair they are one event: OneDrive did not answer, so the copy
  on the device was shown instead.
* A download `Timeout` gets its own variant ("…while downloading <name>. Nothing was saved.") rather than the

### 23.4 Connectivity transitions, one flow at a time

| Flow | What protects it | What the user sees when the network goes |
|---|---|---|
| Opening *From OneDrive* | `openOneDriveBrowser` preflights; no account → no folder request | the offline sentence in the panel, no spinner, Retry available |
| Folder navigation / pagination | `OneDriveSession.list` preflights on every call; `loadOneDrivePage` settles in `finally` | the failure sentence replaces the list, `Retry` appears, the breadcrumb still works (Up stays usable) |
| File download (import) | `SafeWorkbookDownload` streams to `.part`, deletes it on every failure; `importOneDriveFile` settles in `finally` | "The connection was lost while downloading <name>…", progress bar gone, nothing saved, Retry available |
| Remote check (Rescan) | `check` preflights; `rescanOpenWorkbook` settles in `finally`; the local reload runs **after** the remote half | offline/slow sentence, workbook rescanned from the device copy, no spinner |
| Remote update download | `apply` preflights, streams, validates, then installs; `acceptRemoteUpdate` settles in `finally` | download-context sentence, old copy intact, `.part` deleted |
| Everything | one sequence number per flow; only the current operation may clear in-flight flags | no permanently stuck spinner, and a superseded result cannot overwrite newer state |

Concretely, the two rules added in this phase:

* `settleOneDrive(seq)` / `settleRescan(seq)` run in **every** `finally` and apply
  `OneDriveUi.settled()` / `RemoteUpdateUi.settled()`. `settled()` touches *only* the in-flight flags
  (`busy`, `loadingMore`, `signingIn`, `download`, `checking`) and leaves the panel, the account, the
  listing, the last error and the unanswered question alone.
* Closing the panel or cancelling a download advances the sequence **before** cancelling the job, so the
  cancelled coroutine cannot write anything afterwards. This closed the one latent stuck-state found in
  review: a cancelled check could previously have left `checking = true` on screen for ever.

### 23.5 Authentication recovery

* An `AuthRequired`/`AuthExpired` answer anywhere (browse, import, check, update) now also clears the
  panel's signed-in flag, so *From OneDrive* presents its **Sign in** button — the only place this build can
  sign in — instead of a Retry that could only fail again. The message already says "Sign in again to check
  for changes."
* The running operation still finishes: a failed check still reloads the local copy, and a failed update
  still leaves the previous version installed and usable.
* A **cancelled** sign-in produces no message and no state change beyond `signingIn = false`
  (`AuthState.failureOrNull()` returns `null` for `SignedOut`); only `Expired` maps to `AuthExpired`.
* Signing out clears `signedIn`, the account label, the listing and the last error — and touches **no**
  local file, no library entry and no cache.
* No token, id token, tenant id or MSAL exception message is stored in `UiState`, printed or shown; the auth
  failures travel as the app's own enum.

### 23.6 Local-file preservation

Nothing in this phase touches the replacement path, the metadata writers or the download validator, so
Phase 5's guarantees hold verbatim:

* a failed, cancelled or interrupted update leaves the previous bytes **and** the previous metadata;
* no failure advances `etag`/`ctag`/`syncedAt`;
* an unknown remote state is never recorded as a check that succeeded;
* `CHECKED_ONLY` (a declined update) still moves nothing but `checkedAt`.

The new tests re-prove the two halves that matter for *offline*: the remote half refuses before any request,
and the local half (open + parse, the same calls `WorkbookCommentsController.reload()` makes) succeeds with
the monitor reporting offline.

### 23.10 Known limitations and deviations

1. **The ViewModel still cannot be unit-tested** (AndroidViewModel, no Robolectric). The message *selection*
   and the *reset* rules are pure and tested; the code that calls them is reviewed, not executed by a test.
2. **No Retry button in the rescan flow.** The affordance there is the Rescan button itself (and, for a
   failed update, tapping Rescan again), which is why the sentences say what state the workbook is in rather
   than offering a second control. The *import* panel does have a Retry, now gated by `isRetryable()`.
3. **An expired sign-in during Rescan does not open the sign-in panel automatically.** It reports the agreed
   sentence, marks the account as signed out, and the user opens *From OneDrive* to sign in. Popping a modal
   out of a Rescan tap would be a bigger UX decision than this phase was asked to make.
4. **`Unstable` and `Timeout` share one sentence in the rescan context.** Deliberate (see §23.3): the brief
   groups them, and from the user's side they are the same event. They stay distinct in the taxonomy and in
   the import/download context.
5. **A cancelled sign-in writes nothing.** That is the requirement, but it also means the panel cannot say
   "sign-in cancelled" — the button simply remains.
6. **`NotConfigured` (no `.env`) still has a message but no dedicated UX.** It can only appear in a build
   made without Azure configuration, which is not a user-actionable state on a device.
7. **Retry-After is respected in the wording, not enforced as a timer.** The app does not disable Retry for
   the requested number of seconds; it tells the user how long OneDrive asked for. Adding a countdown would
   be new UI, not error handling.
8. **Connectivity loss is detected per operation, not pushed.** There is no listener that cancels an
   in-flight transfer the moment the network drops; the transfer fails at its own socket timeout (20 s read)
   and that is reported as `Unstable`/`Timeout`. The result is predictable and bounded, but not instant.
9. **Nothing of Phase 7+ was started**, and no behaviour outside failure handling was changed: no new screen,
   no new dialog, no new dependency, no change to import/update semantics, no change to replacement or
   metadata rules.
10. **No version bump, no changelog, no commit, no push, no tag** — as instructed. `.env`, `.env.example`,

### 24.10 Crash consistency and recovery — the investigation

**Method, and its limit:** no process was killed. Each test reconstructs the exact on-disk state a kill would
leave at a named point in `WorkbookLibrary.replaceFrom`, then asserts what the next run does. That proves the
*recovery logic*; it does not prove that Android would have persisted those bytes (no `fsync` is issued at
any point — see finding E).

The pipeline, and what survives a kill at each step (`WorkbookLibraryCrashRecoveryTest`, 11 tests):

| # | Interruption point | On-disk state afterwards | Next run | Verdict |
|---|---|---|---|---|
| 1 | before anything is written | entry + file untouched | normal | **safe**, auto-tested |
| 2 | while a `.part` exists | `<itemId>.part` beside the library | the library ignores it; `bytes()` does not count it; the next `replaceFrom` is unaffected; the next download of that item deletes it first | **safe but never swept** (finding D), auto-tested |
| 3 | after the old copy was duplicated to `.previous`, before the swap | target = old, `.previous` = old, `.replacing` = new | target was never removed, so the workbook opens normally; the next `replaceFrom` deletes both leftovers and completes | **safe**, auto-tested |
| 4 | **after the swap, before the index write** (the state Phase 5 flagged) | target = **new bytes**, index = **old sha/size/etag** | the workbook opens (bytes are present); the metadata is stale; the next `replaceFrom` re-hashes, installs and rewrites the index, and the entry becomes consistent again | **recovers, with a caveat** (finding A), auto-tested |
| 5 | after the index write, before cleanup | index and target both new, `.previous` = old | a fresh `WorkbookLibrary` reads a consistent entry whose sha matches the bytes on disk; the leftover is invisible to `list()`/`bytes()` and is removed by the next replacement | **safe**, auto-tested |
| 6 | index **missing** | workbook file intact, no entry | `list()` is empty; the bytes are **not** deleted; the orphan cannot be re-imported (finding B) | **data preserved, entry lost**, auto-tested |
| 6b | index **malformed** | file quarantined as `library.json.bad`, library empty | same as 6; the original index content is preserved in `.bad` | **data preserved**, auto-tested |
| 7 | index points at a **missing file** | entry listed, no bytes | `fileOf(...).isFile == false`, which is what `useSavedWorkbook` reports; re-importing the same file answers `AlreadySaved` and still does not restore it (finding C); a *different* workbook imports normally | **broken entry, no data loss**, auto-tested |
| 8 | `.previous` is the **only** copy (target gone) | index → file X, X absent, X.previous present | before this phase the leftovers were deleted first — destroying the last copy on a failed rollback. **Fixed**: a lone backup is moved back into place and then treated as the current file | **fixed + regression-tested** |

**Findings, with the smallest safe correction for each:**

* **A — stale metadata after a kill between swap and index write (LIMITATION, self-healing).** The file is
  the new version while the index still describes the old one. The workbook still opens, but it is parsed and
  cached under the **old** SHA-256 until something rewrites the entry; the next `replaceFrom` (a Rescan +
  "Update") heals it, and the test proves the healed entry matches the bytes. *Smallest correction, not
  applied:* before opening a saved workbook, compare `entry.sizeBytes` with `library.fileOf(entry).length()`
  and re-hash when they differ (O(1) check in the common case). Deliberately **not** done here — it adds hashing
  to the open path, which is exactly the kind of change a verification phase must not slip in.
* **B — an orphaned file cannot be re-imported (LIMITATION).** With the index lost, the file is stranded:
  `import` finds `<id>.<ext>` on disk and rejects the identical file with "A workbook with this identity
  already exists." Data is preserved but unreachable. *Smallest correction, not applied:* in `import`, when
  `target.exists()` **and no entry claims that id**, adopt the file (it is the content whose hash named it)
  instead of rejecting.
* **C — a listed entry whose file is missing cannot be repaired by re-importing (LIMITATION).** The sha
  matches the broken entry, so `import` answers `AlreadySaved` and copies nothing. *Smallest correction, not
  applied:* when the sha matches an entry whose file is absent, re-install the bytes for that entry.
* **D — nothing sweeps `.part` / `.previous` / `.replacing` at startup (LIMITATION).** They are invisible to
  the library and harmless, but they consume storage until the next download/replacement of the same item.
  *Smallest correction:* a one-line sweep in the ViewModel's OneDrive initialiser. Not applied (it would be a
  new startup behaviour, i.e. a change of behaviour, not verification).
* **E — no `fsync` anywhere (LIMITATION, platform-level).** Neither the file swap nor the index write forces
  the bytes to stable storage, so the *ordering* this design relies on is only guaranteed by the filesystem's
  own journaling. On modern Android (`ext4`/`f2fs`) a rename is ordered after the data it publishes, but that
  is a platform assumption, not something this code enforces. Recorded rather than changed.

**Was a production change justified?** One: the lone-backup guard (row 8). It removes the only way this code
could *delete* the user's last copy, it is two lines, it cannot affect a normal replacement (the target does
exist in that case), and it is covered by a regression test that fails without it. Everything else in this
area is documented rather than "fixed", per the brief.
