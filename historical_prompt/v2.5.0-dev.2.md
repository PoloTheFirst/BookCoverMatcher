# 1. Mission

Implement the next development iteration of BookCoverMatcher's online discovery and collection-matching functionality.

The architecture must combine four approaches:

- **Approach A — Provider-based search:** multiple independent search providers, dedicated adapters, capability-aware query routing, normalized results and browser handoff.
- **Approach B — Image-first discovery:** start from a scanned or supplied cover image, extract available metadata, perform reverse-image discovery, search relevant providers, compare candidate covers locally with OpenCLIP, and present evidence for user confirmation.
- **Approach C — Collection-centric discovery:** connect online candidates to local catalogue and wishlist records while keeping ownership, catalogue presence and wanted status independent.
- **Approach D — Browser-assisted fallback:** when automated access is restricted, unavailable or unsuitable, let the user complete discovery through a browser and submit listing information for local matching.

Approaches A, B and C form the primary architecture. Approach D is the fallback and must integrate with the same candidate and matching pipeline.

## 1.1 Primary reverse-image providers

This release must integrate two reverse-image discovery services:

1. **SauceNAO — first priority.**
2. **IQDB — second priority.**

Both services are part of the intended reverse-image discovery workflow.

SauceNAO must be attempted first. IQDB must also be supported and must not be omitted merely because it is slower.

The implementation must account for IQDB's potentially longer processing time, provider-specific access restrictions and rate limits.

Do not treat a slow response as an immediate empty result.

Do not claim that either provider successfully searched unless a genuine provider response was received and parsed.

## 1.2 Preserve the existing application

This is an incremental implementation, not a rewrite.

Preserve:

- Native Android application architecture.
- Kotlin and Jetpack Compose.
- CameraX workflows.
- Existing OCR functionality.
- Existing ONNX Runtime and OpenCLIP embedding pipeline.
- Existing workbook `.xlsx` parsing, including embedded images.
- Existing catalogue and wishlist persistence.
- Existing DLsite functionality.
- Offline-first workflows.
- Existing profile isolation.

Do not replace working systems without a demonstrated technical reason.

# 4. Fixed product and architecture decisions

## 4.1 Doujin-first identity

Doujin discovery is the primary use case.

DLsite remains the anchor source for doujin identification.

A reliable doujin identity should consider:

1. Circle name (`サークル`).
2. Product title.
3. RJ product identifier, where available.

A title-only match is insufficient to establish exact identity.

Open Library and Google Books are secondary sources. They may supplement general-book discovery and metadata, but must never independently establish a doujin match.

## 4.2 Distinguish the three image capabilities

The implementation must distinguish:

**A. OCR metadata extraction**

Extract visible text from an image to assist search queries.

OCR is not visual product recognition.

**B. External reverse-image discovery**

Submit an image to an external visual-search provider and receive genuine similar-image or source results.

This release uses:

- SauceNAO.
- IQDB.

**C. Local OpenCLIP comparison**

Compare a source cover with candidate covers obtained through provider results or user-supplied material using the existing local embedding pipeline.

These are separate operations and must have separate result provenance.

Never label OCR or local OpenCLIP comparison as external reverse-image search.

## 4.3 Provider priority

Use this provider priority:

| Priority | Provider | Purpose |
|---|---|---|
| 1 | SauceNAO | Primary external reverse-image discovery |
| 2 | IQDB | Secondary external reverse-image discovery |
| 3 | DLsite and other suitable providers | Metadata and product discovery |
| 4 | Open Library / Google Books | Optional secondary general-book metadata |
| 5 | Browser-assisted manual discovery | Fallback for restricted or unsupported sources |
| Local | OpenCLIP | Candidate-cover comparison |

The reverse-image workflow must attempt SauceNAO first and IQDB second.

Both are intended providers. Do not silently skip IQDB because SauceNAO returned results.

The implementation may use sequential execution to respect provider priority and request restrictions. If controlled parallelism is later justified, SauceNAO must still be presented and treated as the primary provider, and concurrency must respect each provider's rate limits.

## 4.4 Secondary-source toggle

Keep Open Library and Google Books behind a user-controllable secondary-sources toggle.

Requirements:

- Do not let secondary sources dominate doujin discovery.
- Clearly distinguish their results from primary doujin sources.
- Do not use them as sole evidence for doujin identity.
- When disabled, do not issue their requests or include their results in the active search.
- Preserve existing functionality when enabled.

## 4.5 Browser-only providers

Keep the existing browser-only providers as manual handoff sources.

When automated access is restricted or unavailable:

- Open the legitimate provider search page or listing URL.
- Let the user perform the search.
- Accept pasted listing URLs and manually supplied metadata.
- Accept an optional cover image.
- Pass the submitted information through the same local candidate-matching pipeline.

Do not scrape restricted pages, spoof browsers, bypass CAPTCHA, circumvent authentication or defeat access controls.

4. Parse the provider's returned result metadata.

7. Handle empty results.
8. Handle malformed responses.
9. Handle network errors and timeouts.
10. Handle invalid API keys.
11. Handle rate limits and daily quota exhaustion.
12. Avoid retry loops that can worsen quota exhaustion.

## 5.3 IQDB — secondary provider

Implement IQDB as the second reverse-image provider.

**Important: verify the actual permitted access method before implementation.**

Inspect:

- IQDB's official public search page.
- Any documented public API or integration interface.
- Its current access restrictions.
- Request formats and image-upload limits.
- Whether local image uploads or image URLs are supported.
- Whether the response is synchronous or involves a separate waiting process.
- Applicable request-spacing and usage restrictions.

Do not assume that a self-hosted IQDB API or an unofficial wrapper describes the public hosted service's API contract.

Do not invent endpoints, parameters, response fields or asynchronous job protocols.

Use a permitted integration method supported by actual evidence.

If the hosted service has no documented public API, determine whether its public image-search interface can be integrated safely and reliably without bypassing access controls or violating its restrictions.

If safe automated integration cannot be established:

- Keep the `IqdbReverseImageSource` abstraction.
- Provide a browser-assisted IQDB search action.
- Allow the user to submit or inspect the IQDB result manually.
- Clearly label IQDB automated search as unavailable or manual-only.
- Do not falsely report successful automated IQDB results.

**Slow response handling**

IQDB may take noticeably longer than SauceNAO.

The implementation must:

1. Support a configurable, provider-specific timeout that is longer than the normal fast-search timeout.
2. Await the actual request completion instead of prematurely treating a slow response as no results.
3. Show an explicit `Searching IQDB...` or equivalent state.
4. Keep the UI responsive.
5. Run network work off the main thread.
6. Support cancellation.
7. Prevent an old IQDB response from overwriting a newer query.
8. Apply respectful request spacing and cooldown behavior.
9. Avoid aggressive retries.
10. Preserve already received SauceNAO results while IQDB is still processing.

Do not implement busy polling.

Only implement polling if the actual documented IQDB protocol returns a job identifier or equivalent asynchronous state that requires it.

If such a protocol exists, follow its documented polling interval, termination conditions and retry behavior.

Do not use an arbitrary short timeout that makes IQDB unusable.

If IQDB exceeds its configured timeout, report a timeout state, not an empty-result state.

## 5.4 Combined reverse-image results

Both providers must return normalized results to a shared aggregation layer.

Preserve:

- Provider identifier.
- Provider result ID, if available.
- Original source URL.
- Original image URL, if available.
- Title.
- Circle or author.
- Product identifier, if available.
- Provider-specific similarity value.
- Provider-specific metadata.
- Search timestamp.
- Result provenance.

Deduplicate only when there is sufficient evidence that two results refer to the same underlying item.

Do not merge distinct editions, different products or separate uploads merely because their titles look similar.

When the same candidate appears in both services:

- Preserve both provider references.
- Preserve both original similarity values.
- Show that the candidate was found by multiple sources.
- Do not invent a combined probability.
- Do not replace one provider's similarity with another provider's score.

A candidate found by both providers may receive stronger evidence provenance, but this must not automatically establish a confirmed product identity.

## 5.5 Reverse-image provider states

Represent at least:

- `NOT_CONFIGURED`
- `READY`
- `SEARCHING`
- `SUCCESS`
- `NO_RESULTS`
- `TIMEOUT`
- `RATE_LIMITED`
- `QUOTA_EXCEEDED`
- `UNAVAILABLE`
- `BLOCKED`
- `CANCELLED`
- `ERROR`
- `MANUAL_ONLY`

Adapt existing enums where appropriate.

A blocked, timed-out, unconfigured or manual-only provider must never be reported as having returned no results.

## 5.6 Reverse-image user experience

The UI should communicate the provider sequence clearly:

1. SauceNAO starts first.
2. SauceNAO results become available as soon as received.
3. IQDB starts afterward or according to a safe controlled schedule.
4. IQDB may take longer.
5. Results from both providers are merged without losing source attribution.
6. The user can cancel the outstanding operation.
7. A failure in one provider does not erase successful results from the other.

Do not make the user wait for IQDB before showing already available SauceNAO results.

Provide clear configuration and error messages without exposing API keys.

### Evidence dimensions

- Product identifier.
- Title.
- Circle.
- Author.
- SauceNAO result evidence.
- IQDB result evidence.
- Local cover-image similarity.
- Provider agreement and source provenance.

### Confirmation

- Allow explicit rejection.
- Persist the user's decision.
- Do not automatically overwrite catalogue records.
- Preserve the distinction between a machine-generated suggestion and user-confirmed identity.

### Keep these facts independent

- Owned: whether the user declares that they own the item.
- Catalogued: whether a corresponding record exists in the local workbook/catalogue.
- Wanted: whether the user wants the item.

Do not infer ownership from catalogue presence.

Do not infer catalogue presence from ownership.

A wanted item may already be catalogued.

Represent catalogue matching independently:

- Matched.
- Ambiguous.
- No match.

Missing information must remain unknown rather than being converted into a negative claim.

### Wishlist integration

- Reuse existing wishlist models and persistence.

- Preserve existing wishlist records.
- Preserve profile isolation.
