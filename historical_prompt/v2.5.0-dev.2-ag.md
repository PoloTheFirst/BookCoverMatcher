## 1. Implementation summary

v2.5.0-dev.2 adds **reverse-image discovery** and the manual collection pipeline that goes with it, and wires the
v2.5.0-dev.1 core into the screen for the first time.

| Area | What actually works in this build |
|---|---|
| SauceNAO | automated search: documented multipart POST, JSON response parsing, quota reporting, per-state error mapping, no retries |
| SauceNAO key | stored AES-256-GCM under an `AndroidKeyStore` key; masked display; remove/clear; never logged or placed in a URL |
| IQDB | **manual only**: no API exists and `robots.txt` disallows its search routes; the app opens IQDB's page and parses what the user pastes back |
| Pipeline | SauceNAO first, IQDB second (even if SauceNAO answered); per-provider timeout; cancellation; stale-response guard; failure isolation |
| Candidates | cross-provider merge on proof of identity, both providers' references and similarity values preserved, no combined score |
| Decisions | suggestion → confirm/reject, persisted per wishlist profile; never edits the workbook or the wishlist |
| Collection facts | owned / catalogued / wanted independent; `LocalProducts.of(CatalogEntry)`; ambiguity preserved |
| Secondary sources | general-book switch that removes providers from the query set (not just the display) |
| Cache | byte-budgeted LRU cover cache, plain Kotlin, unit-tested |
| UI | `Online search → C · Reverse-image discovery`: provider rows, key config, search, candidates, confirm/reject, manual form, IQDB paste, general-book switch |

## 4. Approach A — provider-based search (routing, capabilities, aggregation)

* The dev.1 structured query (`OnlineQuery`) and capability table are now **used**: `ProviderCapabilities.eligible`
  / `skipped` gained an `includeSecondary` flag, and the controller filters the selected providers through it
  before issuing any request.
* DLsite keeps its measured `+` encoding (`QueryForm.PLUS`) and its RJ keyword behaviour — untouched.
* Provider tiering: `dl` = `PRIMARY_DOUJIN`, `ol`/`gb` = `SECONDARY_BOOK`. Switching the secondary sources off
  produces `CatalogueUi.SwitchedOff` (nothing queried) instead of an empty result, and their rows read "switched
  off".
* Aggregation still uses `OnlineAggregator.itemKey`/`ItemIdentity`, so no two providers collapse into one card by
  title.

**Not changed:** which providers are automated. Eight providers remain browser-only for their
previously measured reasons; no provider was newly enabled.

## 5. Approach B — image-first and reverse-image discovery

Sequence implemented (and enforced by `ReverseImageSearchRunner`):

1. the captured cover (existing CameraX / Auto Scan / picker path) is the image;
2. existing OCR (`chrome-lens-py`) still produces the text query — unchanged and still the only OCR;
3. **SauceNAO first** (documented API, key in the body), state published as it runs;
4. **IQDB second** — reported `MANUAL_ONLY`, with the verified reason and its own page;
5. results merged by identity with both providers' references preserved;
6. candidates shown with attributed evidence and explicit Confirm/Reject.

**Evidence dimensions kept separate:** provider similarity (per provider), source URL, product code, title,
circle, author, provider agreement. Missing evidence stays unknown; no score is averaged across providers.

**Local OpenCLIP comparison:** the existing pipeline is untouched and its output is still accepted by
`CandidateMatcher`/`CollectionStatusOf` as an optional input; the reverse-image *card* does not display it yet
(recorded as a limitation, §12).


## 6. Approach C — collection and wishlist integration

* **Ownership ≠ catalogued ≠ wanted.** `CollectionStatus(owned, catalogued, wanted)` treats `null` as "not
  stated"; `CollectionStatusOf.of(...)` derives **only** `catalogued` from the matcher, and an empty workbook
  yields `UNKNOWN`, never `ABSENT`. Ambiguity is preserved (two plausible records → `AMBIGUOUS`).
* **Local records.** `LocalProducts.of(CatalogEntry)` maps `TITLE`, `CIRCLE`, `ARTIST`, `IDENTIFIER` from
  `entry.text(...)`, which is populated only for mapped, present cells — so an unmapped circle becomes *unknown*
  in the comparison rather than a contradicting value.
* **Wishlist.** No schema change was made. Confirming a candidate writes only a decision record; adding to a
  wishlist remains the existing explicit action, whose duplicate prevention is the store's own identity rule
  (`ItemIdentity`), re-asserted in a test (`CandidateReviewTest.the same candidate added twice is one wishlist
  identity`). Profile isolation is preserved: decisions are one file **per profile**, and no existing record is
  touched.
* **Visible relationship:** the candidate card shows the decision state; the existing result cards keep showing
  bookmark/wishlist state, so "found online", "confirmed by me" and "in my wishlist" cannot be confused.

## 7. Approach D — browser-assisted fallback

* **Manual listing form** (`Add listing`): listing URL, title, circle, author, product ID, site label and note.
  `ManualCandidates.validate` requires a title or a product code, refuses a non-`http(s)` URL, collapses
  whitespace, caps lengths, canonicalises an `RJ…` code and never invents a URL. The result is the **same**
  `ProductSearchResult` model, stamped `providerId = "manual"` and `source = <site> | "Manual listing"`, so it
  enters the same candidate list and can be confirmed/rejected.
* **IQDB handoff:** the IQDB row opens `https://iqdb.org/`; `Paste an IQDB result` accepts result lines or a saved
  page and normalises them (`IqdbResultParser`). Nothing is fetched from a pasted URL, and every such candidate is
  flagged "You supplied this candidate".
* **Existing browser-only shortcuts** (Melonbooks, Suruga-ya, Doujin no Mori, E-Hentai, Doujinshi.info,
  MyAnimeList, nhentai, Toranoana) are unchanged and still never counted as searched.

### Final statement

* **SauceNAO automated integration: implemented** per the documented API, **not live-verified**.
* **SauceNAO API-key secure storage: implemented** (Keystore AES-256-GCM; crypto unit-tested).
* **IQDB automated integration: not implemented, blocked by the provider's own published policy.**
* **Exact IQDB access method used: none.** The app opens IQDB's public search page and parses only material the
  user supplies.
* **IQDB documented and permitted?** Documented in `ONLINE_SEARCH.md` §10.4 and `IqdbProtocol`; the automated
  route is *not* permitted by the site's `robots.txt`, which is why it is not used.
* **IQDB slow-response handling tested?** Not live (nothing is submitted); the pipeline's timeout behaviour is
  covered by a fake slow provider.
* **IQDB is manual-only**, not partially implemented.
* **Both providers' results merge correctly** and keep their own similarity values and provenance.
* **SauceNAO priority is respected**, and **one provider's failure leaves the other functional**.
