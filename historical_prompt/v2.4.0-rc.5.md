## 3. Bug A — Incorrect Detected Status after applying an unchanged mapping

### 3.1 Reproduction scenario

In Insights → Fields:

1. Open a workbook and inspect a worksheet.
2. Allow automatic header detection to populate the detected column mappings.
3. Do not change any header-to-column assignments.
4. Confirm that the current mapping is identical to the automatically detected mapping.
5. Click **Apply mapping**.
6. Observe the Detected Status indicator.

**Actual behavior:** The Detected Status changes from blue to grey even though no mapping assignment was changed and the applied mapping is identical to the detected mapping.

**Expected behavior:** The Detected Status must remain blue when the effective applied mapping is equivalent to the automatically detected mapping.

The indicator must not imply that automatic detection has become invalid merely because the user explicitly applied the same result.

### 3.2 Required investigation

Trace the full state lifecycle for detected and applied mappings:

- Automatically detected mapping.
- Current editable mapping.
- Applied mapping.
- Mapping validation state.
- Detected Status state.
- Apply mapping event.
- Mapping persistence and restoration, where relevant.

Identify whether the defect is caused by:

- Comparing object references instead of mapping contents.
- Different internal representations of equivalent mappings.
- Empty or unassigned values being handled inconsistently.
- An Apply mapping event unconditionally changing the detection state.
- A state reset or recomposition issue.
- A stale or incorrectly scoped state holder.
- Incorrect comparison of column identifiers, header names, worksheet identity, or mapping metadata.

Do not simply force the indicator to blue after every Apply mapping operation. The indicator must reflect the actual relationship between the detected mapping and the effective mapping.

### 3.3 Required behavior

Implement a reliable semantic comparison between the detected mapping and the effective applied mapping.

The comparison must:

1. Compare actual mapping meaning rather than object identity.
2. Treat equivalent mappings as equal even if represented by different object instances.
3. Handle empty and unassigned fields consistently.
4. Distinguish genuinely different column assignments.
5. Avoid treating unrelated metadata or transient UI state as a mapping change.
6. Respect worksheet identity and the correct detection result for the worksheet being inspected.
7. Remain correct after recomposition, navigation, reopening the Fields screen, and restoring persisted state.

Expected status behavior:

| Mapping relationship | Expected Detected Status |
|---|---|
| No manual changes; applied mapping equals detected mapping | Blue |
| User manually selects the same detected assignments and applies them | Blue |
| User changes one or more assignments and applies the changed mapping | Grey |
| User changes a mapping and then restores all assignments to the detected mapping | Blue |
| User clears a field that was populated by detection | Grey, if the effective mapping now differs |
| User applies an equivalent mapping represented by a different object instance | Blue |
| A different worksheet has a different detected mapping | Evaluate independently for that worksheet |

Use the existing UI color tokens and status semantics. Do not introduce a new color system or unrelated visual redesign.

### 3.4 Important distinction

The Detected Status is a statement about whether the effective mapping still corresponds to the automatic detection result.

It is not a statement about whether the user has clicked Apply mapping.

Therefore:

- Applying an unchanged mapping must not turn the status grey.
- Applying a changed mapping should turn it grey when the effective mapping differs.
- Restoring the original detected assignments should restore the blue status.

## 4. Bug B — Saving a profile leaks one worksheet's mapping into other worksheets

### 4.1 Reproduction scenario

In Insights → Fields:

1. Open a workbook containing multiple worksheets.
2. Navigate to a worksheet in Fields.
3. Inspect its detected and editable mappings.
4. Change one, several, or none of its header-to-column assignments.
5. Click **Save profile** and save a new Column Mapping Profile.
6. Inspect the mappings belonging to other worksheets.

**Actual behavior:** The values from the currently inspected worksheet are copied or duplicated into other worksheets after saving a new profile. This includes empty or unassigned values.

The affected values depend on which worksheet was being inspected when the new profile was saved. The issue can occur whether the inspected worksheet has had zero, one, or multiple mapping changes.

**Expected behavior:** Saving a new profile must not modify, replace, clear, duplicate, or otherwise contaminate mappings belonging to other worksheets.

Each worksheet's mapping must remain isolated.

### 4.2 Severity and scope

Treat this as a data-isolation and persistence correctness bug.

The defect is not limited to manually modified mappings. The fact that it can happen even when no mapping has been changed suggests that the profile-saving operation may be using the current worksheet's mapping state as a global mapping template, or may be serializing worksheet data under an incorrect identity or scope.

Investigate the complete flow rather than patching only the visible UI.

### 4.3 Mandatory root-cause investigation

Trace the data flow from the Fields screen to the profile-saving implementation and back.

Inspect:

- The current worksheet identifier.
- The workbook identifier.
- Worksheet-specific mapping state.
- Automatic detection results.
- Editable mapping state.
- Applied mapping state.
- Default or empty mapping values.
- Profile creation and serialization.
- Profile storage model.
- Profile-to-worksheet association.
- Profile application and restoration.
- Repository and persistence layers.
- Shared mutable objects and collection references.
- StateFlow, LiveData, Compose state, ViewModel state, or equivalent state holders.
- Map/list construction and copying.
- Keys used to associate mappings with worksheets.
- Any fallback logic that substitutes the currently inspected worksheet's mapping when a worksheet-specific value is missing.

Pay particular attention to these potential failure modes:

1. A single mutable mapping object is reused across multiple worksheets.
2. A worksheet-specific map is accidentally replaced by a global map.
3. A profile stores only the currently inspected worksheet's values but later interprets them as workbook-wide values.
4. Empty values are treated as valid global assignments and overwrite other worksheet mappings.
5. Worksheet names or identifiers are missing, normalized incorrectly, or omitted during serialization.
6. Profile-saving code captures a stale or incorrectly scoped current worksheet state.
7. Shallow copies allow nested mutable mapping objects to be shared.
8. A default profile or fallback mapping is applied to every worksheet.
9. A profile creation event unintentionally invokes mapping application or persistence for unrelated worksheets.
10. A mapping update is keyed by a non-unique value, causing multiple worksheets to share the same entry.

These are investigation targets, not assumptions. Confirm the actual cause before implementing the correction.

### 4.4 Required data-isolation rules

The implementation must enforce the following invariants:

**A. Worksheet identity**

Every worksheet-specific mapping must be associated with the correct workbook and worksheet identity.

Do not rely solely on a display label if the application already has a stable worksheet identifier. If names are used as identifiers, account for the repository's existing handling of duplicate names, renames, and workbook identity.

**B. Independent mapping state**

Each worksheet must own an independent mapping state.

Changing or saving a mapping for worksheet A must not mutate worksheet B's detected, editable, applied, or persisted mapping.

**C. Profile creation is not global mapping application**

Saving a new profile must create a reusable profile definition. It must not silently apply the currently inspected worksheet's mapping to every worksheet.

The current worksheet's mapping may be used as the source for the new profile only if that matches the existing product design. Regardless, creating the profile must not mutate mappings belonging to other worksheets.

**D. Empty values**

Empty or unassigned values must remain scoped to the worksheet and profile entry to which they belong.

An empty value from worksheet A must never clear or replace a populated mapping belonging to worksheet B merely because a new profile was saved while worksheet A was open.

**E. Safe copying**

Where mapping structures are mutable, use independent copies or immutable data structures as appropriate.

Do not retain shared mutable nested objects between worksheet mapping states or profile entries when independent state is required.

**F. Persistence round-trip**

Saving and reloading a profile must preserve its intended contents and scope.

Opening a different worksheet must retrieve that worksheet's own mapping rather than the last worksheet inspected.

**G. No implicit cross-worksheet side effects**

The following actions must not mutate unrelated worksheet mappings:

- Opening a worksheet.
- Inspecting detected mappings.
- Editing one worksheet's mapping.
- Applying one worksheet's mapping.
- Saving a new profile.
- Renaming or selecting a profile.
- Navigating between worksheets.
- Leaving and reopening Insights → Fields.
- Restarting the application and restoring persisted state.

Only an explicit, existing product operation that is intentionally designed to apply mappings across multiple worksheets may do so. Do not add such behavior as part of this task.

### 4.5 Profile behavior to preserve

Do not solve the defect by removing useful profile functionality.

Preserve the existing intended behavior for:

- Creating a new profile.
- Naming and saving a profile.
- Listing and selecting profiles.
- Reusing a saved profile.
- Applying a profile through the existing explicit workflow.
- Worksheet-specific mapping.
- Automatic header detection.
- Manual column selection and override.
- Clearing or unsetting a mapping.
- Preview and validation.
- Persisting mappings and restoring them after navigation or application restart.

A saved profile must not unexpectedly become a global replacement for every worksheet's independent mapping.

If the existing product design intentionally supports reusable profiles across worksheets, preserve that capability while keeping each worksheet's application of the profile explicit and correctly scoped.
