## 4. Root cause of the missing icons

The icon is present in every one of these documents, and it is present in a form **`AndroidSVG 1.4` cannot resolve**,
for two independent reasons:

```xml
<image x="5" y="3" width="14" height="14"
       href="data:image/svg+xml;base64,PHN2ZyBmaWxsPSJ3aGl0ZSIgcm9sZT0iaW1nIiB2aWV3Qm94PSIwIDAgMjQgMjQi…
```

1. **The attribute is SVG 2's `href`.** Shields.io emits the bare attribute, and there is no `xlink:href` anywhere in
   the document. `AndroidSVG 1.4` reads the SVG 1.1 name, so the reference is not even looked at.
2. **The payload is an SVG, and the `<image>` handler is a raster handler.** Even with the attribute found, that
   handler decodes with `BitmapFactory`; an `image/svg+xml` payload produces no bitmap, so the element contributes
   the 14×14 box and nothing inside it.

The badge's `<rect>` background, its gradient wash, its `<clipPath>` and its `<text>` use ordinary geometry and render
normally — which is exactly the reported symptom: correct background and text, empty reserved space where the icon
should be.

## 5. Source evidence that the icons exist

`badge-java.svg` (3 436 bytes) contains the reference quoted above. Base64-decoding its payload yields:

```xml
<svg fill="white" role="img" viewBox="0 0 24 24" xmlns="http://www.w3.org/2000/svg">
  <title>OpenJDK</title>
  <path d="M11.915 0 11.7.215C9.515 2.4 7.47 6.39 6.046 10.483…"/>
</svg>
```

So the icon is an `OpenJDK` glyph of 24×24 units, drawn in white, to be placed in a 14×14 box at (5,3) — the
geometry the renderer was dropping. Kotlin's differs only in colour (`fill="#7F52FF"`), and Bash's is a 24×24 PNG.

## 6. Where in the pipeline the icons were lost

Traced from end to end: `README Markdown → AuthorUrls.resolve → HttpAuthorRemote (bytes) → AuthorFileCache →
AuthorImageDecoder.decode → AndroidSVG parse → render → Compose badge row`.

* **Not the README, the URL resolution, the fetch, the cache or the layout**: the bytes arrive intact (the fixtures are
  the exact documents the app cached), `AuthorImageDecoder` picks `delegateSvg` correctly, and the badge is laid out
  at the right size and position.
* **Lost inside `AndroidSVG`**: the `<image>` element's reference is never resolved (attribute name) and, even if it
  were, the payload type is unsupported (raster-only handler). The renderer therefore draws background and text and
  skips the icon.

This was confirmed empirically in the instrumented test *before* the fix: rendering the raw badge produced **0**
non-background pixels in the icon box.

## 7. The fix, and the files it touched

**`core/author/SvgEmbeddedImages.kt` (new, pure Kotlin)** converts the document instead of the renderer, generically:

* an `<image>` whose reference is `data:image/svg+xml;base64,…` is replaced by
  `<g transform="translate(x,y) scale(s)" …>content</g>`, where the embedded document's own `viewBox`,
  `width`/`height` and `preserveAspectRatio` decide the geometry (`meet` centring by default, `none` honoured), and
  the embedded root's `fill`, `fill-rule`, `fill-opacity`, `stroke*`, `opacity` and `color` are carried onto the
  group so the glyph inherits its colour;
* `<script>`, `<title>`, `<desc>`, `<metadata>` and `<style>` inside an embedded icon are removed;
* an `<image>` whose reference is a **raster** `data:` URI keeps its element but has `href` rewritten to
  `xlink:href` (with `xmlns:xlink` added to the root) so the raster decoder can find it — that is the Bash icon;
* anything else (external URL, malformed base64, oversize payload, embedded SVG with no geometry) is left byte-for-byte
  as it was: nothing is fetched, nothing is executed, and a bad icon can never break the badge.

Limits: 256 KB per payload, 48 conversions per document, and a document with no `<image>` is returned unchanged.

**`data/author/AuthorImageDecoder.kt`**: calls `SvgEmbeddedImages.prepare()` once, before `SmilAnimation.detect`, so
every frame and every cache read inherits the conversion.

No new dependency; `AndroidSVG 1.4` stays as it is.

## 10. Root cause of the “static” Pacman graph

Two things were wrong, and the first is the one the user could see.

1. **Playback was tied to the panel being expanded.** `PanelsAuthor` passed `animateImages = expanded`, and `expanded`
   defaults to `false`. The collapsed panel is a 220 dp scrollable box: a reader can scroll it down to the graph — and
   in that state the frame loop never started, so the picture was genuinely frozen. That is the state the app opens
   in, which is why “in actual application use” the graph looked static while every test and the previous session's
   expanded-state measurement showed motion.
2. **A cropping defect that made the graph wrong even when it did animate.** These documents declare
   `width`/`height` and **no `viewBox`**, and `AndroidSVG` does not scale such a document when the document size is
   changed: it enlarges the viewport but draws the content 1:1, so everything beyond the viewport is clipped. The
   graph (1166×184) is decoded at 0.86× into 1000×157, so its right-hand columns and bottom rows were cut off. The
   same held for any badge rendered at a scale other than 1.

I could **not** reproduce a static graph while the panel was expanded: measured again on this build before the fix,
Pacman moved and the frames differed. The reproducible static case was the collapsed panel, and that is what is fixed.



## 11. Analysis of the animation pipeline

Stage by stage, against the code as it was:

**SMIL timeline.** `SmilAnimation.detect` finds `<animate>`/`<animateTransform>` by scanning tags (not by regex over
the document), records `values`, `keyTimes`, `dur`, `attributeName` and `type`, and takes the loop length as the
largest declared `dur` (29 400 ms) and the rate from `<frameRate>` (5, clamped to 1–10). Sampling is step-based: the
value in force at a normalised time is the last one whose `keyTime` has passed, which is what the generator's paired
keyTimes produce. `begin`, `repeatDur`, `keySplines` and fill-mode are not used by this source and are not
implemented; a document that needs them is refused (`detect` returns null) rather than approximated. Time is taken
modulo the duration, so the loop wraps and a monotonic clock is fine.

**Frame generation.** Each frame rewrites the sampled values into the element's own attributes, composes
`translate`/`rotate` into one `transform`, deletes the consumed animation elements and applies the edits back to
front. This was verified as *content*, not just as strings: `SmilAnimationTest` asserts that frames carry no
`<animate>`, that Pacman's transform both moves and turns, that the eaten-cell count grows, and that the
`<rect>`/`<use>`/`<path>` counts survive; `AuthorRenderTest` asserts that **rasterised** frames differ by more than a
thousand pixels, half a loop apart and one frame apart.

**Scheduling and Compose.** The loop lives in a `LaunchedEffect` keyed on `(animation, playing, lifecycle,
frameWidthPx)` and mutates a `mutableStateOf` frame, so every new frame recomposes the `Image`. Because the keys are
stable across recompositions, no second loop starts; because the effect is keyed on the animation *instance* and the
state only republishes on a repository emission, a recomposition cannot reset the clock. No `remember` holds an
obsolete bitmap, and no cache key is shared between timestamps.

**Visibility and lifecycle.** The loop body runs inside `repeatOnLifecycle(RESUMED)`, so backgrounding the app
cancels it and foregrounding restarts it. `playing` is now `true` whenever the README is composed; the composition
itself is bounded by the *More* tab and by the licence dialog's own tree.

**What was wrong:** only `playing`. It was `expanded`, so the collapsed panel — the panel's default state — never ran
the loop at all.

## 12. The animation fix and the files it touched

* **`ui/MoreScreen.kt`** — `animateImages = true`, with the reasoning recorded: playback follows whether the picture is
  on screen, not whether the panel is expanded.
* **`ui/markdown/MarkdownView.kt`** — `AnimatedSvgPicture` takes `frameWidthPx` and renders frames at the size the
  picture is actually drawn at (`constraints.maxWidth`, clamped to 64–1000) instead of a fixed 1000 px; the effect is

  drawn (it previously swallowed the failure, which is precisely how a frozen graph could go unexplained), and
  `rasteriseSvg` scales the canvas so no-`viewBox` documents are no longer cropped.

## 21. Remaining limitations and unverified behaviour

* **A fully static graph while the panel is expanded was not reproduced.** On this emulator that state animated before
  the fix too; the reproduced defect was the collapsed panel, which is fixed and measured. If the user's device still
  looks frozen, the new `AuthorPage` log line is the place to look — it fires when a frame cannot be rasterised, the
  only remaining way the loop could run without the picture changing.
* **Playback continues while the *More* tab is displayed even if the graph has been scrolled out of the collapsed
  box.** The cost is bounded (5 fps, one image, cancelled when the tab or the app leaves the foreground), but it is
  not true viewport-awareness; that would need the README's scroll viewport threaded into the renderer.
* **Icon support covers the structures these badges use**: an `<image>` pointing at an SVG or raster `data:` URI.
  Icons delivered as an external URL, a CSS `background-image`, or a `<use>` reference to another document are still
  not drawn — deliberately, since drawing them would mean fetching or executing something.
* **No Compose UI-test dependency exists in this project**, so the proof that the *displayed* picture changes is the
  device pixel measurement in §15–16, not an automated UI test; the instrumented tests prove the rendered bitmaps
  change.
* **Software-rendered emulator only** (`swiftshader_indirect`); frame timings on a physical device are unmeasured.
* **`calcMode="linear"` colour ramps are rendered as steps**, which matches what this generator's paired keyTimes
  produce but would be visible on a document that genuinely fades.
