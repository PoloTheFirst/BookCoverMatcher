# BookCoverMatcher — v2.4.0-rc.6 Implementation Prompt

## 1. Objective

Implement and verify the final Fields mapping and Column Mapping Profile corrections for the BookCoverMatcher `v2.4.0` stable release.

This prompt addresses two remaining defects and clarifies the intended behavior of the Detected and custom profile views.

### Remaining defects

1. **Detected Status defect:** Applying a mapping that is identical to the automatically detected mapping incorrectly changes Detected Status from blue to grey.
2. **Profile creation defect:** Saving a new custom profile can incorrectly copy the currently inspected worksheet's mapping values—including empty values—to other worksheets, instead of preserving the correct mapping for each worksheet.

### Essential clarification — profile view switching

The Fields function is supposed to let the user **switch between the Detected view and custom profile views**.

The word *switch* or *swap* here means changing which profile's mapping configuration is currently displayed and active in the Fields interface.

It does NOT mean:

- Exchanging the contents of two profiles.
- Copying custom mappings into the Detected profile.
- Copying detected mappings into an existing custom profile whenever the user switches views.
- Merging the mappings of two profiles during navigation.
- Transferring one worksheet's assignments to another worksheet.
- Mutating or overwriting saved profile data simply because the user selected a different profile.

The Detected profile and every custom profile must retain their own independent mapping data.

A separate requirement applies when creating a new custom profile: the new profile must correctly inherit the mappings of untouched worksheets from its source profile, while retaining the intended modifications to the worksheet being customized.

The implementation must preserve the previously approved `v2.4.0` functionality from rc.2 through rc.5 wherever applicable.

**Implementation prompt identifier:** `v2.4.0-rc.6`

**Agent report filename:** `v2.4.0-rc.6-ag`

## 2. Critical clarification: Detected and custom profile views

Read this section before changing the profile implementation.

### 2.1 Detected is the default profile view

The default profile is named **Detected**.

Its purpose is to display automatically detected header-to-column mappings for worksheets whose table structures are compatible with the application's canonical data model.

For example, in the supplied sample workbook:

- `LIST`
- `DATA`

are examples of worksheets that satisfy the consistent table-structure requirement.

These worksheet names are examples from the test workbook, not hardcoded application rules.

The application must determine compatibility using actual worksheet content, headers, and its existing mapping/detection logic.

Do not hardcode:

- `LIST` or `DATA`.
- Japanese header names.
- Fixed column positions.
- A fixed number of columns.
- The sample workbook's schema.

Worksheets that do not have a compatible or sufficiently detectable structure must retain the application's existing unsupported or unmapped behavior. Do not fabricate mappings.

### 2.2 Custom profiles are independent saved configurations

A custom profile represents a reusable mapping configuration.

It may contain mappings for multiple eligible worksheets.

Each custom profile must retain its own saved mapping configuration independently of:

- The Detected profile.
- Other custom profiles.
- The currently inspected worksheet.
- Temporary editable mapping state.
- Applied mapping state.

Selecting a profile changes which saved configuration is displayed in Fields. It must not exchange or mutate the contents of profiles.

### 2.3 Switching between profile views

The Fields interface must support switching between:

- **Detected**
- Any saved custom profile.

Expected behavior:

1. The user selects Detected.
2. Fields displays the detected mapping for the currently inspected worksheet.
3. The user selects a custom profile.
4. Fields displays that custom profile's saved mapping for the currently inspected worksheet.
5. The user switches back to Detected.
6. Fields displays the original detected mapping again.
7. The user switches back to the custom profile.
8. Fields displays that custom profile's saved mapping again.

This is a view/configuration selection operation.

**Switching profiles must not perform data exchange or implicit profile mutation.**

Specifically:

- Selecting Detected must not overwrite a custom profile.
- Selecting a custom profile must not overwrite Detected.
- Selecting one custom profile must not overwrite another custom profile.
- Switching profiles must not copy the currently inspected worksheet's values to other worksheets.
- Switching profiles must not merge the selected profile with another profile.
- Switching profiles must not silently save temporary edits into a different profile.
- Switching profiles must not discard saved mappings from other worksheets.

If the existing application requires an explicit Apply mapping action after selecting a profile, preserve that workflow. Profile selection and Apply mapping must remain distinct operations unless the existing product design explicitly defines otherwise.

### 2.4 Saving a new custom profile from Detected

When the user is viewing Detected and modifies one worksheet before saving a new custom profile, the new profile must contain a complete and correct per-worksheet configuration.

Example:

| Worksheet | Detected view | User modification |
|---|---|---|
| LIST | Detected mapping A | Changes one or more assignments |
| DATA | Detected mapping B | No changes |
| C108 | Unsupported or unmapped | No changes |

The user modifies `LIST` and saves a new profile named `Custom A`.

Expected contents:

| Worksheet | Custom A |
|---|---|
| LIST | User's modified mapping |
| DATA | Original detected mapping B |
| C108 | Existing unsupported/unmapped state |

The new custom profile must carry forward the untouched eligible worksheets' detected mappings.

It must not copy `LIST`'s assignments or empty values into `DATA`.

### 2.5 Saving with no modifications

If the user inspects a worksheet and saves a new custom profile without changing any mapping, the new profile must still preserve the correct mappings for all eligible worksheets.

The currently inspected worksheet must not become a global template.

### 2.6 Saving a new profile from an existing custom profile

If the existing workflow allows a new custom profile to be derived from another custom profile:

- Use the selected source profile as the inheritance source.
- Preserve its existing per-worksheet customizations.
- Replace only the mapping entries intentionally modified in the current editing workflow.
- Preserve untouched worksheets.
- Do not mutate the source profile.

Do not silently reset existing customizations to Detected when deriving a new custom profile from another custom profile.

### 2.7 Separate data sources and state

The implementation must distinguish:

1. Automatically detected mappings.
2. Saved mapping data in each custom profile.
3. The currently selected profile.
4. The current worksheet's editable mapping.
5. The current worksheet's applied mapping.
6. Temporary unsaved changes.

These are different concepts and must not be collapsed into one mutable global mapping object.

The active profile determines which configuration is displayed. Temporary editing and applying mappings must follow the existing workflow.

## 4. Bug A — Detected Status incorrectly changes from blue to grey

### 4.1 Reproduction

1. Open a workbook.
2. Open Insights → Fields.
3. Select the Detected profile.
4. Allow automatic detection to populate eligible worksheet mappings.
5. Inspect a worksheet without changing any assignments.
6. Click **Apply mapping**.
7. Observe Detected Status.

**Actual behavior:** Detected Status changes from blue to grey despite the applied mapping being identical to the detected mapping.

**Expected behavior:** Detected Status remains blue.

### 4.2 Required investigation

Trace:

- Automatic detection results.
- Current editable mapping.
- Active profile mapping.
- Applied mapping.
- Mapping validation.
- Detected Status calculation.
- Apply mapping event.
- Profile selection and restoration.
- State persistence.

Investigate whether the defect comes from:

- Object-reference comparison instead of semantic comparison.
- Different representations of equivalent mappings.
- Empty/unassigned values.
- An unconditional state reset during Apply mapping.
- Incorrect worksheet/profile scoping.
- StateFlow, Compose state, ViewModel, or recomposition behavior.
- A comparison against the wrong active profile.

Do not fix the symptom by unconditionally setting the indicator to blue.

### 4.3 Required behavior

Implement reliable semantic equality between the detected mapping and the effective mapping for the current worksheet.

The comparison must:

1. Compare actual column assignments rather than object identity.
2. Treat independently constructed but equivalent mappings as equal.
3. Handle empty and unassigned fields consistently.
4. Detect genuine changes.
5. Compare mappings belonging to the same workbook and worksheet.
6. Remain correct when switching between Detected and custom profile views.
7. Remain correct after navigation, recomposition, persistence, and restoration.

Expected results:

| Scenario | Expected status |
|---|---|
| Detected mapping applied without changes | Blue |
| Equivalent mapping reconstructed as a new object | Blue |
| Same detected assignments manually selected and applied | Blue |
| One or more assignments changed and applied | Grey |
| All changed assignments restored to detected values | Blue |
| A detected assignment is cleared | Grey if it differs from detection |
| Custom profile has a different mapping from Detected | Grey relative to Detected |
| Switch back to Detected | Blue when its mapping is applied |
| Different worksheet with different detection results | Independent status |

The status must describe whether the effective mapping corresponds to automatic detection. It must not merely describe whether Apply mapping was clicked.

## 5. Bug B — Incorrect custom profile creation and worksheet mapping contamination

### 5.1 Reproduction

1. Open a multi-worksheet workbook.
2. Open Insights → Fields.
3. Select the Detected profile.
4. Inspect one eligible worksheet.
5. Change zero, one, or multiple assignments.
6. Click Save profile and create a new custom profile.
7. Inspect the mappings for the other worksheets.

**Actual behavior:** Mapping values from the currently inspected worksheet, including empty values, are duplicated or propagated into other worksheets.

**Expected behavior:** The custom profile carries forward the correct mapping for every eligible worksheet:

- The inspected worksheet uses its current intended mapping.
- Untouched eligible worksheets retain their own detected mappings.
- Previously customized mappings are preserved when deriving a new profile from an existing custom profile.
- Unsupported or unmapped worksheets remain in their appropriate state.

The current worksheet must never be used as a universal mapping template for other worksheets.

### 5.2 Required investigation

Trace the complete profile lifecycle:

- Workbook identity.
- Worksheet identity.
- Worksheet structure and compatibility.
- Detected mapping for each worksheet.
- Active profile.
- Profile-specific mapping collection.
- Current editable mapping.
- Current applied mapping.
- Save profile operation.
- Profile serialization.
- Profile selection and switching.
- Mapping restoration.
- Repository and persistence layers.

Investigate:

1. Whether the profile data model supports multiple worksheet mappings.
2. Whether the save operation serializes only the currently inspected worksheet.
3. Whether the current mapping is accidentally assigned to every worksheet.
4. Whether a global mutable mapping object is shared.
5. Whether shallow copies share nested mutable collections.
6. Whether empty values are treated as global defaults.
7. Whether worksheet keys are omitted or incorrectly generated.
8. Whether worksheet names are being used where stable identities are required.
9. Whether the active profile is confused with the Detected profile.
10. Whether profile selection or switching mutates the detected baseline.
11. Whether missing mappings trigger a fallback to the currently inspected worksheet.
12. Whether saving a profile invokes an unintended global Apply operation.

Confirm the actual root cause before implementing the fix.

### 5.3 Required profile snapshot behavior

When saving a new custom profile, construct its contents using the intended inheritance rules.

At minimum, when deriving a custom profile from Detected:

1. Start from the complete set of eligible worksheet mappings in the Detected profile.
2. Preserve each worksheet's own detected mapping independently.
3. Replace only the mapping for the worksheet or worksheets that the user has actually modified in the current editing workflow.
4. Preserve all untouched eligible worksheets' detected mappings.
5. Preserve unsupported/unmapped worksheet states without fabricating assignments.
6. Save the complete resulting profile snapshot.

When deriving a custom profile from another custom profile, use that selected source profile as the inheritance source and preserve its existing per-worksheet customizations.

Do not reset unrelated worksheet mappings to Detected merely because one worksheet was modified.

Do not overwrite the Detected baseline.

### 5.4 Empty values

Empty/unassigned values are meaningful only within the appropriate worksheet mapping.

For example:

- If `LIST` has an unassigned field, that empty value belongs to `LIST`.
- If `DATA` has a valid assignment for the corresponding canonical field, saving a profile from `LIST` must preserve the `DATA` assignment.
- An empty value from one worksheet must not erase or replace another worksheet's mapping.

Do not merge mapping entries by canonical field name alone if doing so causes assignments from different worksheets to collide.

### 5.5 Data identity and independent snapshots

Each mapping entry must be associated with the correct workbook and worksheet.

Use stable identifiers already present in the application wherever possible.

Inspect how the existing implementation handles:

- Different workbooks containing worksheets with the same name.
- Duplicate or ambiguous worksheet identities.
- Worksheet renaming.
- Missing worksheets.
- Profile reuse across workbooks.

Ensure independent mapping data and avoid shared mutable references between:

- Different worksheets.
- Detected mappings and custom profile mappings.
- Different custom profiles.
- Editable and applied mappings.

Profile snapshots must be independent and deterministic.

## 6. Profile view-switching requirements

This section is especially important. Implement the actual view-switching behavior, not data exchange.

### 6.1 Switching from Detected to a custom profile

When the user selects a custom profile:

- The Fields interface must display the selected custom profile's saved mapping for the currently inspected worksheet.
- The selected profile must become the active profile view.
- Other worksheets must display their corresponding mappings from that same custom profile when inspected.
- The Detected profile must remain unchanged.
- Other custom profiles must remain unchanged.
- No profile data should be copied, merged, or exchanged merely because the user switched views.

### 6.2 Switching from a custom profile back to Detected

When the user selects Detected:

- The Fields interface must display the automatic detection results for the currently inspected worksheet.
- The Detected profile must remain the source of truth for automatic detection.
- Custom profile mappings must remain saved and unchanged.
- The custom profile's assignments must not remain visible simply because they were previously selected.
- No custom profile data should be written into the Detected profile.

### 6.3 Switching between custom profiles

When switching from Custom A to Custom B:

- Display Custom B's saved mapping for the currently inspected worksheet.
- Preserve Custom A's saved mapping.
- Preserve Custom B's other worksheet mappings.
- Do not merge the two profiles.
- Do not copy the currently inspected worksheet's values into other worksheets.
- Do not discard saved profile data.

### 6.4 Unsaved edits

Inspect how the existing interface handles unsaved mapping edits when the user switches profiles.

Preserve a predictable and safe behavior consistent with the existing UI:

- Do not silently write unsaved edits into another profile.
- Do not silently mutate the Detected baseline.
- If the existing interface prompts the user to apply, save, or discard changes, preserve that workflow.
- If it does not, implement the smallest appropriate safeguard so profile switching cannot silently contaminate saved profile data.

Do not introduce unnecessary dialogs or redesign the profile selector.

### 6.5 Switching profiles must be reversible

The following sequence must work:

1. Select Detected.
2. Inspect `LIST`.
3. Inspect its detected mapping.
4. Select Custom A.
5. Inspect the custom mapping for `LIST`.
6. Select Detected.
7. Confirm the original detected mapping for `LIST` is displayed.
8. Select Custom A again.
9. Confirm its saved custom mapping is displayed again.

Repeat the sequence for other eligible worksheets.

At no point should selecting a profile modify the saved data of another profile.

### 6.6 Profile selection versus Apply mapping

Keep these operations conceptually distinct:

- **Profile selection:** Changes which profile's configuration is displayed in Fields.
- **Mapping editing:** Changes the editable mapping in the active profile context.
- **Apply mapping:** Applies the current worksheet's effective mapping according to the existing application workflow.
- **Save profile:** Creates or updates a saved profile according to the existing explicit user action.

Do not treat profile selection as an implicit global Apply operation.

Do not treat Apply mapping as a command to rewrite all worksheets.

Do not treat Save profile as a command to exchange profile data.

- Every mapping belongs to its own worksheet.
- Untouched worksheets retain their inherited mappings.

- Changing the selected profile does not mutate saved profile contents.
- Changing the selected profile does not overwrite automatic detection results.
- Switching profiles restores the selected profile's mappings for the current worksheet.

### 7.4 Editable and applied state

- Editing changes the appropriate active-profile editing state.
- Apply mapping applies the appropriate mapping for the current worksheet.
- Applying a mapping does not silently rewrite unrelated worksheets.
- Detected Status is calculated semantically against automatic detection.

### 7.5 Persistence

- Profiles persist all intended worksheet mappings.
- Reloading restores complete profile snapshots.
- Switching between profiles after reopening produces the same results.
- Serialization and deserialization preserve worksheet associations and empty values.
- Existing user-created profiles must not be silently discarded.
