## 4. Architecture requirements

### 4.1 Preserve the existing Android architecture

The Android application remains Kotlin-based.

Rust is responsible only for native OCR processing.

Do not migrate unrelated application logic to Rust.

Preserve the existing OCR abstraction, particularly the existing `OcrTextSource` contract.

Inspect its actual methods, lifecycle, result types, error handling and cancellation behavior before implementing the native adapter.

Do not invent a parallel OCR architecture if the existing abstraction can be extended cleanly.

### 4.2 Kotlin integration

Implement the minimum Kotlin layer needed to call the native Rust OCR engine.

Expected components may include:

- `NativeOcr`
- `RustOcrTextSource`

Use these names only if they fit the actual repository architecture.

The Kotlin layer should:

1. Load the native Rust library safely.
2. Initialize the native engine with validated model paths.
3. Pass image data through a documented and efficient interface.
4. Return structured OCR results.
5. Expose detected text, confidence and bounding-box information where supported.
6. Propagate native errors clearly.
7. Support cancellation.
8. Avoid blocking the main/UI thread.
9. Avoid unnecessary image copies.
10. Release native resources deterministically.

The implementation must follow the actual Rust crate API and JNI requirements.

Do not guess JNI signatures or memory layouts.

### 4.3 JNI design

Implement JNI with careful memory and lifecycle management.

Requirements:

- Use stable JNI entry points and signatures.
- Avoid holding JNI references beyond their valid scope.
- Release acquired arrays and image buffers correctly.
- Handle Kotlin/Java exceptions safely.
- Do not allow Rust panics to unwind across JNI boundaries.
- Convert Rust errors into structured Kotlin-visible failures.
- Validate all dimensions and buffer lengths.
- Avoid unbounded native allocations.
- Avoid unnecessary `unsafe` code.
- Document unavoidable unsafe boundaries.
- Support repeated engine initialization and destruction.
- Prevent concurrent access to mutable ONNX Runtime sessions.
- Ensure cancellation cannot leave an engine in an inconsistent state.

Do not expose raw Rust internal structures directly to Kotlin.

Prefer a stable, minimal JNI interface.

### 4.4 Cancellation and concurrency

The existing Rust engine uses serialized mutable session access.

Preserve this safety model.

Requirements:

- Native OCR operations must not run on the UI thread.
- Multiple OCR requests must not corrupt shared session state.
- Cancellation must be propagated where safely possible.
- Stale results must not overwrite newer requests.
- A cancelled request must not leave native resources allocated indefinitely.
- Initialization and shutdown must be thread-safe.
- Define behavior when cancellation occurs during ONNX inference, where immediate interruption may not be supported.

Do not claim inference can be interrupted if the ONNX Runtime API does not provide that capability.

If immediate native inference cancellation is unsupported, document the limitation and ensure the result is safely discarded.
