## 5 · Reference environment and method

`paddleocr` itself is **not installed** on this machine and could not be installed reliably (Paddle pulls
a large CPU runtime). What *is* available: Python 3.14 with `onnxruntime 1.30.0`, `numpy 2.5.3`,
`opencv-python 5.0.0`, `Pillow 12.3.0`.

So the reference is an **independent implementation of the official PaddleOCR algorithm** — the same
transforms and post-processing, written from the documented pipeline, running the same pinned ONNX files:

```
det: cv2.imread(BGR) → DetResizeForTest(736, min|max) → NormalizeImage(1/255, ImageNet mean/std)
     → ToCHW → det.onnx → DBPostProcess(0.2 / 0.45 / unclip 1.4 / min_size 3)
     → get_mini_boxes (min-area rect) → get_rotate_crop_image
rec: RecResizeImg([3,48,320]) → rec.onnx → CTCLabelDecode(['blank'] + 18,708 chars + ' ')
```

Documented deviations (no others): `pyclipper` absent, so `unclip` expands the min-area rectangle's sides
by `area × ratio / perimeter` — identical for a rectangle polygon; and no crop rotation in the
reference, so the vertical handling could be measured separately. Every stage was then validated
*against the Rust engine*, not just against itself:

* **Recogniser parity — exact.** The Python recogniser run on the Rust engine's dumped crops
  (`--dump-crops`, `rec_on_crops.py`) reproduced the Rust text on **10 of 10** lines of the real cover
  (`THE AUTHORIZED EDITION`, `THE`, `HOBBIT`, `THE ENCHANTING PRELUDE TO`, `"THE LORD OF THE RINGS"`, …)
  with the same per-line confidence to three decimals. That pins preprocessing, BGR order, resize and
  padding, tensor layout/type, the CTC blank/repeat rule, dictionary indices and Unicode handling.
* **Detector parity — compared, one real difference.** Same image, both pipelines found the same regions
  on every fixture (detection recall 1.00 before and after every change), but the reference upscaled
  (`min` policy) while the engine did not (`max`), and the reference normalised BGR while the engine
  normalised RGB. Both were isolated and measured rather than guessed (§6).
* **Decoding.** No dictionary, index or Unicode mismatch was found; the crash-fix-6 dictionary
  reconciliation holds (18,708 entries, class width 18,710, no second softmax).

## 6 · Stage-by-stage parity results

One variable at a time, same fixtures, same models (overall CER; lower is better):

| Variant | det resize | det channels | overall CER |
|---|---|---|---|
| `ref-min-bgr` (PaddleOCR default) | short side → 736 | BGR | 0.161 |
| `ref-min-rgb` | short side → 736 | RGB | 0.172 |
| `ref-max-bgr` | long side → 736 (the engine's) | BGR | 0.161 |
| `ref-max-rgb` | long side → 736 | RGB | 0.149 |

* **Resize policy:** `min` and `max` are indistinguishable overall (0.161 both). The engine keeps `max`
  — its own behaviour, and the one that reads the real cover best — instead of adopting PaddleOCR's
  default. Recorded as an explained difference, not a defect.
* **Channel order:** the official pipeline is BGR (`DecodeImage(img_mode='BGR')`), the engine was RGB.
  Fixed. The measured effect is about one character over ~40 (0.161 vs 0.149 — RGB marginally *better* on
  these synthetic covers), so the change is reported as a parity fix, **not** an accuracy gain; see the
  comment in `native/ocr/src/det.rs` and `tools/ocr-reference/README.md`.
* **Not defects, verified the same way:** DB thresholds/unclip already match the model's `inference.yml`
  (`0.2 / 0.45 / 1.4 / 3000`); the box score is a probability-map mean; crops are min-area-rect in the
  reference and axis-aligned in the engine, which cost nothing measurable on upright or 9°-rotated

## 7 · Root causes, with evidence

1. **Vertical text was destroyed before recognition (fixed).** A detected column taller than wide was
   cropped upright and handed to `RecResizeImg`, which keeps the aspect ratio: a 73×347 column becomes a
   12-pixel-wide canvas, so five characters are squeezed into ~12 px and the model emits one stray glyph.
   `ja_vertical` read `大`/`2`/`试验` depending on thresholds. Feeding the same crop to the recogniser
   directly proves the fix is geometric, not model tuning:

   | input to the recogniser | score | text |
   |---|---|---|
   | as-is | 0.074 | `试验` |
   | rotated clockwise | 0.313 | `修青小站` |
   | **rotated counter-clockwise** | **0.877** | `縱書き小説` |
   | per-character cells | — | `縦書き小説` |

   `engine::recognise_region` now turns a crop with `height ≥ 1.5 × width` 90° counter-clockwise before
   recognition. `ja_vertical` went **CER 1.000 → 0.000** and reads `縦書き小説` exactly.
2. **Detector channel order (fixed, parity).** §6.
3. **Full-width digits reached the search query (fixed downstream).** `じれったい２` was searched
   verbatim; catalogues index `2`. `core/online/SearchText.kt` NFKC-folds the *query* only — the raw text
   stays in `OcrText.text`, the result panel and the log. `OcrQueryExtractor.Suggestion` now carries
   `searchTitle`/`searchAuthor` next to the raw `title`.

Classification of the reported symptoms, as the task requires:

| Reported symptom | Stage | Verdict |
|---|---|---|
| Japanese title absent entirely | crop/geometry (vertical squeeze) **and** model domain weakness | the vertical part is **fixed**; scattered/artistic titles remain hard for PP-OCRv6 Medium |
| `BOODEI`, `Foun`, `m`, `九`, `品` — stray Latin/garbage fragments | recognition on crops that mix artwork with type; the reference reproduces the same behaviour | model/domain limitation, not a decode bug |
| Latin lines read well (`R-18`, `FINAL FANTASY SEVEN Tila Lockhart FAN BOOK`) | recogniser on clean lines | already correct; `Tifa`→`Tila` is a model confusion |
| — | detection recall | **not** the failure mode: recall was 1.00 on every fixture and the real cover's regions were all found |
| — | CTC / dictionary / Unicode | verified correct by the recogniser parity above |

## 16 · Limitations and remaining model weaknesses

1. **No physical-device run.** Everything is emulator x86_64.
2. **The user's cover is untested** (§11). No claim is made about its title.
3. **Scattered/artistic Japanese lettering still loses characters** (`じれったい` → `じれつたい`, and the
   reported `BOODEI`/`Foun`/`九`/`品` fragments). This is PP-OCRv6 Medium on type mixed into artwork, not a
   pipeline bug: the independent reference implementation produces the same behaviour, and the crops are
   correct (verified by dumping them and re-recognising them in the reference).
4. **Full-width digits come out full-width** (`２`); mitigated only on the query side.
5. **Latin typos remain** (`Tifa` → `Tila`, `BOUGHTON`/`HOUGETON`, `RRTOLKIEN`).
6. **Axis-aligned crops** instead of min-area rectangles: no measurable cost on the fixtures, but a
   strongly sheared text line would be cropped with background.
7. **No multi-scale, orientation-search or batching** — not justified by the measurements.
8. **`ja_decorative` regressed by one character** with the BGR change.
9. Synthetic fixtures are cleaner than print; absolute CER here must not be quoted as real-cover accuracy.
