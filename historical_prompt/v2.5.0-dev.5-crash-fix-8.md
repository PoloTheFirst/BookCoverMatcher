# BookCoverMatcher — v2.5.0-dev.5-crash-fix-8

## Objective

Implement and verify the actual integration of native PaddleOCR into the existing **Online → READ THE COVER** feature.

This task corrects the intended application behaviour:

**Chrome Lens OCR and PaddleOCR must coexist as two independently selectable OCR engines. Neither engine should replace or silently fall back to the other.**

The previous `v2.5.0-dev.5-crash-fix-6` task reportedly implemented native Rust/JNI PaddleOCR, Kotlin integration, model installation, and engine selection infrastructure. However, the actual Online → READ THE COVER experience still appears to identify or use `chrome-py-lens`.

Do not assume that the previous implementation report is accurate or that the integration is complete. Audit the actual source code, Git history, application wiring, and runtime behaviour before making changes.

The primary deliverable is a working, verifiable OCR engine selector connected to the real READ THE COVER execution path.

# 1. Required Intended Behaviour

## 1.1 Two selectable OCR engines

The existing READ THE COVER feature must support these two engines:

| Engine | Implementation | Role |
|---|---|---|
| Chrome Lens OCR | Existing `chrome-lens-py` / Chaquopy implementation | Existing engine; retain unchanged |
| PaddleOCR | Native Rust `bc_ocr` + ONNX Runtime, PP-OCRv6 Medium | Additional alternative engine |

Both engines must process the same input image and provide OCR text through the same downstream online-search workflow.

The user must be able to select either engine without changing any other Online feature settings.

## 1.2 Engine selection UI

Add or correct a persistent OCR engine selector in the Online tab's READ THE COVER settings or an appropriate nearby location.

Suggested presentation:

**OCR Engine**

- Chrome Lens (default)
- PaddleOCR (PP-OCRv6 Medium)

Requirements:

1. Clearly identify both engines by human-readable names.
2. Do not expose internal identifiers such as `chrome-py-lens` as the primary user-facing engine name.
3. Preserve the user's selection across application restarts.
4. Use Chrome Lens as the default for existing installations and new installations.
5. Do not automatically change the selected engine because another engine becomes available.
6. Clearly indicate when PaddleOCR is unavailable because its native library or model files are missing or invalid.
7. Do not silently switch to Chrome Lens when PaddleOCR is selected.
8. Do not silently switch to PaddleOCR when Chrome Lens is selected.
9. Keep the selector relevant to READ THE COVER rather than changing unrelated OCR functionality.
10. Respect existing UI design conventions and localization practices.

The setting must be connected to the actual execution path, not merely stored or displayed.

## 1.3 Actual execution routing

The expected architecture is:

```text
Online Tab
    |
    v
READ THE COVER
    |
    v
Read selected OCR engine
    |
    +-----------------------------+
    |                             |
    v                             v
Chrome Lens OCR               PaddleOCR
    |                             |
    v                             v
Existing Python OCR           RustOcrTextSource
    |                             |
    +-------------+---------------+
                  |
                  v
          Shared OCR result
                  |
                  v
       Existing online-search flow
```

The implementation must trace the real production call path, starting at the READ THE COVER user action and ending at the OCR text consumed by the online-search workflow.

Do not create a parallel OCR demonstration screen or a test-only implementation and claim that the feature is integrated.

## 1.4 Shared OCR interface

Retain the existing `OcrTextSource` abstraction wherever possible.

Both implementations must use the same interface:

- Existing Chrome Lens implementation.
- Native PaddleOCR implementation (`RustOcrTextSource`).

The engine-selection layer should dispatch to the correct implementation for every READ THE COVER request.

Avoid unnecessary architectural rewrites. Reuse the existing classes and infrastructure if they are correct.

## 1.5 Engine identity and diagnostics

The application must identify the engine that actually processed each request.

Requirements:

- Human-readable engine name in the UI.
- Internal engine identifier in diagnostic logs.
- Engine version where available.
- Actual selected engine recorded for each OCR request.
- Clear errors when the selected engine cannot execute.
- No misleading status that reports PaddleOCR merely because its preference is selected.
- No misleading status that reports Chrome Lens merely because an old identifier remains in a generic OCR status field.

If the UI displays an engine status, distinguish:

- Selected engine.
- Engine availability.
- Engine actually used for the current request.

These are separate states.

# 3. PaddleOCR Integration Requirements

## 3.1 Preserve the existing native implementation

Reuse the existing native Rust OCR implementation and model configuration.

Target model:

**PaddleOCR PP-OCRv6 Medium ONNX**

Do not substitute PP-OCRv6 Small or Tiny.

Preserve:

- Existing detector preprocessing and postprocessing.
- Existing recognizer preprocessing.
- The verified 18,708-entry recognition dictionary.
- The 18,710-class CTC mapping.
- Existing ONNX Runtime configuration.
- Existing JNI and Kotlin native interface where valid.
- Existing model SHA256 validation.
- Existing model installation and verification mechanisms.

Do not unnecessarily replace or redesign these components.

## 3.2 APK-bundled model availability

PaddleOCR must be ready for normal users after installing the distributable APK. Its availability must not depend on a developer manually installing model files.

Verify:

- Native library is packaged for the current ABI.
- ONNX Runtime can be loaded.
- Detector model is included in the APK.
- Recognizer model is included in the APK.
- The exact verified recognition dictionary is included in the APK or another verified packaged resource.
- All model and dictionary hashes are verified.
- Engine initialization succeeds.

If PaddleOCR is unavailable, display a clear explanation. Do not mark it Ready merely because the preference contains `"paddle"`.

## 3.3 Package complete PaddleOCR assets into the APK

**Mandatory: every distributable APK must contain the complete PaddleOCR implementation and all required model assets.**

A normal end user must not need to build Rust, download ONNX models separately, run PowerShell/ADB/`run-as`, copy models, configure a model directory, or connect to the internet at runtime.

Package at minimum:

1. PP-OCRv6 Medium detector ONNX model.
2. PP-OCRv6 Medium recognizer ONNX model.
3. The verified 18,708-entry recognition dictionary.
4. Any additional configuration or metadata required by the native implementation.
5. ABI-appropriate `libbc_ocr.so`.
6. The required ONNX Runtime native library, once per ABI.

Use the exact model revisions, dictionary, and SHA-256 values already verified by the previous implementation. Do not substitute PP-OCRv6 Small or Tiny.

Prefer an Android asset location such as:

`app/src/main/assets/ocr/ppocrv6/`

The final APK itself must contain the required model files. Files that exist only in a developer directory, Git-ignored folder, CI cache, external storage, or manually prepared emulator do not satisfy this requirement.

### 3.3.1 Reproducible build-time asset preparation

If model files should not be committed to Git, implement an automatic Gradle build dependency that obtains the pinned assets during the developer/CI build.

- Pin exact upstream revisions and expected SHA-256 hashes.
- Automatically obtain missing assets as part of the normal Gradle build.
- Verify every asset before packaging.
- Fail the build if any required file is missing, truncated, or hash-invalid.
- Do not require a separate undocumented manual script.
- Keep downloaded model artifacts out of Git unless repository conventions explicitly require tracked assets.
- Document first-time network requirements for the build environment.
- Reuse verified local artifacts on subsequent builds.

The end user must not perform any build-time preparation.

### 3.3.2 Automatic first-launch extraction

If the native ONNX Runtime interface requires filesystem paths, automatically extract packaged assets into application-private internal storage.

- Do not ask the user to select a directory.
- Use internal storage, not shared external storage.
- Verify SHA-256 and expected size before marking files ready.
- Write temporary files and atomically rename only after successful verification.
- Avoid partially initialized model directories.
- Recover safely from interrupted extraction.
- Reuse verified files on later launches.
- Prevent concurrent initialization from racing or corrupting files.
- Do not request storage permissions.
- Do not require runtime internet access.

Preparation must not block the entire application indefinitely. Use background execution and expose a meaningful preparation state when necessary. Other application features must remain usable while PaddleOCR assets are prepared.

If extraction or verification fails, report a clear error, preserve the selected engine preference, provide retry where appropriate, do not silently fall back to Chrome Lens, and do not claim PaddleOCR is ready.

### 3.3.3 APK and ABI verification

Add or update an automated verification task/script that inspects the actual generated APK archive, not merely the source asset directory.

For every distributable APK, verify:

- Detector ONNX exists and its extracted hash matches the pinned hash.
- Recognizer ONNX exists and its extracted hash matches the pinned hash.
- Dictionary exists and its hash/content is correct.
- `libbc_ocr.so` exists for the APK's ABI.
- ONNX Runtime exists once for that ABI.
- No required asset is excluded by Gradle packaging rules.

Preserve all officially supported ABIs, at minimum `arm64-v8a` and `x86_64` if those remain supported. A universal APK must contain the appropriate native libraries for every supported ABI. Each ABI-specific APK must contain all model assets and the matching native libraries.

The verification report must include:

| Resource | Expected | Actual | Verification |
|---|---|---|---|
| Detector ONNX | Pinned SHA-256 | APK entry and extracted hash | Pass/fail |
| Recognizer ONNX | Pinned SHA-256 | APK entry and extracted hash | Pass/fail |
| Dictionary | Pinned SHA-256 | APK entry and extracted hash | Pass/fail |
| Rust library | ABI-specific | APK entry | Pass/fail |
| ONNX Runtime | ABI-specific, one copy | APK entry | Pass/fail |

Also report each APK's file size, total OCR asset size, native library sizes per ABI, and whether model assets are compressed or stored uncompressed.

A successful Gradle build alone is not proof that packaging is complete.

### 3.3.4 APK size and distribution constraints

The model assets were previously reported to total approximately 139 MB. Confirm actual sizes from the pinned files and report final APK sizes.

This size increase is intentional. Do not reduce it by removing required model files, substituting a smaller model, moving models to a user-managed directory, requiring users to download models after installation, or making PaddleOCR developer-only.

Check applicable Android and distribution-channel size limits. If a channel imposes a constraint, explain the exact limitation and propose a delivery mechanism that still provides a complete, straightforward installation without requiring users to manually obtain model files. Do not unilaterally weaken the APK-bundling requirement.

## 3.3 No silent fallback

If PaddleOCR is selected and fails:

- Return a clear PaddleOCR error.
- Do not invoke Chrome Lens automatically.
- Do not silently change the stored preference.
- Preserve the error category and useful diagnostic information.

If Chrome Lens is selected and fails:

- Return the Chrome Lens error.
- Do not invoke PaddleOCR automatically.

The user can manually select the other engine and retry.
