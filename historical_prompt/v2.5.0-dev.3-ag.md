## 2. Root cause of the SauceNAO automation failure

**The key was never stored.** It was not a status-display bug, a stale cache or a missing provider registration:

1. `OnlineSearchController.saveSauceNaoKey` → `SauceNaoKeyStore.save` → `AesGcmSecretBox.seal(key, plain, iv)`.
2. `seal` called `Cipher.init(ENCRYPT_MODE, keyStoreKey, GCMParameterSpec(128, iv))` — i.e. it supplied **its own
   nonce**. An `AndroidKeyStore` AES/GCM key is created with `setRandomizedEncryptionRequired(true)` and **forbids**
   that.
3. The platform refused it. Measured on the emulator while reproducing:

   ```
   E keystore2: Caused by:
   E keystore2:  0: system/security/keystore2/src/enforcements.rs:585:
                NONCE is present, although CALLER_NONCE is not present
   E keystore2:  1: Error::Km(r#CALLER_NONCE_PROHIBITED) for AppUid(10235)
   ```
4. `save` caught the exception, returned `false`, and the UI said *"That does not look like a SauceNAO key; nothing
   was saved."* — blaming the user's key. Verified at the time: `shared_prefs/` contained
   `bookcover_online.xml` and `chaquopy.xml` but **no `bookcover_online_secrets.xml`**; the row stayed `NEEDS KEY`
   after a save attempt with a syntactically valid key.
5. With nothing stored, `SauceNaoReverseImageSource.readiness()` correctly answered `NOT_CONFIGURED`, and
   `ReverseImageSearchRunner` skipped the provider before any socket opened. The UI was telling the truth about a
   state the crypto layer had produced.

Secondary defect found in the same flow: after any run, `reverseProviderRows()` prefers the recorded run over the
provider's live readiness, so a `NOT_CONFIGURED` run recorded *before* a key existed would keep the row on
`NEEDS KEY` even after a successful save.

Introduced by: v2.5.0-dev.2 (`a73e814`), which added both the Keystore-backed store and the run-row preference. No
earlier build stored a credential at all, so this could not have appeared before.

## 3. SauceNAO implementation changes

| File | Change |
|---|---|
| `core/secret/SecretBox.kt` | `seal(key, plain)` no longer accepts an IV: it calls `Cipher.init(ENCRYPT_MODE, key)` with **no** parameter, rejects a non-12-byte cipher IV, and prefixes `cipher.iv` to the ciphertext. `open` is unchanged (decrypting with the stored IV is allowed). The class comment records the `CALLER_NONCE_PROHIBITED` evidence. |
| `core/online/reverse/SauceNaoKeyRules.kt` *(new)* | Pure rules: `isPlausible(raw)` (8–128 chars, no internal whitespace), plus `SauceNaoKeyRejection` / `SauceNaoKeySaveResult` and `describe(rejection)` — two different, key-free messages for "malformed" and "storage failed". |
| `data/SauceNaoKeyStore.kt` | `save` returns `SauceNaoKeySaveResult` instead of `Boolean`; uses the cipher-chosen IV; writes with `commit()`; **reads the value back** through `key()` and reports `STORAGE_FAILED` if that fails. |
| `online/OnlineSearchController.kt` | `saveSauceNaoKey` renders the specific rejection message, and on success **discards the stale SauceNAO run** (`reverseRuns.remove(...)`) before rebuilding the rows, so the row reflects live readiness. |
| `ui/ReverseImagePanel.kt` | Adds **Replace** next to **Remove** for a stored key; the field opens with a *New SauceNAO API key* hint and a *Cancel*, so replacing never requires deleting the working key. |

Why this fixes the cause rather than the symptom: the failing operation was *encryption with a caller-supplied
nonce*. The IV now comes from the platform, which is the documented way to use a Keystore AES/GCM key. Nothing is
caught-and-ignored: a storage failure gets its own state, and the round-trip check makes "saved" mean "readable".
The provider reads the key at call time (`apiKey = { sauceNaoKey.key() }`), so a replaced key is used by the very
next request.

Provider states are unchanged in kind and still distinguish `NOT_CONFIGURED`, `READY`, `SEARCHING`, `SUCCESS`,
`NO_RESULTS`, `RATE_LIMITED`, `QUOTA_EXCEEDED`, `TIMEOUT`, `BLOCKED`, `UNAVAILABLE`, `CANCELLED`, `ERROR` and
`MANUAL_ONLY`. An invalid key is reported by the provider's own answer: a non-zero `header.status` becomes `ERROR`
(or `QUOTA_EXCEEDED` when the allowance is exhausted), an HTTP 403/451 becomes `BLOCKED` with a message naming the
key as the likely cause, and neither is retried.

## 7. IQDB card rubbish bin and dismissal (requirement 4)

* **Placement.** The card's title row now holds the title (`weight(1f)`) and, when the card is eligible, an
  `IconButton` (36 dp) at the top-right containing `Icons.Filled.Delete` (18 dp) — the material-icons-core bin, which
  the project already depends on.
* **Accessibility.** `contentDescription = "Dismiss IQDB result"`, an `IconButton` touch target, and the rest of the
  card remains a separate (non-icon) tap area, so a normal tap cannot dismiss.
* **Eligibility.** `ReverseCandidateUi.isIqdbOnly` = "reported by `iqdb` **and not** by `saucenao`". Every IQDB card
  (automated or pasted) gets the icon; SauceNAO-only cards never do; a card both providers found keeps its card,
  because dismissing it would discard the first-priority provider's evidence. `providerIds` is carried through
  `ReverseImageCandidate.toUi`.
* **Effect.** `OnlineSearchController.dismissCandidate(key)` removes that key from `searchCandidates` and
  `pastedCandidates` and republishes. It touches no other card, no SauceNAO result, no `CandidateDecisionRecord`, no
  workbook cell, no wishlist entry and no cached image, and it writes nothing to disk. A later search may show the
  result again (no persisted dismissal), as the requirement allows. Because the operation is purely in-memory and the
  runner's generation guard drops stale runs before `applyReverseResult`, a late response cannot reinsert a dismissed
  card.
* **Tests.** `IqdbCandidateUiTest` (5) covers eligibility and attribution survival; the runtime flow below covers the
  interaction.

Runtime evidence (device):
`9 candidate(s)` with exactly one node whose `content-desc` is `Dismiss IQDB result` → tap → `8 candidate(s)` and
**zero** such nodes, with the SauceNAO cards (`SauceNAO 40.27%`, …) still present and no crash.

  outside the repository, which was deleted immediately afterwards).
* It never entered the repository: no source file, test, changelog, report, or documentation contains it.
* `adb logcat` was scanned for the full key, its first 8 characters and its last 4 characters: **no match**.
* `shared_prefs/bookcover_online_secrets.xml` holds base64 ciphertext only; the plaintext exists only inside the
  app's decrypt path.
* **The prompt file is the one place it exists on disk**: `historical_prompt/v2.5.0-dev.3.md` contains the key
  verbatim (the user had pasted it there and it was staged before this task).
* **Incident during this task, recorded honestly:** the first attempt at the docs commit accidentally included that
  prompt file — `git add` of the report plus a plain `git commit` carried the index entry that had been restored
  earlier. It was caught immediately by a 40-hex scan of the commit (`git show --stat` showed
  `historical_prompt/v2.5.0-dev.3.md`), the commit was undone **before any push** (`git reset --soft HEAD~1`), the
  file was unstaged, and the docs commit was recreated containing only the report. **Nothing was pushed with the
  key**: `git log -p f544ff1^..HEAD` now contains exactly four 40-hex tokens — the two commit hashes and the
  synthetic `0123…4567` test fixture — and neither the local nor the remote history has ever held the key.
* The file is now listed in `.git/info/exclude` (a local, uncommitted exclusion) so it cannot be staged by accident
  again. Recommendation for the user: keep it out of Git, and rotate the key if that file has been shared; if it
