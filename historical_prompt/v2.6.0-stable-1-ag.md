## 4. Pacman 60 FPS requirement

### 4.1 What the previous implementation actually did, and why it could not be faster

Crash-fix 3 sampled the document's timeline at 18 fps and produced each frame by rebuilding the frame document,
parsing it with `AndroidSVG` and rasterising it — measured at 15.6 fps presented. `PacmanFrameCostTest` (instrumented,
real asset, real renderer) shows that no scheduler could have done better on that path:

```
PACMAN-COST parse=16.51ms raster=70.60ms
PACMAN-COST production=77.11ms layered=0.04ms
PACMAN-COST budget=16.67ms (60 fps)
```

A whole-document frame cost **77.11 ms** — the parse (16.5 ms) is minor and the **rasterisation (70.6 ms)** is the
bottleneck, against a 16.67 ms budget. Better timers, string caching or more threads could not have reached 60 fps; the
renderer had to stop re-rasterising the whole picture.

### 4.2 The source's own temporal resolution

| Animation | Elements | Duration | Mode | What it means at 60 Hz |
| --- | --- | --- | --- | --- |
| Pacman `translate` | 1 | 29 000 ms, 145 keys | linear (SMIL default) | ~200 ms between keys → **12 real intermediate samples** per segment; motion is genuinely continuous |
| Ghost `translate` ×4 | 4 | 29 000 ms, 118–145 keys | linear | same |
| Pacman `rotate` | 1 | 29 000 ms, 82 keys | `discrete` | quarter-turns; no interpolation expected |
| Pacman `d` (mouth) | 1 | **500 ms**, 3 values | no mode | a chomp cycle of its own, 2 shapes per 500 ms |
| Ghost `visibility` | 31 | 29 000 ms | discrete | which direction sprite shows — a table lookup |
| Cell `fill` | 20 | 29 000 ms | discrete | each eaten cell steps once, at its own keyTime |

Only the translations are continuous, and they are continuous *for real*, so 60 fps is honest smoothness rather than
duplicated frames. Sampling each animation against **its own** duration also fixed a latent fidelity bug: the 0.5 s mouth
cycle had been sampled against the 29 s loop, freezing Pacman's mouth on its first shape for the first 14.5 s.

### 4.3 Implementation

- **`SmilTimeline` (new, pure Kotlin, JVM-testable)** splits the document once into the **scenery** (canvas, 371 cells,
  maze walls, month labels — the document with every `<animate>` and all five movers removed), the **movers** (Pacman +
  4 ghosts with their translate/rotate/fill/shape animations and, per ghost, its direction sprites), and the **20
  flashing cells** with their switch keyTimes. `sceneAt(t)` answers "what does the frame look like now" without drawing.
- **`PacmanCompositor` (new, Android)** builds all bitmaps once: the scenery via `AndroidSVG`, the 21 ghost PNGs decoded
  from their `<symbol>` data URIs and scaled once, Pacman's mouth shapes pre-rasterised by `AndroidSVG` from the
  document's own `d` values (so the geometry stays the renderer's, not a hand-written path parser). A frame is then one
  blit, at most twenty rounded rects, four sprite blits and one rotated blit into a reusable buffer.
- **`MarkdownView`** builds the compositor off the main thread, alternates two frame buffers (Compose compares bitmap
  instances, so reusing one would leave the old picture on screen), and paces playback with **`withFrameNanos`** — the
  Compose frame clock, i.e. the display's own vsync — instead of a fixed `delay`.
- **Nothing is allocated or parsed per frame.** A tick whose `frameKey` is unchanged draws nothing, one loop per image is
  owned by `LaunchedEffect`, playback runs only while the picture is shown and the app is `RESUMED`, and the
  compositor's bitmaps are released on dispose (frame buffers deliberately not recycled — Compose may still hold one).

### 4.4 Equivalence with the old renderer

A rewrite that is fast but wrong is worthless, so `theComposedFrameMatchesTheWholeDocumentFrameAtTheSameInstant` renders
the same instants both ways and compares pixels:

```
PACMAN-FPS equivalence at 0ms: 2388 of 124888 pixels differ
PACMAN-FPS equivalence at 6000ms: 2277 of 124888 pixels differ
PACMAN-FPS equivalence at 18000ms: 1735 of 124888 pixels differ
```

1.4–1.9 % of pixels differ — sprite antialiasing edges only, which is the expected difference between blitting a decoded
sprite and re-rasterising it from the document. The picture is the same picture.

## 12. Remaining limitations

1. **Release signing is impossible here.** There is no release keystore in the repository and I will not fabricate one or
   present the debug key as a release key. The owner must supply a release key, and its secrets must reach the build
   through a local, untracked mechanism — never through chat or a tracked file.
2. **`display-mask:0.3.0` is unresolved and packaged.** Removing it is not demonstrably safe: the class sits on the
   interactive sign-in path (`DualScreenActivity#getHinge`), and proving otherwise needs a real-device sign-in test that
   could not be run. Owner decision required (accept and document, publish a notice, or exclude after a device test).
3. **Real OneDrive/MSAL verification was not performed.** No Microsoft account exists in this environment and bypasses are
   forbidden, so sign-in, drive discovery, folder navigation, pagination and workbook download remain unverified for the
   release.
4. **The 60 fps measurement is an emulator measurement.** Taken on a 60 Hz virtual display with a host GPU; the software
   GPU reaches only ~33 fps, which is that renderer's limit rather than the app's. No physical phone was available, and
   refresh rates above 60 Hz could not be exercised (`mRefreshRateChangeable: false`).
5. **Presentation timestamps were not directly observable.** `dumpsys SurfaceFlinger --latency` returns no rows for the
   app layer on this Android 17 image, so "presented" is evidenced by HWUI's frame count at vsync cadence plus its jank
   percentage, not by per-buffer timestamps.
6. **Sustained windows were ~53 s, not hours.** Thermal throttling and long-run memory drift were not measured beyond the
   flat PSS observed during the runs.
7. **Light and dark app themes are indistinguishable in this app** (one navy palette), so both were exercised as *system*
   light mode (`night mode: no`) and *system* dark mode (`yes`).
8. **The compositor depends on this document's shape** — ghosts as `<symbol>` PNGs, Pacman as a single `<path>`, cells as
   `c-<col>-<row>` rects. `SmilTimeline.detect` returns null for anything else and the app falls back to the
   whole-document renderer: correct, but slow. No current asset exercises that fallback.
9. **`SmilAnimation.SMOOTH_FPS`/`hasContinuousMotion` and `AuthorImageDecoder.renderFrame` are now used only by tests and
   the fallback path**, not by playback. They were deliberately left in place (the still frame and the equivalence test
   depend on them) rather than deleted in a release-blocked commit.
10. **One pre-existing JVM test is flaky** (`WorkbookLibraryCrashRecoveryTest`): it failed once in three full runs and
    passes in isolation. It is unrelated to this task and was not "fixed" by loosening it, but a release would want it
    stabilised before the suite can be trusted as a gate.

## 13. Final release decision

**NOT READY — BLOCKED.**

Implementation and testing are complete, and the performance requirement is met with measurement rather than assertion:
the animation presents 59.3–59.6 frames per second on a 60 Hz display, 1.28–1.71 % janky, at 1.53 ms of CPU per frame
against a 16.7 ms budget, with zero frames while off screen and a picture that matches the previous renderer to within
1.9 % of its pixels. The full suites pass (1,385 JVM, 39 instrumented), the debug and release variants build, and the
changelog validates.

It is not a release. `app-release.apk` is signed with the Android debug certificate, `display-mask:0.3.0` is packaged
