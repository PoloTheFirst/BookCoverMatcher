## 1. Mission

Investigate and fix the application crash in BookCoverMatcher.

The application currently crashes during execution. The exact root cause and affected component must be established through repository inspection, crash reproduction where possible, Logcat analysis, code tracing and testing.

This is a bug-fix task, not a feature-development task.

Your responsibilities:

1. Inspect the current application and repository state.
2. Identify the crash location and root cause.
3. Trace the relevant execution path and dependencies.
4. Implement the smallest reliable fix.
5. Add regression tests where practical.
6. Run the relevant tests and build verification.
7. Update documentation and the development report.
8. Commit and push the fix to the correct branch.

Do not make speculative changes or broadly refactor unrelated components.

**Important: Keep the development version unchanged at `2.5.0-dev.2`. Do not create `2.5.0-dev.3` or another version.**

## 3. Crash investigation

Do not assume the crash is related to the most recently developed online-search or reverse-image functionality.

Investigate the entire relevant execution path.

### 3.1 Establish the failure

Inspect available evidence:

- Android Studio Logcat.
- `FATAL EXCEPTION`.
- Exception type.
- Exception message.
- Full stack trace.
- Nested `Caused by` exceptions.
- Crashing thread.
- Android lifecycle state.
- Relevant coroutine or background-task execution.
- Relevant application logs.
- Recent implementation changes and Git history.

If the user has supplied a crash log, treat it as primary evidence.

If no crash log is available:

1. Inspect the application for likely crash paths.
2. Attempt to reproduce the crash using the available environment.
3. Run the application and relevant tests where possible.
4. Inspect recent changes for regressions.
5. Identify suspicious code paths and explain the evidence supporting each hypothesis.

Do not claim that a crash has been reproduced if it has not.

### 3.2 Investigate likely failure categories

Check these categories where relevant:

**Application startup**
- Application initialization.
- Dependency initialization.
- ViewModel creation.
- Dependency injection or service registration.
- Persistent-data loading.
- Database initialization.
- Migration failures.
- Invalid application configuration.

**Jetpack Compose**
- Invalid state transitions.
- Incorrect state ownership.
- Lifecycle-related state access.
- Invalid navigation.
- Composable crashes.
- Invalid list keys.
- Null or invalid data assumptions.
- Recomposition-related side effects.

**Coroutines and concurrency**
- Unhandled coroutine exceptions.
- Incorrect dispatcher usage.
- Access to UI state from the wrong thread.
- Lifecycle cancellation problems.
- Race conditions.
- Stale asynchronous responses.
- Incorrect structured concurrency.
- Exceptions escaping background jobs.

**Image processing**
- CameraX lifecycle handling.
- Invalid image input.
- Bitmap allocation and decoding.
- Memory exhaustion.
- OCR initialization.
- ONNX Runtime initialization.
- OpenCLIP embedding execution.
- Image cache failures.

**Workbook and catalogue**
- Excel parsing.
- Embedded image extraction.
- Invalid workbook data.
- Missing catalogue fields.
- Persistence and serialization.
- Unexpected empty collections.
- Corrupt or incompatible saved data.

**Online search and reverse-image discovery**
- Provider initialization.
- SauceNAO configuration and API-key handling.
- IQDB slow-response and timeout handling.
- Network exceptions.
- Invalid response parsing.
- Cancellation.
- Result aggregation.
- Invalid URLs.
- Missing metadata.
- UI state updates after navigation.
- One provider failure propagating into unrelated functionality.

**Android platform compatibility**
- Manifest configuration.
- Permissions.
- File-provider configuration.
- Scoped storage.
- SDK compatibility.
- Android lifecycle and API-level differences.

These are investigation targets, not assumptions about the actual cause.

## 4. Root-cause analysis requirements

Before implementing the fix, establish:

1. The exact component responsible.
2. The specific failing operation.
3. The conditions under which the failure occurs.
4. Why the current implementation fails.
5. Whether the issue was introduced by recent changes.
6. Whether the issue affects other application workflows.
7. Whether there are related failure paths that need protection.

Trace the exception to the underlying defect rather than merely suppressing the visible error.

Examples of unacceptable superficial fixes:

- Catching every exception and ignoring it.
- Returning empty results whenever a provider fails.
- Disabling a feature to avoid a crash without justification.
- Adding arbitrary delays to hide a race condition.
- Replacing invalid values with hardcoded defaults without understanding their meaning.
- Swallowing coroutine exceptions.
- Adding broad null checks that conceal an invalid data contract.
- Disabling tests.
- Rewriting unrelated components.

If the evidence indicates multiple independent defects, document them separately and fix only those necessary to resolve the reported crash and prevent closely related regressions.

## 5. Implementation requirements

### 5.1 Minimal and targeted repair

Implement the smallest maintainable fix that addresses the verified root cause.

Requirements:

- Follow existing project architecture and conventions.
- Reuse existing models and abstractions.
- Preserve public interfaces unless a change is necessary.
- Preserve existing DLsite functionality.
- Preserve SauceNAO and IQDB functionality.
- Preserve provider isolation and error reporting.
- Preserve local OpenCLIP and OCR functionality.
- Preserve workbook parsing and embedded-image extraction.
- Preserve catalogue and wishlist persistence.
- Preserve profile isolation.
- Preserve offline functionality.

Do not use the crash fix as an excuse to redesign the application.

### 5.2 Error handling

Where the root cause requires improved error handling:

- Catch only appropriate exceptions.
- Preserve useful diagnostic information.
- Do not expose sensitive information.
- Keep provider failures isolated.
- Do not convert failures into false successful or empty results.
- Ensure cancellation behaves correctly.
- Keep UI state consistent after failures.
- Prevent uncaught background exceptions from crashing unrelated workflows.

### 5.3 Data safety

If the crash involves stored data, migrations or serialization:

- Inspect existing stored-data formats.
- Preserve backward compatibility.
- Do not delete or reset user data.
- Add a migration only when genuinely necessary.
- Test both existing and newly written data.
- Handle malformed records safely without silently destroying unrelated records.

## 6. Regression testing

Add or update deterministic tests for the actual root cause.

Depending on the affected component, cover:

- The original crash-triggering input or execution path.
- Normal successful execution.
- Null or missing optional values.
- Empty data.
- Invalid data.
- Failure and exception handling.
- Cancellation.
- Lifecycle transitions.
- Repeated execution.
- Relevant concurrency conditions.
- Backward compatibility if persistence is involved.

Do not add tests for unrelated hypothetical problems simply to increase test count.

If the crash is UI-specific and cannot be adequately covered by unit tests, use the most appropriate available Android instrumentation or UI test.

Do not weaken or remove existing tests to obtain a passing build.

Do not add live network dependencies to the default unit-test suite.

- The original functionality is preserved.

- Relevant unit tests pass.
- The debug build succeeds.
