## 2. October/November background defect

### Source investigation

- Original graph asset: `pacman-contribution-graph-dark.svg` (84,944 bytes), the `prefers-color-scheme: dark`
  `<source>` of the README's `<picture>`; also present as a test fixture at
  `app/src/test/resources/author/pacman-contribution-graph-dark.svg` and in `app/src/androidTest/assets/author/`.
- SVG dimensions: `width="1166" height="184"` — **and no `viewBox`**.
- Original viewBox: none. This is the root of both defects.
- Background element(s): a single root-level `<rect width="100%" height="100%" fill="#0d1117"/>`. Both lengths are
  **percentages**, so they are resolved against the viewport, not against the canvas.
- October region coordinates: month labels sit on the `y=10` baseline; `Oct` is at x=1044 and the trailing `Nov` at
  x=1132/1154 — i.e. the last ~166 units of the 1166-unit canvas.
- November region coordinates: the same trailing label plus the last ~6 column groups, x ≈ 1000…1164.
- SVG groups/styles affecting those regions: none. There are 4 `<g>` elements (the four ghosts, each carrying one
  `<animateTransform>`), 21 `<symbol>`/`<use>` sprite pairs, 53 `<animate attributeName="fill">` elements and no `<style>`
  or CSS classes. The right-hand area is drawn by exactly the same elements as the rest of the grid: nothing there is
  special except that it lies beyond x = 1000.
- Animation transformation affecting background: none. `SmilAnimation.frameDocument` rewrites animated attributes only
  and never touches the root tag or the background rectangle; the frames therefore inherit whatever the root says.
- Verified root cause: `rasteriseSvg` asks for a 1000-px-wide bitmap (`maxWidth`), i.e. `scale = min(2.625, 1000/1166)
  = 0.857`, and sets the document size to 1000 × 157. `AndroidSVG` resolves `100%` against that viewport, so the
  background painted **1000 × 157** of a canvas whose content spans **1166 × 184**. The 166 units on the right and the
  27 units at the bottom were never painted at all, leaving them transparent so the Author page's navy panel
  (`#062442`-ish) showed through. Mapping to the screen (image box x 74–1005, scale ≈ 0.8) predicts the background
  ending at x ≈ 889 px, which is exactly where the measured panel-navy pixels began.

### Fix implemented

- Background implementation: the background rectangle itself is left exactly as the generator wrote it. What changed is
  the document around it: new `core/author/SvgCanvas.kt` gives the root the `viewBox` it was missing, so `100%` finally
  means "the whole canvas". Nothing is recoloured, no Compose overlay was added, and no month-specific patch exists.
- Coordinate bounds: `viewBox="0 0 1166 168"` — the generator's width unchanged, the height trimmed from the declared
  184 to the drawing's own bottom (the last cell ends at y=167) plus one unit of margin. The declared
  `height="184"` is rewritten to `height="168"` in the same pass, because a 168-unit box inside a 184-unit document
  would be letterboxed and would put an empty transparent band back exactly where the surplus row was removed.
- How full-canvas coverage is guaranteed: a document that already has a `viewBox` is returned unchanged (identity); one
  that declares numeric `width`/`height` and no `viewBox` gets `viewBox="0 0 width height"`, which is the reference box
  percentages resolve against. The decoder additionally no longer scales the canvas itself when a `viewBox` is
  present — the renderer maps the box onto the bitmap — so nothing is scaled twice.
- How background is kept behind content: the rectangle is the first child of the root, and no z-order, `<use>` or
  sprite is reordered, so it stays behind every cell, label and sprite.
- How generated animation frames retain the background: `SvgCanvas.normalise` runs once, before `SmilAnimation.detect`,
  and `frameDocument` only rewrites animated attributes; the root tag (and therefore the `viewBox` and the background)
  is present in every frame. A JVM test asserts the `viewBox` and `fill="#0d1117"` in the document and in frames at
  0 ms, half the loop and the last millisecond.
- How light/dark Android app themes are handled: the app has a single navy palette (it does not follow the system
  theme), and the graph uses the generator's own dark variant chosen by `MarkdownParser`, so the picture is dark in
  both. Verified with the system in **light** mode (night mode: no): the canvas is painted in every band and the panel
  never shows.
- Confirmation global app theme was not changed: no theme, palette, `Theme.kt` or `MaterialTheme` file was touched.

## 3. Redundant bottom row

### Source investigation

- Original SVG grid row count: **7** — the correct number of weekdays. Distinct cell `y` values: 15, 37, 59, 81, 103,
  125, 147 (pitch 22, cell height 20).
- Original row coordinates: row *n* occupies y = 15 + 22n to 35 + 22n, so the grid spans y = 15…167. The month labels
  sit on the `y=10` baseline above it.
- Original bottom row contents: 53 real cells (`c-0-6` … `c-52-6`), exactly like every other row — 371 cells in total
  (53 columns × 7 rows), all present. Nothing about the last row is empty or synthetic in the source.
- Last valid contribution row: row 6, y 147…167, drawn and animated like the others (the pacman and the four ghosts
  walk it: every `translate` in the document has y ∈ [15, 147], so sprites occupy up to y=167).
- Original viewBox: none; declared canvas `height="184"`.
- Whether surplus row existed in source or was introduced during transformation: **neither row was ever a heat-map
  row.** The source has 7 rows and the transformation never adds one. What existed was 17 units of *empty canvas*
  below the grid (184 − 167) plus 10 more units that the background failed to paint (the percentage rect stopped at
  y=157), i.e. a 27-unit full-width strip of the page's navy panel immediately under the last row.
- Verified root cause: that strip. A uniform, full-width, panel-coloured band exactly one row high, sitting directly
  beneath the last row, is what reads as "an unnecessary extra heat-map row"; it is the same missing-`viewBox`
  defect as §2, measured at `y=1743…1758` on the before screenshot (`(6,36,66)` where the canvas should be).

### Fix implemented

- Exact correction: the canvas is trimmed to the drawing's own bounds — `viewBox="0 0 1166 168"` with the declared
  `height` rewritten to 168 — and the background now covers all of it. The bottom is derived from the geometry
  (maximum `y + height` over every `<rect>`, and every `<text>` baseline), never from a hard-coded number.
- Source or transformation layer modified: the transformation layer, in one place (`SvgCanvas.normalise`, called by
  `AuthorImageDecoder.decode`). The asset, the cells and the animation are untouched; both the dark and the light
  variant are corrected identically because only their palette differs.
- Original row count: 7 (371 cells).
- Resulting row count: **7** (371 cells) — unchanged, asserted on the real asset.
- Last valid row preserved: yes; its bottom edge (y=167) is inside the new box with one unit to spare.
- Valid contribution cells preserved: all 371; the transformation replaces only the root tag, so no cell, coordinate,
  `fill` or `<animate>` is rewritten.
- New viewBox/bounds: `0 0 1166 168` (was: no viewBox, 1166 × 184).
- Clipping/mask/transform changes: none. The document contains no `clipPath`, no `mask` and no root transform; the four
  `<g>` transforms belong to the ghosts and are untouched.
- Pacman alignment preserved: the grid, the sprite translations and the animation timeline are byte-identical, so
  pacman still walks the same cells; the box is 1 unit taller than the lowest sprite pixel (167), so nothing is cut.

## 8. Remaining limitations

- **Emulator, not hardware.** Everything was verified on `Medium_Phone_API_37.0` with a software GPU. The defect was
  geometric (a document size and a viewBox), so it is not GPU-dependent — but it was not re-measured on a phone.
- **One density.** 2.625× was used, the same as crash-fix 3. The bitmap width cap (1000 px) is what shrinks the
  viewport below the canvas, so a display whose target scale is at or below 1000/1166 = 0.857 would have hidden the
  symptom rather than fixed it; at every density the new `viewBox` makes the result correct.
- **The trim trusts the source's own bounds.** `SvgCanvas.normalise` trims to the lowest `<rect>` bottom or `<text>`
  baseline. If a future generator draws, or animates a sprite, below that point, the strip it needs would be cut. The
  rule also requires a numeric `width`/`height` and no `viewBox`; anything else is returned unchanged, which means such
  a document keeps today's behaviour rather than being guessed at.
- **Light/dark app themes are indistinguishable in this app.** The Author page uses one navy palette and does not
  follow the system theme, so "app light mode" was exercised as *system* light mode (night mode `no`). The graph is
  dark in both because the README's dark `<source>` is chosen by the parser, not by the theme.
- **Three pixels** at one instant of the loop fall within my tolerance of the panel colour; they are sprite
  antialiasing, which is why the assertion is a bound. A stricter zero would be a false test.
- **Playback** was exercised for tens of seconds at a time, not for the full 29.4 s loop repeatedly, and the frame rate
  itself (crash-fix 3's 15.6 fps) was not re-measured — only that frames change (466 samples in 700 ms).
- **The `<picture>` preference** still assumes the repository keeps publishing `pacman-contribution-graph-dark.svg`; a
  repo that stops doing so falls back to the light graph, as documented in crash-fix 3.

## 9. Final assessment

**PASS.**

Both reported defects are fixed and verified on a running device, and they turned out to be the same defect: a
percentage-sized background inside a document that declared no `viewBox`, so `100%` meant the shrunken viewport rather
than the canvas. October and November now sit on the generator's `#0d1117` canvas like every other month (`x 890–989:
98 canvas pixels, 0 navy`, and 0 navy in every band), the empty strip under the last row is gone (the picture is 1166 ×
168 instead of 1166 × 184), and nothing was removed from the heat map: 7 weekday rows and 371 cells before and after,
asserted on the real asset and counted again in the rendered picture.

No earlier fix regressed: icons are still crisp, badges still grouped, `💻` still rendered, the graph still animates
(and still pauses off-screen), and neither the animation timeline nor the layout rules were touched. The full suites
pass (1,385 JVM / 33 instrumented, 0 failures), the build is clean, and the changelog validator passes.

What keeps this from being "verified everywhere": emulator only, one density, one app palette, and the trim's
dependency on the source's own drawing bounds — all listed in §8.
