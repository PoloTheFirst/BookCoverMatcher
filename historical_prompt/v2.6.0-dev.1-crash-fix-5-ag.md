## 4 · Actual Graph endpoints, and what the live service says

**Inspected** `core/remote/GraphUrls.kt` — the only place that builds a Graph URL:

| Purpose | Endpoint the app actually calls |
|---|---|
| root listing | `GET https://graph.microsoft.com/v1.0/me/drive/root/children?$select=id,name,folder,file,size,eTag,cTag,lastModifiedDateTime,parentReference&$top=200` |
| child listing | `GET …/v1.0/me/drive/items/{percent-encoded id}/children?…same…` |
| probe | `GET …/v1.0/me/drive/items/{id}?…same…` |
| download | `GET …/v1.0/me/drive/items/{id}/content` — 302 followed **without** a token |

There is **no** `/me`, `/me/drive` or `/me/drive/root` call: the app addresses the root through
`/me/drive/root/children`, exactly what Microsoft documents for "list children in the root of the current user's
drive".

### 4.1 Live evidence for the exact request

**Executed** from the build machine, no credentials involved: the app's own root-children URL with a deliberately
invalid bearer token.

```
HTTP=401
{"error":{"code":"InvalidAuthenticationToken","message":"Protocol 'Bearer' failed to validate because the token
  could not be read.","innerError":{"date":"…","request-id":"…","client-request-id":"…"}}}
```

A malformed `$select`, an unsupported `$top` or a wrong path answers **400 `invalidRequest`**, not this — so the
URL, the query and every property name are accepted by the real service. **Inspected** against Microsoft's
documentation: `GET /me/drive/root/children` supports `$select`/`$top` (default page size 200); `folder`, `file`,
`size`, `eTag`, `cTag`, `lastModifiedDateTime`, `id`, `name` and `parentReference` are all driveItem/baseItem
properties; `Files.Read` is the least-privileged delegated permission for this call on a personal account. One

## 7 · Root cause

**Unconfirmed.** No account exists in this environment, so the user's own failure could not be reproduced: I
cannot make MSAL return a result and I cannot make Graph answer an authenticated request. Saying otherwise would
be invention.

What this run did establish:

1. **The repository's part of folder access is correct as far as it can be checked** — endpoints, query, property
   names, id encoding, folder/file classification, pagination, error classification, empty-vs-failed UI state.
   The request is accepted by the live service (§4.1).
2. **A real defect that produces the user's symptom with no error message: the panel could wait forever.** MSAL
   only answers through `BrowserTabActivity`; when the browser never redirects (a redirect mismatch, an error
   page, a tab left open), `signIn` awaited a callback that could not arrive, `signingIn` stayed true and the
   panel showed a spinner with a disabled button and no message. "I cannot access any OneDrive folder" is exactly
   what that looks like. **Fixed** (§8.1).
