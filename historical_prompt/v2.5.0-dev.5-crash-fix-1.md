# 3. Phase A — Establish the Actual APK Artifact

Before changing code, identify exactly which APK failed to install.

## 3.1 Build artifact identification

Inspect the output of the actual Gradle build.

Identify:

- APK filename.
- Exact filesystem path.
- Build variant.
- Application ID.
- Version name.
- Version code.
- APK file size.
- APK SHA-256 checksum.
- Build timestamp.
- Signing configuration.

Do not use an old APK from a previous build.

Do not assume that an APK located in an output directory is the one that was installed.

If multiple APKs exist, identify their differences.

## 3.2 APK integrity

Verify the generated APK as a ZIP archive.

Check:

- Archive integrity.
- Required APK entries.
- `AndroidManifest.xml`.
- `resources.arsc`.
- `classes.dex` files.
- Native library entries, if any.
- Unexpected missing or zero-length entries.

Use appropriate Android SDK tooling, such as `apkanalyzer`, `aapt`/`aapt2`, or equivalent tools already installed in the environment.

Do not modify the APK manually as a substitute for fixing the Gradle packaging process.

## 3.3 Manifest verification

Inspect the final packaged manifest, not only the source manifest.

Verify:

- Application ID.
- `minSdkVersion`.
- `targetSdkVersion`.
- Package name.
- Required permissions.
- Activity declarations.
- Manifest-merger output.
- Native-library-related declarations, if applicable.
- Any malformed or conflicting manifest entries.

Check whether the generated manifest is compatible with the target Android version.

Do not arbitrarily lower `minSdkVersion` or change `targetSdkVersion` merely to suppress the error.

Any SDK change must be justified by actual compatibility requirements.

# 4. Phase B — Diagnose the Installation Failure

Investigate the following categories systematically.

## 4.1 APK corruption or incomplete artifact

Determine whether:

- The APK was generated incompletely.
- The APK was truncated during copying or downloading.
- The installed artifact differs from the Gradle output.
- The file extension does not match the artifact format.
- The APK is actually a split/base APK that requires additional APK files.
- The APK was incorrectly repackaged or modified after signing.

If the artifact is corrupted, identify where corruption occurred and correct the artifact-generation or transfer process.

## 4.2 Signing configuration

Inspect the APK signing configuration and verify the generated APK with Android SDK signing tools.

Check:

- APK signature validity.
- Signing scheme.
- Certificate consistency.
- Debug/release signing configuration.
- Whether the APK was modified after signing.
- Whether an existing installation uses a conflicting signing certificate.

Use `apksigner verify` with verbose output and certificate information.

Do not disable signing verification or introduce insecure signing practices.

If the issue is an existing installation signed with a different key, distinguish that problem from APK parsing failure and report the appropriate installation error.

## 4.3 Android version compatibility

Identify the actual target device's Android version and API level.

Compare it against the packaged manifest's minimum and target SDK values.

Check whether the device supports the APK's required features.

Do not assume the Android version from the Gradle build configuration.

If no connected device is available, inspect the available device information and explicitly report that installation compatibility could not be verified.

## 4.4 ABI and native library compatibility

Inspect every native library packaged in the APK.

Check:

- ABI directory names.
- ELF architecture.
- Native library validity.
- Required shared-library dependencies.
- Android API compatibility.
- Whether the device ABI is supported.
- Whether native libraries are packaged in the correct location.

The previous report states that `libbc_ocr.so` was built for:

- `x86_64`
- `arm64-v8a`

with API 26.

However, the report also states that `app/` was untouched and does not establish that this library was packaged into the APK.

Verify the actual APK rather than assuming it contains the Rust library.

**Important distinction:** An unsupported or missing native ABI commonly causes an installation or runtime-loading problem of a different kind. Do not automatically classify every ABI issue as the cause of Android's package-parsing message.

Do not add unnecessary native libraries or ONNX Runtime copies.

Preserve the existing ONNX Runtime 1.20.0 arrangement.

## 4.5 Android package format

Determine whether the intended artifact is:

- A standalone APK.
- A universal APK.
- An ABI-specific APK.
- A split APK.
- An APK generated from an Android App Bundle.

Do not install only a base APK if the generated package requires additional splits.

For this workflow, prefer a directly installable debug APK unless the project intentionally uses a different distribution format.

Do not change the application distribution format without a clear reason.

## 4.6 Gradle and Android Gradle Plugin

Inspect:

- Android Gradle Plugin version.
- Gradle wrapper version.
- Kotlin plugin version.
- Android Build Tools version.
- SDK configuration.
- NDK configuration.
- Packaging options.
- Manifest-merger output.
- AAPT2 resource processing output.

The previous report mentions that an offline build failed because an uncached AAPT2 version was required by the user's uncommitted AGP configuration.

Do not revert or replace that configuration without authorization.

Distinguish the offline dependency-resolution issue from the APK installation issue.

If the online build succeeds, preserve that fact and investigate the generated APK independently.

# 5. Phase C — Reproduce the Failure

A fix is not complete until the failure is reproduced or its cause is established through sufficient artifact evidence.

## 5.1 Device installation test

If an Android device or emulator is connected:

1. Identify its Android version and ABI.
2. Identify the exact APK being installed.
3. Record the APK checksum.
4. Run the installation using Android Debug Bridge.
5. Capture the complete command output and exit status.
6. Capture relevant PackageManager/logcat output if installation fails.

Use the equivalent of:

```powershell
adb devices -l
adb install -r "path\to\BookCoverMatcher.apk"
```

If the install fails, capture detailed diagnostics rather than relying solely on the generic Android popup.

Use `adb logcat` and PackageManager diagnostics to identify the actual parser or installation error.

Do not claim the installation succeeded simply because the command was executed.

## 5.2 Compare artifacts

If an older working APK is available, compare it with the failing APK.

Inspect:

- Manifest.
- Signing information.
- Application ID.
- SDK requirements.
- APK structure.
- Native library contents.
- Resource table.
- DEX files.
- Build variant.

Identify the exact difference that explains the failure.

Do not introduce unrelated changes based on speculative comparisons.

## 5.3 If the original failure cannot be reproduced

If no target device, original APK or sufficient diagnostic output is available:

- Inspect the latest generated APK thoroughly.
- Perform all available structural and signing checks.
- Build a fresh APK.
- Attempt installation on an available compatible emulator/device.
- Clearly state what remains unverified.

Do not invent an installation failure cause.

If additional information is essential, ask the user for the original failing APK and the device's Android version/API level, along with the exact installation method.

Do not mark the issue as fixed without sufficient evidence.

# 6. Phase D — Apply the Smallest Correct Fix

Once the cause is established:

1. Identify the specific faulty configuration or build step.
2. Make the smallest change that resolves the issue.
3. Preserve the existing project architecture.
4. Preserve existing user modifications.
5. Avoid changing unrelated dependencies.
6. Avoid modifying OCR functionality unless the evidence directly identifies it as the cause.
7. Keep the app's existing Python/Chaquopy OCR workflow intact.
8. Do not attempt to implement the unfinished Rust OCR engine as part of this corrective task.

If the issue is caused by:

- **APK corruption:** Fix the generation, copying or distribution process.
- **Manifest incompatibility:** Correct the relevant manifest or SDK configuration.
- **Signing:** Correct the signing configuration while preserving expected debug/release behavior.
- **ABI packaging:** Correct ABI filtering or native-library packaging.
- **Split APK confusion:** Generate and use the correct installable artifact.
- **Resource packaging:** Correct the actual AAPT2/resource configuration issue.
- **Gradle configuration:** Correct only the setting proven to cause the problem.

Do not make multiple speculative changes simultaneously.
