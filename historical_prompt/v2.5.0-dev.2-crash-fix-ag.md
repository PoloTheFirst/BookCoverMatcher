## 3. Root cause

| Item | Value |
|---|---|
| Component | `OnlineSearchController` (`app/src/main/java/com/bookcovermatcher/online/OnlineSearchController.kt`) |
| Exact cause | **Kotlin property-initializer order.** `_ui = MutableStateFlow(OnlineSearchUi(… reverse = ReverseImageUi(providers = reverseProviderRows() …)))` runs during construction. `reverseProviderRows()` read `reverseRuns[source.id]`, but `private val reverseRuns = LinkedHashMap<String, ReverseImageRun>()` was **declared after `_ui`**, so the JVM field was still `null` when the initializer ran. |
| Why the compiler allowed it | The read happens inside an instance *method*, so there is no definite-assignment check across methods; the declared type is non-null while the unassigned JVM field is `null`. |
| Why the tests missed it | No unit test constructs `OnlineSearchController` (it needs a `Context`); compilation cannot observe runtime field state. |
| Introduced by recent changes? | **Yes** — commit `a73e814` (v2.5.0-dev.2). The dev.1 controller had no initializer reading a later-declared field. |
| Impact | **100 % of launches**: the app could not start, so every feature was unreachable — not only the new one. |

## 4. Investigation

Path traced, in the order the JVM takes it:

1. `MainActivity.onCreate` → Compose content → `viewModel()` → `ViewModelProvider.AndroidViewModelFactory.create`
   → `MainViewModel.<init>`.
2. `MainViewModel` property `online = OnlineSearchController(app, viewModelScope, onMessage = ::showToast)`
   (line 110).
3. Constructor defaults (`sauceNaoKey`, `decisionStore`, `reverseSources`) are built, then class-body initializers
   run **top to bottom**.
4. `_ui` (pre-fix line 124) → `OnlineSearchUi(providers = providerStatuses(...), reverse =
   ReverseImageUi(providers = reverseProviderRows(), …))` (line 134).
5. `reverseProviderRows()` → `reverseRuns[source.id]` → field not yet assigned → **NPE**.

Files inspected: `OnlineSearchController.kt`, `MainViewModel.kt`, `OnlineSearchUi.kt`, `ui/OnlineSearchPanel.kt`,
`ui/ReverseImagePanel.kt`, `online/SauceNaoReverseImageSource.kt`, `online/IqdbReverseImageSource.kt`,
`data/SauceNaoKeyStore.kt`, `data/CandidateDecisionStore.kt`, `core/online/reverse/*`, `AndroidManifest.xml`,
`app/build.gradle.kts`.

**Other initialization-order hazards checked (all clean):**

| Field / call | Depends on | Verdict |
|---|---|---|
| `_ui` → `prefs.*` | constructor parameter | safe |
| `_ui` → `providerStatuses(...)` | constructor parameter `prefs` (its `secondaryOn` default) | safe |
| `_ui` → `sauceNaoKey.hint()` | constructor parameter | safe |
| `_ui` → `reverseProviderRows()` | **`reverseRuns`** | **the defect** (now takes an explicit map) |
| `decisions` initializer → `decisionStore` | constructor parameter | safe |
| `reverseRunner` → `reverseSources` | constructor parameter | safe |

No other defect was found in the launch path.

## 5. Fix implementation

| File | Change |
|---|---|
| `online/OnlineSearchController.kt` | reverse-image state block (`reverseRunner`, `reverseRuns`, `reverseJob`, `reverseCancelled`, `reverseGeneration`, `searchCandidates`, `manualCandidates`) moved **above** `_ui` with a comment stating the declaration-order rule; `_ui` now calls `reverseProviderRows(runs = emptyMap())`; `reverseProviderRows(runs: Map<String, ReverseImageRun> = reverseRuns)` is a one-line delegation; the inline row building and `defaultDetailFor` left the controller |
| `online/ReverseProviderRows.kt` (new) | `object ReverseProviderRows { fun of(sources, runs): List<ReverseImageProviderUi>; fun detailFor(providerId, state): String }` — plain Kotlin, no `android.*`, everything passed as a parameter |
| `app/src/test/java/com/bookcovermatcher/online/ReverseProviderRowsTest.kt` (new) | 5 regression tests (§6) |

**Why this fixes the root cause rather than the symptom**

* The NPE came from *reading uninitialised instance state during construction*. The builder no longer has instance
  state to read: the map and the source list are parameters, and the initializer passes an explicit `emptyMap()`.
  Nothing can be `null` there any more.
* The declaration order was corrected as well, so the data the initializer depends on exists first, and a comment
  records why that order must not be "tidied up".
* No exception is caught and no error is swallowed; the invalid access itself is gone.

**Why unrelated functionality was not touched:** the defect was entirely inside one constructor. DLsite, SauceNAO
and IQDB adapters, the runner/aggregator, storage, OCR, OpenCLIP, workbook parsing, catalogue matching, wishlist
persistence and profile isolation are unchanged; the row builder moved with identical output.


## 6. Regression tests

New file `app/src/test/java/com/bookcovermatcher/online/ReverseProviderRowsTest.kt` (JUnit 4, deterministic, no
device, no network). It tests the **exact call the constructor makes**, with fake providers:

| Test | What it pins |
|---|---|
| `building the rows from an empty run map does not throw and yields both providers` | the failing path itself: `of(sources, emptyMap())` returns both rows in priority order (1 SauceNAO, 2 IQDB) with their readiness states, details, `manualOnly` flags, zero results and no quota |
| `a missing SauceNAO key is drawn as needing a key, not as ready` | `NOT_CONFIGURED` resting state and its explanation |
| `the input order does not decide the display order` | rows are sorted by provider priority, not list order |
| `a finished run overrides readiness and its own numbers are shown` | a `SUCCESS` run wins over readiness, its hit count and the provider's own quota line are shown, and the untouched provider keeps its resting state |
| `a failure's own message is shown verbatim instead of a resting explanation` | a `TIMEOUT` row shows the provider's message and no result count |

Existing tests were neither weakened nor removed; the suite grew from 869 to **874** tests.

Additional manual (runtime) checks against the original failure scenario are recorded in §8.
