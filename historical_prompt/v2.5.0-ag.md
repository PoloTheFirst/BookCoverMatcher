## 3 · Cache-clear text: root cause and fix

**Symptom.** *More → Clear online session cache* showed
`Session cache cleared â€" saved bookmarks and wishlist items are untouched.`

**Root cause.** Not a resource-encoding problem and not a `strings.xml` entry: the sentence was a
literal in `OnlineSearchController.kt`, and the *file itself* carried the damage. At some point the
Kotlin sources were read as Windows-1252 and written back as UTF-8, so U+2014 (UTF-8 `E2 80 94`)
became three characters (`â`, `€`, `”`). The compiler and the toast faithfully reproduced those three
characters — no runtime transcoding was involved, which is why a cosmetic fix elsewhere could not work.

**Fix.** The damaged byte sequences were reversed exactly (`encode(cp1252).decode(utf8)`, iterated for
the doubly-encoded runs) across the packaged sources and `ONLINE_SEARCH.md`: **109 lines in 4 files**
(`OnlineSearchController.kt` 21, `WorkbookCommentsUi.kt` 28, `DlsiteResponseParser.kt` 9+3,
`ONLINE_SEARCH.md` 42 lines). The sentence now lives in one place:

```kotlin
object SessionCacheMessages {
    const val CLEARED = "Session cache cleared \u2014 saved bookmarks and wishlist items are untouched."
}
```

**Exact final text** (one em dash, U+2014):

```
Session cache cleared — saved bookmarks and wishlist items are untouched.
```

**Regression guard.** `SessionCacheMessageTest` (5 tests) pins the sentence, asserts the em dash is a
single U+2014, refuses every character of the old damage, and scans the packaged sources for the
`â€` double-encoding signature so it cannot quietly return. `thePackagedSourcesCarryNoDoubleEncodedUtf8`
found two of my own new files still carrying the signature during this work and they were cleaned
before the release, which is exactly what the check is for.

## 4 · Original result-profile image: root cause

Traced end to end: camera (`applyCapture` ← `captureManual` / Auto Scan) and gallery
(`onImagePicked` → `decodePhoto(bytes, Config.MAX_IMAGE_DECODE)`) both reach
`MainViewModel.applyCapture(image: PixelImage, …)`, which built a **224-pixel thumbnail**
(`codec.makeThumbJpeg`, `Config.THUMB_SCAN_W/H`) for `TargetUi.thumbJpeg` and, for the online tab, an
OCR JPEG at `OCR_MAX_EDGE` (1280) that the controller keeps in memory only.

The save path then did this:

```kotlin
pickerScanThumb = if (mode == PickerMode.SAVE_SESSION) _ui.value.target?.thumbJpeg else null
```

so (a) a **result profile** (`SAVE_RESULT_PROFILE`) stored **no image at all**, and (b) an offline
session stored the 224-pixel thumbnail. `SearchSession` had a single image field (`scanThumbName`, in
`thumbs/`), used by the folder/session rows. `SessionDetailScreen` — the profile opened inside its
folder — rendered no image at all. The originals were therefore never persisted: they existed only as
decoded pixels during the capture.

## 5 · What is saved now (camera and upload alike)

`applyCapture` encodes the **same decoded pixels at their own resolution**:

```kotlin
val original = codec.encodeJpeg(image, maxOf(image.width, image.height), AndroidImageCodec.ORIGINAL_QUALITY)
…
lastOriginalJpeg = original          // assigned together with TargetUi, so image and cover always match
```

* quality `ORIGINAL_QUALITY = 92` (the OCR copy uses 84, the row thumbnail 72);
* `maxEdge` is the picture's own long edge, so nothing is downscaled here — the only transformation is
  JPEG encoding;
* a picked photo is bounded by `Config.MAX_IMAGE_DECODE` before it reaches this point, and a camera
  frame by the frame size. **Honest limitation:** the pipeline holds decoded pixels, not the camera's
  own file, so a saved original is a re-encoded JPEG of those pixels, not the untouched original file;
* an encoding failure sets `lastOriginalJpeg = null` and never breaks the capture.

`openPicker`-equivalent (`showPicker`) now passes it for **both** save modes
(`SAVE_SESSION` and `SAVE_RESULT_PROFILE`), and `closePicker`/`confirmPicker` clear it so a profile can
never inherit another cover's picture.

## 6 · Storage and session association

* `originals/` is a sibling of `thumbs/`, one file per profile: `<sessionId>_original.jpg`.
* `SearchSession.originalImageName: String?` is a **separate** reference from
  `scanThumbName`; `SessionDraft.originalJpeg: ByteArray?` carries the bytes into one write.
* `WishlistRepository.saveSession` writes the original **before** `records.json`:
  ```kotlin
  originalImageName = draft.originalJpeg?.let { writeOriginal("${sessionId}_original.jpg", it) },
  ```
* `writeOriginal` is atomic: `name.tmp` → delete target if present → `renameTo`. A failure throws
  `IOException` before the record is written, so no record can point at a file that is not there.
* The JSON gains `"originalImage"` next to `"scanThumb"`, and decode reads it as a nullable string.
* Move (`moveSession`, `withFolder`), rename (`renameSession`) and every copy/legacy path carry the
  field through unchanged, so an association survives navigation and renames.
* Folder **copy** duplicates the bytes under a new name (`copyOriginal`), never shares one file: two
  profiles can neither overwrite nor delete each other's picture.

## 7 · Display placement

`buildSessionDetail` resolves the file (`wishlist.originalFile(name).takeIf { it.isFile }`) into
`SessionDetailUi.original`, and `SessionDetailScreen` draws `ProfileOriginalImage(detail.original, …)`
**after the header, kind/query chips and metadata line, and before the results list** — i.e. at the top
of the opened profile, above the saved entries:

* `ContentScale.Fit` with `fillMaxWidth()` and `heightIn(max = 240.dp)`: aspect ratio preserved, never
  cropped into a tile, and a tall cover cannot push the results off the screen;
* tapping it opens the same picture in a full-size `Dialog` (tap to dismiss);
* `FileImage` gained a `contentScale` parameter (default `ContentScale.Crop`, unchanged for rows), so
  the folder and session rows keep their existing thumbnails;
* the picture appears once — the profile screen does not repeat it in a tile — and the screen renders
  one image only.

## 8 · Legacy records and cleanup

* `originalImageName` is nullable and defaults to `null`; a record written before v2.5.0 simply has no
  `"originalImage"` key, decodes to `null`, and the profile screen shows
  *"No original image was saved with this profile."* rather than substituting the thumbnail (a thumbnail
  is never promoted to an original).
* `removeSessionImages(session)` deletes the row thumbnail **and** the original, and is called from
  `deleteSession`, `deleteFolder`/`deleteFolders` (via `commit`) and the "all results were duplicates"
  rollback in `saveSession`. Items shared with other sessions/folders are untouched, so a file is only
  removed with the record that owns it.
* A copy owns its own file, so deleting the source folder leaves the copy's picture intact (tested).

   file — the pipeline never holds that file.
2. A picked photo is bounded by `Config.MAX_IMAGE_DECODE`.
3. Profiles saved before v2.5.0 have no original image and cannot get one retroactively; the detail view
   says so instead of promoting a thumbnail.
4. The universal release APK is ~316 MiB because the PP-OCRv6 models live inside it (unchanged policy).
