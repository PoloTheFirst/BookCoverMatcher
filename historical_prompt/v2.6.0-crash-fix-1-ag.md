## 2. Screenshot validity and inspection result

`BookCoverMatcher-QA/phase9-evidence/author-expanded-1.png`, reported at 1 384 316 bytes, exists at exactly
**1 384 316 bytes**. It is **not a PNG**:

```
first bytes: FF FE FD FF 50 00 4E 00 47 00 0D 00 0A 00 1A 00 ...
              BOM   U+FFFD  P     N     G     CR    LF    SUB
```

* `FF FE` is a **UTF-16LE byte-order mark**; every subsequent ASCII byte is followed by `00`, which is UTF-16 for
  the same character.
* The PNG signature should start `89 50 4E 47`. The `89` arrived as `FD FF` = **U+FFFD**, the replacement character
  a lossy text conversion writes when it cannot decode a byte.
* Decoding the file as UTF-16LE yields 692 158 code units beginning `PNG\r\n\u001a\r\n` followed by a complete
  `IHDR` chunk whose width and height words are **1080 × 2400** — a full device screenshot, intact apart from that
  one byte.

So the capture was correct and the *file* was mangled afterwards. The mechanism was then reproduced on purpose:
`adb exec-out screencap -p > shot.png` in PowerShell writes the binary stream through a text encoder and produces
exactly this corruption (`FF FE FD FF 50 00 4E 00 …`, and `System.Drawing` then reports "Out of memory" because it
is not an image). This is the same class of mistake that made the Cline image ingestion fail: **the evidence file
was broken, not the app.**

Every screenshot in this report was instead taken through the device filesystem
(`adb shell screencap -p /sdcard/x.png` then `adb pull`), and each one was validated by its `89 50 4E 47` signature
before use. Those captures are `BookCoverMatcher-QA/phase9-evidence/author-live-1.png`,
`author-live-2.png`, `pacman-frame-a.png`, `pacman-frame-b.png`.

## 4. Root cause and exact fix

Three defects were real, and each had a different cause.

1. **Badge sizing — a sizing rule that did not distinguish a badge from a photograph.**
   `MarkdownView.OtherBlock` drew *every* `MdBlock.Image` as
   `Modifier.fillMaxWidth().aspectRatio(decodedRatio)` with `ContentScale.FillWidth`. The banner (3840×2160) and the
   graph (1166×184) want that. A Shields.io badge is about 100×20, so the same rule reserved ~932 px of height 186 px
   — and, because the README lists thirteen badges, thirteen such bands, ~2 400 px of page before the contribution
   graph. Measured on the device before the fix: the *My Contribution Graph* heading sat far below the fold; after
   it, at y ≈ 1 544 in the same scroll state.
   **Fix:** `AuthorImageSizing` (new, pure Kotlin) is the single rule for the box. Badges get
   `height = 20.dp`, `width = min(20 dp × own aspect, 60 % of the row)`; everything else keeps the row width and its
   own ratio (bounded to 3× the width for absurdly tall inputs). `MdImageGrouping` (new, pure) collects consecutive
   badges so they wrap into a row instead of one row each, and `MarkdownView` draws them with `ContentScale.Fit` —
   so the box already has the badge's shape and the bitmap can never be distorted.

2. **Emoji — the renderer had no shortcode vocabulary.**
   `Inline.flush()` emitted prose verbatim. **Fix:** `EmojiShortcodes.expand` is applied to prose runs only, inside
   `Inline.flush()`, and only when the run has no URL. A curated `:name:` → emoji table replaces recognised names,
   leaves unknown ones verbatim, and cannot touch a code span (built without passing through the buffer), a fenced
   block (never reaches the inline parser) or a link target (`url != null`).

3. **Frozen graph — `AndroidSVG` ignores SMIL, and the code documented that as permanent.**
   The old `decodeSvg` parsed the document once and rendered it; its comment claimed the graph is
   "SMIL-animated … rendered as a still picture … a real platform limitation". A successful parse was being treated
   as support for the format's semantics.
   **Fix:** `SmilAnimation` (new, pure Kotlin) reads the document's own timeline — `dur`, `keyTimes`, `values`,
   `attributeName`, `<frameRate>` — and produces the still document for a requested instant by rewriting the
   animated attributes and deleting the animation children. `AuthorImageDecoder.renderFrame` rasterises that
   document, and `MarkdownView.AnimatedSvgPicture` swaps the picture at the declared rate. No WebView (the project
   documents that it renders no third-party pages), no script, no extracted GIF, no invented tweening: the frames
   are the source document at the times the source itself declares.

Nothing was removed, hidden or replaced with a screenshot, and the source README was not edited.

## 8. Pacman source format and animation implementation

Evidence gathered before writing any code:

* `https://raw.githubusercontent.com/PoloTheFirst/PoloTheFirst/output/pacman-contribution-graph.svg` →
  **200**, `Content-Type: image/svg+xml`, **85 444 bytes**.
* Root element `<svg width="1166" height="184">`; `<metadata><info><frames>147</frames><frameRate>5</frameRate>
  <durationMs>29400</durationMs></info></metadata>` — a **29.4 s loop at 5 fps**.
* Animation elements: **54 `<animate attributeName="fill" dur="29400ms" repeatCount="indefinite" keyTimes="…"
  values="…">`** on day-cell `<rect>`s, the same on the `#pacman` path (yellow/red mouth), and **6
  `<animateTransform>`** — one `type="translate"` carrying 147 positions over the loop, one `type="rotate"` carrying
  the facing angles, the rest on the ghost sprites. All SMIL: no CSS `@keyframes`, no explicit frame list.
* The ghosts are 21 base64 PNGs embedded as `<image href="data:image/png;base64,…">` inside `<symbol>`/`<use>`.
* `result_profile.svg` contains none of this (§10), so it was not used as a source of information.

Implementation: `SmilAnimation` (new, pure Kotlin, no Android type in it) parses the document once with a stack-based
tag scanner (skipping comments, CDATA and processing instructions) into `AnimatedElement`s, each owning its `Smil`
children with `values`, `keyTimes`, `dur`, `attributeName` and, for transforms, `type`. `frameDocument(t)` takes
`t mod dur`, samples each animation with **step semantics** — the value whose `keyTime` has passed is the value in
force, which is what the generator's paired keyTimes produce — writes the value into the element's own attribute
(`fill="…"`), composes `translate`/`rotate` into `transform="translate(x,y) rotate(a cx cy)"`, deletes the consumed
animation elements, and applies the edits back to front. The result is a plain still SVG that `AndroidSVG` can draw.

`AuthorImageDecoder.decode` now detects the animation on first decode and keeps frame 0 as the bitmap;
`renderFrame(animation, elapsedMs)` rasterises a later instant. `MarkdownView.AnimatedSvgPicture` owns the loop:

* one `LaunchedEffect` keyed on `(animation, playing, lifecycle)` → a recomposition cannot start a second loop, and
  leaving composition cancels it;
* it runs inside `repeatOnLifecycle(RESUMED)` → backgrounding the app stops it;
* `playing` is `expanded` from the Author panel → a collapsed panel does no work at all;
* the period is `1000 / framesPerSecond` taken from the document, clamped to `1..10` fps;
* a frame that fails to render leaves the previous one on screen, so the page can never blank.

Unsupported SMIL (motion paths, `keySplines`, `begin`/`end` event timing) is not approximated: `detect` returns null
when nothing can be sampled and the picture is shown still, and a document with no `dur` is refused so a static
badge is never mistaken for an animation.

It is a **raster-to-vector trace of a 537×594 thumbnail screenshot**, not a copy of the README and not a rendering of

* **Resolution**: 537×594 against a 1080×2400 screen and against a source banner of 3840×2160 — it is a downscaled

* **Text became geometry**: each glyph is now a stack of filled polygons; it cannot be selected, scaled or re-laid

* **Colour was quantised**: 46 386 distinct fills is colour noise, not design — tracing approximates each region with
  many near-identical polygons, and gradients (the app's panel gradients, the badge pills' rounded shading) collapse
  into flat steps. This is the "somewhat lossy" appearance the user described, and it is inherent to the tracing
  step, not a compression setting.
* **Animation was flattened**: the Pacman graph in it is a single still trace, because a trace of a screenshot has no
  timeline to carry.
* **Aspect ratio changed**: 537/594 ≈ 0.90 versus the device's 1080/2400 = 0.45, so it is not even the same framing.

Conclusion: it is usable only as a rough diagnostic picture of what a screenshot looked like. It is **not** a
substitute for the README or for its assets, and it is not the original of anything. The Author page therefore keeps
rendering the actual Markdown with the actual referenced assets, as before. No generation pipeline for it exists in
the repository, so nothing was modified.

## 11. Automatic refresh lifecycle and cache behaviour

Unchanged by this task, and re-verified on the device rather than assumed:

* `MainViewModel.init` still starts the refresh **once per ViewModel**, in `viewModelScope` on
  `Dispatchers.IO`: `authorRepository.loadCached()` then `authorRepository.refresh()`. A ViewModel survives rotation
  and is created once per launch, so recomposition, rotation and opening *Licences* cannot start a second job; the
  repository additionally holds an `AtomicBoolean` single-flight guard.
* `loadCached()` publishes the cached README and the cached pictures (or the bundled copy) with **no network**, so
  the first frame is complete offline.
* `refresh()` issues one conditional GET for the README (`If-None-Match`/`If-Modified-Since` from
  `AuthorFileCache.Meta`) and then revalidates every referenced picture even when the README answered **304** —
  because a Shields.io badge and the contribution graph are generated, so an unchanged README does not imply
  unchanged pictures.
* A response replaces the cache only after `AuthorContentValidator.acceptsReadme` / `acceptsImage` (size bounds, no
  HTML/JSON error page, bytes must sniff as a real image), and only through `AuthorFileCache.atomicWrite`
  (`.part` → rename), so a failed or truncated refresh cannot destroy the last good copy.
* Runtime observation: on this launch the status line read *"Saved copy, last refreshed 11/9/26 3:31 PM. A refresh
  runs on every app launch."*, which is `AuthorSource.CACHED` plus a fresh `refreshedAt` — i.e. the refresh ran, the
  README answered 304, and the cached copy stayed on screen. The same line appeared before the Author panel was
  opened, which is the "refresh independent of navigation" requirement.
* `AnimatedSvgPicture` only ever reads the decoded animation from state; it never fetches, so animation cannot cause
  network traffic and cannot invalidate the cache.

## 17. Remaining limitations

* **The animation is re-rendered, not engine-played.** Each frame is an SVG re-parse plus a CPU rasterisation
  (38–57 ms per frame on this emulator) instead of a platform animation. It is comfortably inside the 200 ms the
  source allows per frame, but it is more work than a native animation would be, and it is why playback is gated on
  *expanded* + *RESUMED*.
* **Only the SMIL features this document uses are supported:** `attributeName="fill"` and
  `translate`/`rotate`/`scale`/`skew` on `keyTimes`/`values` with a `dur`. Motion paths, `keySplines` and
  `begin`/`end` timing are refused (`detect` returns null) rather than approximated, so such a document shows still.
* **Linear colour interpolation is rendered as a step.** Correct here — the generator's paired keyTimes make the

  bounded to 3× the row height, so it cannot own the screen).

* **No instrumented test exists for the badge size or the animation** (see §13); both rest on device measurement.
* **The corrupt QA screenshot is kept as evidence**, not repaired: its content is recoverable by decoding it as
