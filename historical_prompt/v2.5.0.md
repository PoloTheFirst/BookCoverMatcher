### 2.2 Preserve original result-profile images

**Current problem:**

Saved result profiles do not reliably retain the original captured or uploaded image. Some profiles retain only a thumbnail or another derivative. Furthermore, opening a result profile inside a wishlist folder does not display its original image at the top of the detail view.

**Required behaviour:**

When the user selects **Add entire result profile to wishlist**:

1. Preserve the actual original image used for the search.
2. Support both camera-captured images and uploaded images.
3. Store a persistent original-image asset associated with the correct saved result-profile session and wishlist folder.
4. Keep the original image separate from the thumbnail.
5. Do not substitute a thumbnail, OCR crop, provider image, workbook image or resized preview for the original.
6. Display the saved original image prominently at the top of the result-profile detail view when the user opens that profile from its folder.
7. Display the image above the saved result entries and metadata.
8. Preserve the source image across app restarts, process recreation, navigation and offline use.
9. Ensure different profiles cannot accidentally share or overwrite one another's image.
10. Keep existing thumbnails for compact folder/session list rows where appropriate.

**Image persistence and lifecycle:**

- Trace both camera capture and image-picker/upload paths.
- Follow the image from acquisition through Search state, result-profile draft creation, session persistence, wishlist repository and folder detail UI.
- Investigate whether original image data is currently discarded or replaced by thumbnail data such as `scanThumb`.
- Preserve original source bytes wherever available.
- If the existing pipeline only retains decoded pixels, preserve the highest practical source quality using the existing image-processing architecture. Document unavoidable transformations honestly.
- Introduce a separate persistent original-image reference or filename.
- Use existing storage abstractions where possible.
- Make writes atomic.
- Handle storage failures without creating broken or misleading image references.
- Preserve backward compatibility with existing saved profiles.
- Legacy profiles without an original image must still load safely and display an appropriate placeholder.
- Do not fabricate an original image from a thumbnail.
- Clean up image files when their owning records are deleted, but only when no other persisted record references them.
- Moving or renaming a profile must preserve the image association.
- Avoid unnecessary full-resolution image loading and excessive memory consumption.

**UI requirements:**

- The original image must appear at the top of the opened result-profile detail view inside the wishlist folder.
- It must not appear only in the folder tile, session list row or Search screen.
- Preserve its aspect ratio.
- Do not crop it into a fixed thumbnail shape.
- Use a sensible display-height limit for portrait covers and smaller screens.
- If the existing UI supports image inspection or enlargement, retain that interaction.
- Avoid displaying duplicate copies of the same image in adjacent sections.

**Required tests:**

- Camera-captured profile retains its original image.
- Uploaded-image profile retains its original image.
- Image association is correct for each profile.
- Image remains available after repository reload/process recreation.
- Legacy profiles without original-image references remain readable.
- Deleting a profile removes only unreferenced image files.
- Thumbnail and original-image storage remain independent.
- Storage failures do not corrupt existing wishlist data.
- Original-image display works offline.
