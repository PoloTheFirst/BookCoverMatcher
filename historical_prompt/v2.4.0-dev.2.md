## 4. Architectural requirements

Before implementing the five features, identify the common data and processing infrastructure they should share.

### 4.1 Canonical catalogue model

Use or extend the existing catalogue model rather than creating five independent data representations.

Where supported by the existing application, represent these concepts distinctly:

- Workbook and workbook identity.
- Worksheet identity.
- Source record identity.
- Workbook column and source-field mapping.
- Embedded image identity.
- Image-to-record association and association confidence/status.
- Metadata fields and missing-value status.
- Collection record identity.
- Publication date, acquisition date, and import date as distinct date meanings.
- Data-quality findings and their evidence.

Reuse existing models where they already provide the necessary semantics.

Do not introduce duplicate representations of the same record merely to support a new screen.

### 4.2 Shared processing layer

Prefer a shared, testable processing layer for:

- Workbook inspection.
- Record extraction and normalization.
- Column mapping.
- Image association.
- Data-quality checks.
- Analytics aggregation.
- Timeline construction.

UI composables should display results rather than independently reimplementing workbook parsing or data calculations.

Keep expensive processing off the main thread, use bounded memory, and support cancellation or progress reporting where the existing architecture allows it.

### 4.3 Preserve source data

Workbook processing must remain local-first and offline-capable.

- Treat source workbooks as read-only.
- Never execute VBA macros.
- Do not silently modify original workbooks.
- Do not convert unknown or missing values to zero, empty strings, or fabricated metadata without an explicit and justified rule.
- Do not invent associations between embedded images and source records.
- Preserve distinctions between Circle and Artist.
- Preserve existing collection data and user-entered metadata.
- Make any future export or correction workflow explicitly previewable.

## 5. Feature A — Spreadsheet Health Report

### 5.1 Purpose

Create a comprehensive, understandable report that helps users determine the quality and completeness of a selected workbook.

The report should identify actual problems in workbook structure, record metadata, embedded images, image associations, and data consistency.

It must be useful even when no internet connection is available.

### 5.2 Report categories

Implement checks supported by the current parser and data model.

**Workbook and worksheet structure**

- Workbook loading and parsing failures.
- Worksheets that could not be inspected.
- Worksheets with no detectable records, where this can be established.
- Unsupported or partially supported workbook structures.
- Records that cannot be reliably interpreted.

**Record completeness**

- Missing titles.
- Missing Circle or Artist fields, evaluated independently.
- Missing product identifiers.
- Missing URLs or invalid URL formats, where applicable.
- Missing price or date values when the workbook's mapping establishes those fields as relevant.

Do not report an optional field as an error simply because it is absent. Distinguish required, optional, unmapped, and unknown fields.

**Image integrity and associations**

- Embedded images successfully associated with records.
- Images without a confident record association.
- Broken or unresolved image relationships.
- Images that are referenced but cannot be extracted.
- Records with no associated cover image, when the association data supports that conclusion.
- Duplicate or near-duplicate images, only where the existing comparison logic can substantiate the finding.

Do not classify an image as orphaned merely because one association method failed if another supported association path may still resolve it.

**Metadata and consistency**

- Duplicate product identifiers.
- Duplicate records with sufficient matching evidence.
- Conflicting metadata between records or sources.
- Suspiciously malformed values.
- Unrecognized or ambiguous column mappings.

Distinguish confirmed errors from possible issues that require human review.

### 5.3 Severity and findings model

Each finding should contain, where applicable:

- Stable finding identifier.
- Category.
- Severity, such as error, warning, or informational.
- Human-readable explanation.
- Affected workbook, worksheet, record, field, or image.
- Evidence used to establish the finding.
- Suggested next action.
- Whether the finding is automatically resolvable, manually resolvable, or informational only.

Avoid making up a confidence score unless the detection method provides a meaningful basis for one.

### 5.4 Report interface

Provide:

- Overall workbook summary.
- Counts by finding category and severity.
- Clear separation between confirmed problems and potential issues.
- Filterable findings list.
- Useful empty, loading, partial-result, and error states.
- Access to relevant record or image details where supported by the current navigation architecture.
- A shareable or exportable report, using an existing export mechanism if available.

The report must not automatically repair data or overwrite source files.

### 5.5 Acceptance criteria

- Findings are generated from actual workbook inspection results.
- Missing, unknown, optional, and unmapped values are handled distinctly.
- Findings identify the affected item whenever possible.
- The report does not count the same underlying issue repeatedly without a clear reason.
- Findings remain consistent with the workbook parser's actual capabilities.
- All report calculations are testable independently of the UI.

## 6. Feature B — Visual Spreadsheet Browser

### 6.1 Purpose

Add a visual browsing experience for workbook records and embedded covers, allowing users to inspect a workbook without relying exclusively on a conventional spreadsheet-like list.

Reuse the existing image browser, workbook library, record models, and association logic where appropriate.

### 6.2 Browsing modes

Provide a visual gallery with cover thumbnails and available record metadata. Where the existing application architecture permits, provide a complementary tabular or detailed record view.

Users should be able to:

- Browse records grouped by worksheet.
- View the associated cover image.
- See the available title, Circle, Artist, product identifier, URL, and other mapped fields.
- Distinguish records with confirmed associations from unresolved images and records with no known cover.
- Filter by worksheet, association status, missing metadata, and other relevant fields.
- Sort using available and correctly typed values.
- Open a larger image viewer using the existing image-viewing conventions.
- Navigate between records without losing their browsing context.

Do not fabricate missing record values to make gallery cards appear complete.

### 6.3 Image handling

Reuse existing thumbnail caching and full-resolution viewing logic where possible.

- Avoid loading every full-resolution image into memory.
- Use lazy rendering and bounded image caching.
- Handle corrupt, missing, and unsupported images gracefully.
- Preserve aspect ratio and avoid unnecessary image distortion.
- Display a clear placeholder when no usable cover is available.
- Keep image association status visible when relevant.

### 6.4 Navigation and state

Integrate the browser into the established navigation structure instead of introducing an unnecessary duplicate destination.

Preserve applicable filters, sorting, worksheet selection, and scroll position when moving between a record and its details.

Ensure the feature does not unexpectedly reset existing Search or Wishlist directory state.

### 6.5 Source navigation distinction

Worksheet-to-source-row/cell navigation was previously deferred for v2.4.0 planning.

Treat it as a separately identified capability. Do not falsely claim that opening a record in the visual browser provides exact source-row or source-cell navigation unless that functionality has actually been implemented and tested.

If exact navigation is included in the existing approved v2.4.0 scope, implement it as a separate, explicit feature with validated source coordinates. Otherwise, document it as deferred and avoid expanding this milestone beyond the five priorities without justification.

### 6.6 Acceptance criteria

- The browser displays records and images using the shared data model.
- The user can distinguish confirmed associations from unresolved associations.
- Filters and sorting operate on actual workbook data.
- Large workbooks do not require loading all full-resolution images simultaneously.
- Image and record navigation preserve the relevant browsing state.
- Existing image-viewing and workbook-browsing features continue to work.

## 7. Feature C — Column Mapping Profiles

### 7.1 Purpose

Support workbooks that use different column names and layouts without hardcoding a single schema into every workflow.

Provide reusable profiles that map source workbook columns to canonical BookCoverMatcher fields.

### 7.2 Canonical field mapping

Support the fields that exist in the application data model, potentially including:

- Title.
- Circle.
- Artist or Author, according to the existing terminology and schema.
- Product identifier.
- URL.
- Price.
- Description or notes.
- Publication date.
- Tags.
- Other existing supported metadata fields.

Do not introduce a second, competing definition of Circle or Artist.

### 7.3 Mapping interface

The user should be able to:

1. Select a workbook and worksheet.
2. Inspect detected headers and sample values.
3. Select a saved mapping profile or create a new one.
4. Map source columns to canonical fields.
5. Leave columns unmapped.
6. Resolve ambiguous or conflicting mappings.
7. Preview the interpreted records.
8. Confirm the mapping before applying it to workbook analysis.

When the workbook has no header row or uses unusual structures, provide an explicit manual-mapping path only if the current parser can safely support it.

### 7.4 Mapping validation

Validate mappings before processing:

- Required fields are mapped where the workflow needs them.
- One source column is not assigned to incompatible fields without explicit justification.
- Ambiguous headers do not silently become definitive mappings.
- Duplicate or conflicting mappings are reported.
- Optional fields can remain unmapped.
- Unknown values remain unknown.
- Column order changes are handled using stable identifiers where available rather than relying only on positional assumptions.

### 7.5 Profile persistence

Save profiles using the project's existing persistence architecture.

A profile should record, as appropriate:

- Profile name.
- Mapped canonical fields.
- Stable source-header identifiers or normalized header names.
- Relevant workbook-layout assumptions.
- Profile version or schema information, if required for safe future evolution.

Do not bind a profile permanently to a workbook filename if the same profile can safely be reused elsewhere.

Provide sensible handling for renamed columns, missing headers, and stale profiles.

Do not silently apply a stale or ambiguous profile without warning the user.

### 7.6 Acceptance criteria

- A saved profile can be reused.
- Applying a profile produces consistent field mappings.
- Ambiguous mappings are visible before processing.
- Circle and Artist remain separate.
- The source workbook is never modified by mapping.
- Mapping behavior is covered by tests using representative workbook fixtures.

## 8. Feature D — Collection Analytics

### 8.1 Purpose

Provide useful, transparent statistics about the user's catalogue and collection, using existing records and persisted data.

Do not introduce an external analytics service or require an account or network connection.

### 8.2 Suggested analytics

Implement analytics supported by the available data:

- Total catalogued records.
- Records grouped by Circle and Artist.
- Records grouped by tags.
- Records grouped by collection status, such as owned or wanted, if those statuses exist.
- Records grouped by source or workbook.
- Records with missing metadata.
- Records with or without associated covers.
- Duplicate and potential-duplicate counts, using established matching evidence.
- Publication-year distribution, when publication dates are available and reliable.
- Import or acquisition trends, only when those dates are actually recorded.

Do not infer purchase price, publication date, or ownership from unrelated fields.

### 8.3 Calculation rules

Define the meaning of every metric.

For example:

- A record count must use a consistent record-identity rule.
- An image count must not be presented as a book count.
- Missing metadata must not be counted as a genuine zero.
- Potential duplicates must not automatically be subtracted from totals.
- Records with unknown dates must remain in an unknown category rather than being assigned an arbitrary year.

Avoid double-counting records imported from multiple sources.

### 8.4 Interface

Provide a readable analytics dashboard with:

- Summary totals.
- Charts or grouped breakdowns appropriate to the available data.
- Clear labels and units.
- Empty states when insufficient data is available.
- Filtering by workbook, source, or collection subset where appropriate.
- A way to inspect the records behind a metric when supported by the current navigation architecture.

Use the project's existing charting approach if one exists. Add a new charting dependency only when the benefit is justified and its maintenance, binary-size, and compatibility implications have been evaluated.

### 8.5 Performance

Do not recalculate expensive aggregates on every UI recomposition.

Use the repository's established background-processing and caching patterns, and invalidate cached analytics when relevant underlying data changes.

### 8.6 Acceptance criteria

- Counts can be verified against known test datasets.
- Aggregations use consistent identity and deduplication rules.
- Missing and unknown values are handled correctly.
- Metrics remain consistent with collection changes.
- The dashboard works offline.

## 9. Feature E — Collection Timeline

### 9.1 Purpose

Add a chronological view of catalogue activity and publication information, allowing users to understand their collection over time.

Publication, acquisition, and import dates must be treated as distinct concepts.

### 9.2 Timeline modes

Support timeline modes based on the dates available in the existing data model:

1. **Publication timeline** — when a book was published or released, if known.
2. **Acquisition timeline** — when the user acquired a book, if explicitly recorded.
3. **Import timeline** — when a record was added to BookCoverMatcher, if that timestamp is available and reliable.

Do not invent acquisition dates for existing records based on their import dates.

If the application cannot reliably establish a particular date type, omit that timeline mode or clearly explain its limitation.

### 9.3 Timeline interface

Provide:

- Chronological grouping by year and, where useful, month.
- Cover thumbnail and title.
- Relevant Circle, Artist, and product metadata.
- Clear date labels indicating what the date represents.
- Filtering by source, worksheet, collection status, and other applicable fields.
- Sorting in ascending or descending order.
- An explicit unknown-date group or filter when unknown dates are present.
- Navigation to record details without losing the timeline's context.

Records with unknown dates must not disappear silently from the collection.

### 9.4 Data and performance

Reuse existing date parsing and normalization logic. Support the date formats that the application actually encounters.

Handle malformed dates and ambiguous date formats without silently interpreting them incorrectly.

Use lazy rendering for large timelines and avoid repeatedly parsing dates during UI recomposition.

### 9.5 Acceptance criteria

- Each timeline entry uses a clearly identified date type.
- Unknown and invalid dates are handled explicitly.
- Publication dates are not substituted for acquisition or import dates.
- Chronological ordering is correct and deterministic.
- Timeline filtering and navigation preserve the relevant state.

## 10. Cross-feature integration

The five features must use a consistent data model and shared processing rules.

### Integration requirements

- Column Mapping Profiles must inform the record interpretation used by the Health Report, Visual Spreadsheet Browser, and applicable analytics.
- The Health Report and Visual Spreadsheet Browser must use the same image-association results.
- Analytics must use the same record identity and metadata rules as the browser.
- The Timeline must use the same canonical record model and validated date fields.
- A data-quality finding must refer to the same underlying record or image shown by the browser whenever a stable identity is available.
- Changing a mapping profile must invalidate dependent derived results where necessary.
- Changes to catalogue records must invalidate affected analytics and timeline caches.
- All features must remain usable offline when their underlying data is local.

Avoid implementing the same parser, mapping logic, association algorithm, or aggregation logic separately for each feature.
