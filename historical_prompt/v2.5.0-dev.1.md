# BookCoverMatcher — v2.5.0-dev.1 Implementation Prompt
## Advanced Online Cover Discovery, Local Matching, and Cross-Source Collection Management

## 1. Role and mission

Act as the senior Android engineer responsible for extending the existing BookCoverMatcher application.

The application has already implemented online search functionality, but its current approach produces unsatisfactory results for most sources. DLsite is the exception: its existing implementation is comparatively useful and must be preserved.

Your task is to investigate the existing implementation and deliver an advanced refinement of two related feature areas:

1. **Online cover discovery and local matching**
2. **Cross-source search and collection status management**

This is an enhancement of an existing application, not a greenfield rewrite. Understand the current code, identify why the existing search methods perform poorly, and improve the underlying provider architecture, matching pipeline, result presentation, caching, and collection integration.

Do not assume that every existing provider is broken. Diagnose each provider independently and preserve working behavior.

## 5. Feature A — Online cover discovery and local matching

<badge color="danger">High priority</badge>

### 5.1 Objective

Allow users to search online sources using one or more identifying attributes:

- Product or publication title.
- Circle or publisher.
- Author or creator.
- Product identifier, such as a DLsite RJ code.
- Other provider-specific identifiers.
- A local cover image or selected local image as a visual comparison reference.

The application should retrieve multiple candidate products and compare them with local spreadsheet records.

The user must be able to understand why a candidate is considered a match and manually confirm or reject the result.

### 5.2 Search input and query handling

Improve the existing search interface to support practical query combinations.

Examples:

- Title only.
- Circle only.
- Author only.
- Product code only.
- Title + circle.
- Title + author.
- Product code + title.
- Image reference + available metadata.

Implement appropriate query normalization:

- Trim leading and trailing whitespace.
- Normalize repeated spaces.
- Handle full-width and half-width characters where relevant.
- Handle Japanese and Latin text without destroying meaningful characters.
- Preserve meaningful punctuation in product identifiers.
- Normalize known provider-specific identifier formats.
- Avoid aggressive normalization that changes product identity.
- Retain the original query for display and diagnostics.

For DLsite, preserve the existing space-normalization behavior and RJ identifier handling.

Do not force every provider to use the same query format. Provider-specific query construction must remain possible.

### 5.3 Provider-specific search strategy

Implement a provider-aware search strategy.

Each provider should define its own supported search capabilities, such as:

- Title search.
- Creator or author search.
- Circle or publisher search.
- Product identifier lookup.
- Cover-image retrieval.
- Product metadata retrieval.
- Original listing URL retrieval.

Do not assume every provider supports all search dimensions.

Where a provider supports only title-based search, communicate that limitation rather than silently pretending it supports author, circle, or product-code searches.

The provider implementation should return normalized application data while retaining source-specific metadata.

### 5.4 Multiple candidate covers

The result interface must display multiple candidate covers in a clear, comparable layout.

Requirements:

1. Display candidate cover images side by side or in a responsive grid.
2. Preserve each image's aspect ratio.
3. Avoid stretching or cropping covers in a way that removes important visual information.
4. Show the product title and source.
5. Show the relevant circle, author, publisher, or identifier when available.
6. Show the original listing link.
7. Clearly indicate missing metadata.
8. Support loading, error, and unavailable-image states.
9. Avoid displaying duplicate candidates as if they were independent products.
10. Allow the user to open a candidate's details without losing the current search context.

The layout must remain usable on typical Android phone screen sizes.

Do not impose an arbitrary fixed five-result limit. Implement sensible pagination, incremental loading, or a configurable result limit according to each provider's actual capabilities and performance constraints.

Do not create fake additional results when a provider returns fewer candidates.

### 5.5 Explainable local matching

For each candidate, compare the available metadata and cover image with local spreadsheet records.

The matching system should support the following evidence dimensions:

| Matching dimension | Expected behavior |
|---|---|
| Title similarity | Compare normalized titles and meaningful textual similarity |
| Circle similarity | Compare circle or publisher names where available |
| Author similarity | Compare creator or author metadata |
| Product identifier | Compare exact and normalized identifiers |
| Image similarity | Compare candidate cover embeddings with local cover embeddings where available |

The system must explain which evidence contributed to the match.

Example presentation:

- Title similarity: high.
- Circle: exact match.
- Author: unavailable.
- Product identifier: exact match.
- Image similarity: strong visual similarity.

Do not present unavailable evidence as a negative match. Distinguish between:

- Match.
- Partial match.
- Mismatch.
- Unknown or unavailable evidence.

### 5.6 Matching architecture

Use a structured matching pipeline rather than a single opaque score.

The pipeline should:

1. Normalize candidate metadata.
2. Retrieve relevant local records.
3. Compare product identifiers.
4. Compare titles.
5. Compare circle and publisher names.
6. Compare author or creator names.
7. Compare cover images when usable embeddings are available.
8. Aggregate the available evidence.
9. Rank candidate-to-record matches.
10. Produce an explanation for the ranking.

Exact product identifiers should be treated as particularly strong evidence. However, do not automatically declare two products identical solely because their titles are similar.

Implement a configurable and documented weighting strategy if a combined score is used.

The system must account for missing metadata and must not unfairly penalize a candidate because a provider does not expose a particular field.

Keep raw evidence and the resulting score separate so the UI can explain the result.

Avoid false precision. A score should not imply a calibrated probability unless the system has actually been validated as one.

### 5.7 Image similarity

Use the existing OpenCLIP/ONNX Runtime embedding infrastructure where technically appropriate.

Requirements:

- Reuse compatible local cover embeddings.
- Avoid recomputing embeddings unnecessarily.
- Generate candidate-cover embeddings only when required.
- Normalize embeddings consistently before similarity comparison.
- Use the same embedding model and preprocessing assumptions for comparable vectors.
- Handle missing, corrupted, or unsupported images gracefully.
- Avoid blocking the main thread during image decoding or inference.
- Reuse cached embeddings when the image content has not changed.

If the current application cannot safely reuse its existing embedding pipeline for online candidate covers, investigate the actual technical reason before modifying it.

Do not introduce an unrelated image-similarity model without demonstrating why the existing model is unsuitable.

### 5.8 Search by image versus image comparison

Treat these as separate capabilities:

**Image comparison:** The application downloads candidate cover images from supported providers and compares them against a selected local cover or local spreadsheet images.

**Reverse-image discovery:** The application submits an image to an external provider and asks that provider to discover visually similar products.

Do not claim reverse-image discovery exists merely because image embeddings are used locally.

Only implement reverse-image discovery where a provider explicitly supports a legitimate integration method. Otherwise, retain image comparison as a local matching capability and clearly communicate the limitation.

### 5.9 Manual confirmation and rejection

The user must remain in control of the final match.

Provide actions to:

- Confirm a candidate as the matching local record.
- Reject a candidate.
- View the matched local record.
- View the matching evidence.
- Reopen the original online listing.
- Review alternative local matches.

Confirmation must be explicit.

A high similarity score must not automatically overwrite an existing spreadsheet mapping or collection record.

Persist confirmed associations using the existing application persistence architecture.

Rejected candidates should not be repeatedly presented as confirmed matches. If rejection history is persisted, make sure it does not permanently suppress a candidate that has materially changed or is being searched under a different context.

Preserve the existing result-profile behavior and ensure that switching profiles does not mutate or exchange the underlying profile data.

### 5.10 Candidate-image caching

Implement reliable local caching for downloaded cover images.

Requirements:

1. Reuse previously downloaded images when appropriate.
2. Avoid downloading the same image repeatedly.
3. Use stable cache keys derived from canonical image URLs or content identity.
4. Handle different URLs that resolve to identical content where practical.
5. Validate image responses and file contents.
6. Handle failed, interrupted, or incomplete downloads.
7. Avoid storing unbounded numbers of images.
8. Implement a bounded cache with an appropriate eviction strategy.
9. Support cache invalidation and refresh.
10. Preserve the user's saved or bookmarked result images where the existing design requires them to remain available.
11. Avoid blocking UI rendering while retrieving images.
12. Ensure that cached images can be used offline after successful retrieval.

Use the existing Android storage architecture where possible.

Do not place temporary cache files in public storage unnecessarily.

Keep image cache files separate from durable user-owned collection data.

Document cache limits, eviction behavior, and failure handling.

### 5.11 Performance and concurrency

The search pipeline must not freeze the UI.

Implement:

- Asynchronous provider requests.
- Appropriate coroutine dispatchers.
- Request cancellation when a search is replaced.
- Protection against stale responses overwriting newer results.
- Reasonable connection and read timeouts.
- Controlled concurrency across providers.
- Appropriate retry behavior for transient failures.
- Per-provider error isolation.

One provider failing must not cause all other provider results to disappear.

Avoid retry loops and uncontrolled parallel downloads.

## 6. Feature B — Cross-source search and collection status

<badge color="danger">High priority</badge>

### 6.1 Objective

Provide one unified search interface for multiple supported online sources.

Results should be grouped by source and retain clear links to their original listings.

The user should also be able to determine whether each product is:

- Owned.
- Wanted.
- Already catalogued.
- Unknown.

This status information must integrate with existing local spreadsheet records, wishlist behavior, and online search results.

### 6.2 Unified search interface

The user should be able to enter one search query and search multiple enabled providers from a single interface.

Requirements:

1. Support selecting all available providers.
2. Support selecting individual providers.
3. Clearly show which providers are enabled.
4. Allow provider-specific search capability differences.
5. Display results grouped by source.
6. Display source names consistently.
7. Preserve the original listing URL for every result.
8. Allow opening the original listing.
9. Handle individual provider failures independently.
10. Indicate loading and completion states for each provider.
11. Prevent duplicate searches caused by repeated UI events.
12. Support cancellation and refresh.
13. Retain useful search context when opening and returning from a result.

A provider must not be included as successfully searched if its request failed or its access was blocked.

Distinguish:

- Search completed with results.
- Search completed with no results.
- Search failed.
- Search unsupported for the requested query type.
- Search blocked or unavailable.
- Search still in progress.

### 6.3 Source grouping and cross-source duplicates

Group results by their originating source.

Where the same product appears on multiple sources, the application should be able to identify likely duplicates without deleting or merging independent source listings.

Use a normalized product identity model based on available evidence, including:

- Exact product identifiers.
- Normalized titles.
- Circle or publisher.
- Author or creator.
- Cover-image similarity.

A shared title alone is insufficient to guarantee that two listings represent the same product.

When duplicate listings are suspected:

- Retain the individual source listings.
- Indicate that they may refer to the same product.
- Allow the user to inspect the evidence.
- Avoid automatically merging records without adequate confidence.
- Preserve each source's original URL and metadata.

### 6.4 Local collection status model

Introduce the following statuses:

| Status | Meaning |
|---|---|
| Owned | The user has indicated that they own the product |
| Wanted | The user wants to acquire the product |
| Already catalogued | A corresponding record exists in the local spreadsheet/catalogue |
| Unknown | The application cannot determine the product's local collection state |

Do not treat these concepts as interchangeable.

In particular, **Owned** and **Already catalogued** are different facts:

- A user may own an item that has not yet been added to the spreadsheet.
- A spreadsheet may contain an item that the user has not confirmed as owned.
- A wanted item may already have a local record for tracking purposes.
- An unknown item may have insufficient information for reliable identification.

Design the data model so that collection ownership and catalogue presence can coexist without contradictory state.

If a mutually exclusive UI status is used for compact presentation, derive it from the underlying facts and document the precedence rules. Do not discard independent information simply to fit a single enum.

### 6.5 Status determination

Determine catalogue presence by matching the online candidate against local records.

Use the matching pipeline defined in Feature A.

The application should distinguish:

- Exact identifier match.
- Strong metadata match.
- Probable match.
- Ambiguous match.
- No matching record.
- Insufficient information.

Do not mark a product as already catalogued based only on a weak title similarity.

Where multiple local records are plausible, ask the user to choose rather than selecting one silently.

Ownership must be based on an explicit user action or reliable existing user data. Do not infer ownership merely because a product appears in the spreadsheet.

Wishlist status must remain consistent with the existing wishlist system.

### 6.6 Collection-status controls

From online search results, the user should be able to:

- Mark a product as owned.
- Add a product to the wishlist.
- Remove a product from the wishlist.
- Change an existing ownership status.
- View the corresponding local catalogue record.
- Confirm a catalogue match.
- Correct an incorrect catalogue match.
- Return a product to unknown when its status is no longer known.

Require confirmation before destructive or potentially ambiguous operations.

Prevent duplicate wishlist entries when the same product appears on multiple providers.

Where a product is identified as the same item across multiple sources, changes to its collection status should apply to the shared product identity while preserving its individual source listings.

Where identity is uncertain, do not automatically share status across separate candidates.

### 6.7 Wishlist and existing data compatibility

Inspect the existing wishlist and persistence architecture before implementation.

Preserve:

- Existing wishlist records.
- Existing bookmarks for online results.
- Existing result-profile data.
- Existing local spreadsheet mappings.
- Existing user-created associations.
- Existing profile isolation behavior.

Do not silently migrate, delete, or overwrite existing data.

If a database migration is required:

1. Inspect the current schema and migration framework.
2. Define an explicit migration.
3. Preserve all existing records.
4. Handle duplicate identities safely.
5. Provide a rollback or recovery strategy appropriate to the existing architecture.
6. Test migration from a real previous-version database fixture.

Do not create a second independent wishlist implementation.

## 15. Git workflow — commit and push to online_improvement

The implementation must be developed and published directly on the existing `online_improvement` branch.

**Unlike the previous release workflow, this task explicitly requires a commit and push after implementation.**

### 15.1 Verify the branch before implementation

Before modifying source code:

1. Inspect the current branch.
2. Verify that `online_improvement` exists locally.
3. Verify that it originates from the finalized `v2.4.0` release commit or has the expected subsequent development history.
4. Inspect its upstream tracking configuration.
5. Inspect the remote repository and branch.
6. Check the working tree for existing user changes.
7. Identify unrelated modifications and preserve them.

If the current branch is not `online_improvement`, switch to the existing branch only after confirming that doing so will not lose or overwrite uncommitted work.

If the branch does not exist or its history differs unexpectedly, stop and report the discrepancy. Do not silently recreate or reset it.

### 15.2 Implementation must remain on online_improvement

Perform all source-code, test, documentation, changelog, and version changes on `online_improvement`.

Do not switch to `master` or `dev` to implement or integrate the feature.

Do not merge this development work into either branch.

### 15.3 Pre-commit verification

Before committing:

1. Run the required unit tests.
2. Run the Android build.
3. Run relevant lint and static checks.
4. Verify database migration compatibility.
5. Review the final diff.
6. Check for accidental secrets, credentials, generated files, temporary files, and unrelated modifications.
7. Confirm the development version is `v2.5.0-dev.1`.
8. Confirm the prompt and agent report are saved in `historical_prompt`.
9. Confirm that the report accurately reflects the actual implementation and test results.

Do not commit code that has not been reviewed.

Do not stage every file blindly. Stage only the intended implementation, documentation, test, changelog, version, and prompt/report files.

### 15.4 Commit the implementation

After successful verification, create a descriptive commit on `online_improvement`.

The commit message should identify the `v2.5.0-dev.1` online discovery and collection-management refinement.

The commit must contain the intended implementation and its associated documentation and tests.

Do not include unrelated user changes.

If required tests are blocked, report the exact limitation and do not represent the commit as fully verified. Do not silently omit required work merely to create a commit.

### 15.5 Push directly to online_improvement

After the commit succeeds:

1. Verify the new commit is on `online_improvement`.
2. Verify the intended remote and upstream.
3. Push `online_improvement` to that remote.
4. If no upstream exists, configure the upstream for `online_improvement` using the intended remote.
5. Verify the remote branch contains the new commit.
6. Record the resulting commit hash and push confirmation in the agent report.

If the push is rejected because the remote branch has advanced, inspect and reconcile the divergence safely. Do not force-push, overwrite remote work, or rewrite published history.

If authentication or network issues prevent pushing, retain the local commit and report the failure precisely. Do not claim the remote is updated.

### 15.6 Strict branch restrictions

- Commit the implementation on `online_improvement`.
- Push the implementation to `online_improvement`.
- Do not push to `master`.
- Do not push to `dev`.
- Do not merge into `master` or `dev`.
- Do not create a stable release tag.
- Do not force-push.
- Do not rewrite existing history.
- Do not delete or recreate existing branches.
- Do not discard user changes.
