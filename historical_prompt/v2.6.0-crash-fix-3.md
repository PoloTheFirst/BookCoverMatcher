## 2. Issue A — Improve Shields.io icon image quality

### Observed problem

Badge sizing is now correct, but some Shields.io icons appear blurred or soft. This is a visual-quality problem, not a request to enlarge the badges.

The previous fixed-height badge sizing and grouping behavior must remain intact.

### Investigation

Trace the complete badge-image pipeline:

1. Identify the actual Shields.io badge URLs used by the Author page.
2. Inspect the returned image formats and source dimensions.
3. Determine whether the badges are delivered as SVG, PNG, or another format.
4. Inspect the rendering path from Markdown parsing through image loading, decoding, scaling, and Compose drawing.
5. Check whether the current SVG renderer rasterizes images at insufficient resolution.
6. Check whether images are decoded into undersized bitmaps and then enlarged.
7. Check whether scaling, filtering, clipping, density conversion, or an intermediate image cache degrades quality.
8. Determine whether the image is being rendered at a different size from the size used to calculate its decoded resolution.
9. Compare the actual rendered icon against the original source.

Do not assume that increasing the Compose display size is the correct solution.

### Implementation requirements

Choose a solution based on the verified cause.

Preferred behavior:

- Preserve vector rendering for SVG assets where the existing renderer supports it reliably.
- If rasterization is necessary, render at an appropriate resolution for the actual display density and intended display size.
- Avoid rasterizing a vector into a small bitmap and subsequently enlarging it.
- Preserve aspect ratio and avoid unnecessary resampling.
- Avoid degrading image quality through repeated decode/scale/cache cycles.
- Use appropriate filtering for the actual source format and scaling direction.
- Keep badge sizing fixed at the established Crash-fix-1 dimensions unless device evidence demonstrates a genuine sizing defect.
- Keep the existing badge grouping and row layout.
- Do not hardcode a special case for Java or any individual badge.
- Do not replace real badge icons with manually drawn substitutes or screenshots.
- Do not compromise SVG safety or introduce unsafe HTML/WebView rendering.

If the source image itself is low resolution, determine whether a suitable vector or higher-resolution source is available before changing the rendering pipeline.

### Tests

Add or update tests for the actual root cause.

At minimum, verify:

- SVG badge assets remain vector-rendered where supported, or are rasterized at sufficient resolution.
- Raster sources are not enlarged from an unnecessarily small decode.
- Aspect ratio is preserved.
- Existing fixed badge height and width constraints remain unchanged.
- Badge grouping remains unchanged.
- Malformed or unsupported images fail safely.
- Existing Markdown image and SVG behavior does not regress.

Tests must exercise the production rendering or sizing logic rather than only test a duplicated implementation.

### Device verification

Run the app on an emulator or physical device.

Capture the actual rendered badge row and inspect it at native resolution.

Compare:

- Original source image.
- Actual displayed badge.
- Icon edge sharpness.
- Text sharpness.
- Badge dimensions.
- Appearance at the device's actual density.

Do not claim that quality is improved based solely on successful compilation or a unit test.

## 3. Issue B — Apply a dark visual theme to the Pacman contribution graph

### Observed problem

The Pacman animation itself now works. Do not replace or unnecessarily redesign the working animation implementation.

The contribution graph currently has an unwanted white/light visual appearance. It should use a coherent dark contribution-graph theme, including both its background and its text.

### Required visual behavior

The Pacman contribution-graph component should use a deliberately dark visual palette:

- Dark background behind the contribution graph.
- Readable light-colored text.
- Appropriate contrast for labels, month names, weekday labels, and other graph annotations.
- Contribution-level colors that remain distinguishable against the dark background.
- Pacman and contribution cells remain clearly visible.
- Any legends or labels belonging to the graph should use compatible colors.

Use the existing README/source graph palette as a reference where appropriate, but inspect the actual source assets and implementation before deciding exact colors.

The dark theme applies to the Pacman contribution-graph presentation itself. It must not force the rest of the application into dark mode.

The component must remain readable regardless of whether the Android application is currently using its light or dark theme. In particular, do not allow a light-theme text color to become invisible against the graph's dark background.

Do not simply place a dark rectangle behind the existing white-themed graph while leaving its text, labels, or other elements unreadable.

### Investigation

Trace the current graph rendering pipeline:

1. Identify the original contribution graph SVG and its styling.
2. Inspect the SVG background, text fills, contribution colors, CSS styles, and inherited/default colors.
3. Determine how the graph is transformed by the existing SMIL animation implementation.
4. Determine whether the animation frame generation preserves the original styles.
5. Check whether Compose or Android theme values override or affect the graph's colors.
6. Check whether the graph's SVG is being modified or reconstructed in a way that introduces white backgrounds or dark text.

Do not change the original graph data or animation behavior merely to change its visual palette.

### Implementation requirements

- Apply a consistent dark palette to the graph's actual rendered content.
- Ensure background and text colors are both explicitly controlled.
- Preserve the contribution graph's original data and layout.
- Preserve Pacman movement and contribution-cell animation.
- Preserve SVG transforms, masks, clipping, and other required visual structures.
- Ensure all generated animation frames use the same intended dark palette.
- Avoid a flash of white or a light-theme frame when the animation starts or resumes.
- Keep the graph readable in both Android light mode and Android dark mode.
- Do not globally change the app theme or unrelated Author-page components.

If the original SVG contains styles that are difficult to override safely, implement a focused and testable transformation rather than applying broad string replacements.

## 4. Issue C — Increase Pacman animation smoothness

### Observed problem

The Pacman animation now works, but its movement should be smoother.

Crash-fix-1 reported an original source frame rate of approximately 5 FPS. The current implementation must be inspected rather than assuming that this rate is still the effective rate.

### Investigation

Trace the full timing pipeline:

1. Original SVG animation duration and timing declarations.
2. SMIL animation sampling.
3. Frame-generation interval.
4. Generated frame caching or reuse.
5. Animation scheduler or coroutine.
6. Compose state updates and recomposition.
7. Actual visible frame changes on the running device.

Determine the effective frame rate at every stage.

Identify whether frame generation, SVG parsing, rendering, scheduling, or Compose state updates are limiting smoothness.

### Implementation requirements

Increase the effective animation frame rate to a visibly smoother level.

Target:

- Aim for approximately 15–20 FPS where the device can sustain it.
- Do not exceed the source animation's meaningful temporal resolution without a reason.
- Preserve the original animation duration and motion timing.
- Do not accelerate Pacman's movement simply to create more frames.
- Sample intermediate animation times from the original SMIL timeline.
- Keep the existing animation architecture where practical.
- Avoid repeatedly parsing the entire SVG on every frame.
- Reuse precomputed frames or other safe caching where appropriate.
- Keep frame generation and display scheduling separate if that improves performance.
- Avoid unbounded frame generation, excessive allocations, or uncontrolled background work.
- Stop or pause animation when the graph is not visible.
- Resume appropriately when it becomes visible again.
- Prevent duplicate animation loops after navigation, recomposition, or lifecycle changes.
- Avoid updating Compose state when the displayed frame has not changed.
- Do not introduce a WebView merely to obtain smoother SVG animation.

If the device cannot sustain the target frame rate, report the measured rate and bottleneck honestly rather than claiming the target was achieved.

### Runtime verification

Verify on an actual running emulator or device:

- Pacman visibly moves more smoothly than before.
- The graph background and text retain the dark palette throughout animation.
- There is no white flash during startup, navigation, or resume.
- The graph pauses when hidden.
- The graph resumes when visible.
- Navigation into and out of the Author section does not create duplicate loops.
- Backgrounding and foregrounding the app do not cause runaway animation.
- Animation does not cause excessive CPU usage, memory growth, or UI jank.

Measure actual visible frame changes over a defined interval. A changing frame counter or changing generated SVG string is not proof of smooth visible animation.

Record the measurement method, interval, observed frame count, and calculated effective FPS.
