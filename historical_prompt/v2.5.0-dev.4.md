# 1. Mission and Scope

Implement **v2.5.0-dev.4** for BookCoverMatcher.

This release extends the existing reverse-image discovery and wishlist integration. Its primary purpose is to make SauceNAO results as usable as IQDB results in the application's collection workflow.

The six required changes are:

1. Extract a usable cover/product image from SauceNAO result webpages when possible, and display it in the corresponding SauceNAO result card.
2. Add a top-right rubbish-bin icon to every SauceNAO result card, matching the existing IQDB dismissal behavior.
3. Allow individual SauceNAO results to be bookmarked and added to the wishlist.
4. Include SauceNAO results in **Add entire result profile to wishlist** whenever SauceNAO participated in the search.
5. Rename **Bookmark all results** in the Online tab to **Bookmark all platform results**.
6. Add a separate **Bookmark all discovery results** action under the reverse-image discovery section.

Do not redesign the entire Online tab or replace the existing reverse-image discovery architecture.

Preserve the functionality delivered in v2.5.0-dev.3 unless a specific change is required for this release.

# 3. Requirement 1 — Extract and Display SauceNAO Result Images

## 3.1 Objective

Currently, SauceNAO results may contain useful product or cover information without a corresponding image displayed in the result card.

Improve this by attempting to retrieve a representative image associated with each SauceNAO result.

The goal is to make visual comparison easier, particularly when a result contains a title or source URL but the user cannot immediately identify whether the cover matches the scanned image.

## 3.2 Image retrieval strategy

Inspect the actual SauceNAO response model and current provider adapter first.

Use the following retrieval priority:

1. **Image URL already included in the SauceNAO response**, if it is a usable result image.
2. **Open Graph metadata** from the result webpage, especially `og:image`.
3. **Twitter/X card image metadata**, such as `twitter:image`, when available.
4. A clearly identifiable primary product or cover image exposed through the webpage's ordinary HTML metadata or permitted page content.
5. No image, if none of the above methods provides a suitable image.

Do not assume every SauceNAO result has an image URL.

Do not assume that the first image found in arbitrary HTML is the correct cover.

## 3.3 Retrieval restrictions

Implement image retrieval conservatively:

- Only retrieve publicly accessible content.
- Respect website access restrictions and applicable provider requirements.
- Do not attempt to bypass authentication, CAPTCHA, anti-bot protection or other access controls.
- Do not execute arbitrary webpage JavaScript to obtain an image.
- Do not use browser automation as an automatic workaround for blocked image retrieval.
- Apply reasonable connection and read timeouts.
- Limit response size and image dimensions.
- Validate HTTP status, content type and actual image decoding.
- Reject malformed, unsupported or excessively large images.
- Avoid fetching arbitrary local-network or private-network destinations.
- Validate redirect destinations as well as initial URLs to mitigate SSRF.
- Restrict accepted schemes to safe HTTP/HTTPS URLs.
- Prevent image retrieval from becoming an unrestricted webpage proxy.

If a website blocks access, returns an unusable page, or does not expose a suitable image, preserve the SauceNAO result and display the existing image placeholder.

**Image extraction failure must never cause an otherwise valid SauceNAO result to disappear.**

## 3.4 Data model

Inspect the existing normalized discovery-result model.

Extend it only where necessary to represent:

- Original SauceNAO result image URL, if available.
- Resolved webpage image URL, if successfully extracted.
- Image retrieval state.
- Optional cached image reference or existing image-cache key.
- Image source/provenance, so the UI can distinguish a provider-supplied image from a webpage-extracted image.

Do not duplicate fields that already exist.

Image state should distinguish at least:

- Not requested
- Loading
- Available
- Unavailable
- Failed

Keep image retrieval separate from the core SauceNAO metadata parsing process.

A failure to extract an image must not invalidate the title, source URL, similarity information or other provider metadata.

## 3.5 UI behavior

Every SauceNAO result card should display its retrieved image when available.

Requirements:

- Use the existing card's layout and visual style as the baseline.
- Preserve readable title, source, provider attribution and other existing metadata.
- Use a sensible image aspect ratio and scaling mode.
- Prevent the image from stretching or distorting.
- Show a neutral placeholder while loading or when unavailable.
- Avoid layout jumps when images load.
- Ensure the image does not obscure bookmark or dismissal controls.
- Support light and dark themes.
- Ensure scrolling remains smooth with multiple result cards.

Do not make the card depend on successful image retrieval.

## 3.6 Cache and lifecycle

Reuse the existing image cache if one exists.

Do not introduce a second independent image-cache system without a clear architectural reason.

If caching is needed, follow existing project conventions:

- Bounded storage.
- Reuse across recompositions.
- Appropriate cache invalidation.
- Safe handling of expired or invalid URLs.
- No unbounded accumulation of downloaded images.
- No accidental deletion of shared cached images when a card is dismissed.

Image retrieval must be asynchronous and cancellable where supported.

Prevent stale requests from updating cards belonging to a newer search.

- Avoid accidentally creating duplicate records.

Follow existing IQDB interaction conventions so that the two providers behave consistently.

## 5.3 Data mapping

Inspect the current wishlist data model and the existing IQDB-to-wishlist mapping.
