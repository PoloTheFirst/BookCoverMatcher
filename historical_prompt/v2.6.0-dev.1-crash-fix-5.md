## 4. Investigate Microsoft Graph drive and folder endpoints

This is the central investigation.

Inspect every endpoint used for OneDrive discovery and folder listing. Verify the actual endpoint strings in the implementation rather than assuming the intended endpoint is being called.

Consider the following Graph operations where appropriate to the current design:

- `GET /v1.0/me`
- `GET /v1.0/me/drive`
- `GET /v1.0/me/drive/root`
- `GET /v1.0/me/drive/root/children`
- `GET /v1.0/me/drive/items/{item-id}/children`

Do not add all these requests unnecessarily. Establish which requests the application actually needs.

Investigate:

### A. Drive discovery

- Does the app assume a drive ID that has never been obtained?
- Does it use `/me/drive` correctly for the authenticated personal account?
- Does it incorrectly assume that a user's OneDrive drive is immediately available?
- Does it mishandle a missing drive, unprovisioned drive or service error?
- Does it confuse a user's profile identity with the drive identity?
- Is a cached drive ID stale or associated with a different account?

### B. Root folder

- Does the root request use the correct endpoint?
- Is the returned root item parsed correctly?
- Does the app incorrectly treat a missing or unexpected root property as an empty folder?
- Is the root item ID retained correctly?
- Does the app construct the children URL using the correct identifier?

### C. Folder children

- Is the correct children endpoint called?
- Are item IDs URL-encoded safely?
- Does the code incorrectly use a folder path where a drive item ID is required?
- Does it incorrectly use a drive ID as an item ID, or vice versa?
- Are folders distinguished from files using the correct Graph response fields?
- Are `folder` and `file` facets parsed correctly?
- Are empty folders handled correctly?
- Are special characters in folder names and IDs handled safely?

### D. Pagination

- Is `@odata.nextLink` handled correctly?
- Does the code accidentally stop after the first page?
- Does it reject valid next links?
- Does it accidentally reconstruct or modify a server-provided next link?
- Is the next link validated before attaching a bearer token?
- Does pagination produce duplicate or missing items?
- Does a later-page failure incorrectly erase the first page's valid results?

Preserve the existing HTTPS and Graph-host validation rules. Never send a bearer token to an untrusted host.

### E. Response parsing

- Is the response expected to contain the correct JSON shape?
- Is the `value` collection parsed correctly?
- Are missing optional fields handled safely?
- Does the parser incorrectly reject a valid response?
- Does it confuse an empty collection with a malformed response?
- Does it incorrectly require properties that Graph does not guarantee?
- Does it handle unexpected content types and HTML error pages safely?

Do not silently convert malformed or failed responses into an empty folder.

## 7. Improve the user-facing folder-access result

Reuse the error taxonomy introduced by crash-fix-4.

Do not create a competing second taxonomy without a compelling reason.

The user should not see a misleading empty folder or indefinite spinner when folder listing fails.

The UI should distinguish at least:

- Not signed in.
- Authentication required.
- Sign-in cancelled.
- Permission denied.
- Drive unavailable or not provisioned.
- Network unavailable.
- Graph service failure.
- Folder not found or no longer accessible.
- Invalid or unexpected Graph response.
- Folder listing failed for an unknown reason.

Use concise wording and an appropriate recovery action.

Examples of appropriate recovery behavior:

- Authentication required: offer sign-in again.
- Permission denied: explain that account permission or consent may be required.
- Network unavailable: preserve the user's current state and allow retry.
- Drive unavailable: explain that the OneDrive drive could not be accessed.
- Graph service failure: offer retry without claiming that the device is offline.
- Invalid response: report that folder contents could not be read.

Do not display raw server messages or internal exceptions to the user.

Do not report an empty folder when the request actually failed.

Do not leave the app permanently in a loading state.

Do not clear a previously authenticated account merely because one folder request failed.
