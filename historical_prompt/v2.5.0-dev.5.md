# 1. Mission and Architectural Scope

Replace the existing Python-based `chrome-lens-py` OCR workflow with a native Rust OCR implementation using PaddleOCR PP-OCRv6 ONNX models and ONNX Runtime.

The new OCR implementation must:

- Run locally on Android.
- Avoid Python runtime dependency for OCR.
- Use Rust for the OCR inference and image-processing core.
- Integrate with the existing Kotlin Android application through a safe native interface.
- Preserve the existing OCR-to-search workflow.
- Remain independent of the OpenCLIP visual matching pipeline.
- Support the languages relevant to the application's book-cover recognition workflow.
- Avoid blocking the Android UI.
- Reuse the application's existing image acquisition and state-management architecture.

**This is an OCR-engine migration, not an application rewrite.**

Do not migrate OpenCLIP, workbook parsing, wishlist logic, reverse-image discovery, SauceNAO or IQDB into Rust as part of this release.

Do not replace Jetpack Compose or the existing Kotlin application layer.

## 1.1 Phase 1 scope

This release focuses on:

1. Feasibility verification for Rust + Android + ONNX Runtime.
2. Native Rust OCR engine implementation.
3. PP-OCRv6 model integration.
4. Kotlin/JNI integration.
5. OCR output normalization.
6. Integration with the existing OCR-to-online-search workflow.
7. Accuracy, performance, memory and regression testing.
8. Safe removal of the old Python OCR implementation after successful validation.

# 2. Model Selection and Compatibility Verification

## 2.1 Correct model naming

Use the official PaddleOCR model names.

The intended high-accuracy server-tier model is:

- `PP-OCRv6_medium_det`
- `PP-OCRv6_medium_rec`

The PP-OCRv6 model family uses three tiers:

| Model tier | Intended deployment |
|---|---|
| PP-OCRv6_tiny | Edge/IoT |
| PP-OCRv6_small | Mobile/desktop |
| PP-OCRv6_medium | Server |

Do not refer to the model as `PP-OCRv6 Server/Large` in implementation filenames or configuration unless an actual official model artifact uses that exact name.

## 2.2 Medium model is the target, not an assumed Android-compatible artifact

The user's target is the high-accuracy medium/server tier.

However, the official PaddleOCR Android deployment documentation currently lists PP-OCRv6 small and tiny, alongside PP-OCRv5 mobile. It does not establish that every PP-OCRv6 medium ONNX artifact is supported by that Android example.

Therefore:

1. Attempt to validate the exact PP-OCRv6 medium detection and recognition ONNX artifacts.
2. Verify their input/output tensor types, shapes, operators and dynamic dimensions.
3. Verify that the models can run using the selected Android ONNX Runtime build.
4. Verify that the models can run through the intended Rust integration.
5. Benchmark actual inference on Android hardware.
6. Check memory usage and application stability.

Do not silently substitute PP-OCRv6 small if medium fails.

If medium cannot be integrated reliably, document the exact incompatibility and benchmark PP-OCRv6 small as a fallback.

Report the trade-off and obtain explicit user approval before changing the target model tier.

## 2.3 Model size and storage

Do not hardcode the proposed 90–120 MB estimate.

Inspect the actual downloaded model artifacts and report:

- Detection model size.
- Recognition model size.
- Dictionary/configuration size.
- Total packaged size.
- Extracted storage footprint.
- Estimated peak runtime memory.

The medium model may be substantially larger than the original estimate.

Evaluate whether model assets should be:

If models are copied from packaged assets:

- Copy them off the compressed asset stream into internal storage.
- Verify successful extraction.
- Avoid copying them repeatedly on every scan.
- Use model version or checksum information to determine whether extraction is necessary.
- Handle insufficient storage and corrupted files gracefully.

Do not introduce remote model downloads unless explicitly justified and approved.

# 7. Camera, Rescan and Concurrency

## 7.1 Safe image ownership

The supplied plan suggests passing a fresh canvas memory address to Rust after terminating the active frontend worker loop.

Do not implement this approach.

A raw memory address can become invalid when the Kotlin image buffer, bitmap or frontend worker is released.

Instead:

- Use an immutable image snapshot or owned byte buffer.
- Define explicit ownership and lifetime rules.
- Avoid retaining pointers to temporary Android image memory.
- Release native buffers after inference.
- Prevent concurrent access to mutable image buffers.

## 7.2 Rescan cancellation

When the user taps Rescan:

1. Cancel the previous OCR job through the existing coroutine/job or cancellation mechanism.
2. Prevent the previous job from updating the current UI state.
3. Submit the new image as a separate inference request.
4. Associate results with the correct scan/request identifier.
5. Ignore stale results from previous requests.
6. Release temporary buffers and resources safely.

Do not terminate arbitrary frontend threads.

Do not forcibly stop the Android application worker context.

Do not use unsafe thread termination to cancel native inference.

If ONNX inference cannot be interrupted immediately, ensure the result is discarded safely and that subsequent scans cannot corrupt shared native state.

## 7.3 Concurrency policy

Start with a safe, controlled inference policy.

Unless benchmarking proves that concurrent OCR requests are beneficial, serialize access to the shared detector and recognizer sessions.

Avoid:

- Unbounded worker threads.
- Concurrent access to non-thread-safe buffers.
- Repeated model initialization.
- Excessive image copies.
- Blocking UI rendering.
- Uncontrolled CPU thread counts.

Document the chosen concurrency policy.

- Android version.
- Device hardware.
- NNAPI driver.
- Supported operators.
- Model graph.
- ONNX Runtime build.

- Preferred execution provider.

- Thread count.
- Optional precision settings.
