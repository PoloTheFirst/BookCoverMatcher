**Baseline gaps found (the real defect surface):**

1. **No structured query.** One free-text string goes to every provider, so an author name is searched as a DLsite keyword and a circle name is searched as an Open Library title. `ProviderCatalog.QueryForm` only decides how a *space* is encoded.
2. **No declared capabilities.** Every automated provider is treated as supporting the same query; the UI cannot say "this provider cannot search an author".
3. **No candidate↔local-record matching.** The app can rank local covers by OpenCLIP embedding (`CatalogIndex`/`FlatIpIndex`), but nothing compares an online candidate's metadata with a local record, and nothing explains a match.
4. **No cross-source identity, collection status, or cover cache** (as the prompt says).
5. DLsite's space handling (`+`) and RJ handling already exist in `DlSite`/`QueryForm` and were **not touched**.

**Constraints respected:** no backend, no new dependency, no provider enablement, no access-control bypass, no OCR-as-recognition claim, DLsite untouched, embedding pipeline untouched.

## 4. Matching implementation

* **Dimensions:** identifier (weight 0.45), title (0.30), circle (0.15), author (0.10), cover similarity
  (0.35, supplied by the caller).
* **Strategy:** each dimension is compared independently and carries its own `EvidenceState`
  (`MATCH`/`PARTIAL`/`MISMATCH`/`UNKNOWN`) plus a human-readable detail line and the measured similarity.
* **Aggregation:** `score = 100 · Σ(weight·component) / Σ(weight)` over **available** dimensions only, so a
  provider that sends no circle cannot lose points for it. Components: identifier 1/0, text and cover = the
  measured similarity.
* **Verdicts:** exact identifier → `LIKELY_MATCH`; any contradiction → `NO_MATCH`; title + score ≥ 72 +
  another corroborating dimension → `LIKELY_MATCH`; score ≥ 50 → `POSSIBLE_MATCH`; nothing comparable →
  `INSUFFICIENT_EVIDENCE`. Constants are documented in the object, not scattered.
* **Explanation:** `ProductMatch.explanation()` returns one line per available dimension, e.g.
  `identifier: RJ01234567 is the same`, `title: matches (100%): "Blue Archive" vs "Blue Archive"`,
  `cover: cover similarity 93%`.
* **Image similarity:** accepted as an optional `Double` input; **not computed** here, because that belongs
  to the existing OpenCLIP/ONNX pipeline, which is not called yet.
* **Ambiguity:** `ambiguous(ranked)` returns every likely/possible match within 8 points of the best, so a
  UI asks the user instead of silently choosing.
* **Confirmation/rejection persistence:** **not implemented** (no schema change was made).
