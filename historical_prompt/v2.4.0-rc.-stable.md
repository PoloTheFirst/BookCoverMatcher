# Stable Release Finalization — BookCoverMatcher v2.4.0

## 1. Release artifact names

Use the following filenames:

- Final implementation prompt: `historical_prompt\v2.4.0-rc-stable.md`
- Agent execution report: `historical_prompt\v2.4.0-rc-stable-ag.md`

Do not retain the old `v2.4.0-rc.7` prompt or report filenames as the names of the final stable artifacts.

## 2. Release identity

- Final tested development version: `v2.4.0-rc.7`
- Stable release version: `v2.4.0`
- Release branch: `master`
- New development branch: `online_improvement`

The release must preserve the actual implementation and test results from `v2.4.0-rc.7`. Do not introduce unrelated feature changes during release finalization.

## 3. Pre-release verification

Before changing Git state:

1. Inspect the current branch, commit, working tree, remotes, and tags.
2. Verify that `v2.4.0-rc.7` is the intended final release.
3. Review all pending changes and identify user-owned or unrelated modifications.
4. Verify that the release build and required tests have passed.
5. Check version metadata, documentation, changelog, and release references for consistency.
6. Preserve existing release history and do not restore changelog entries previously removed by the user.

If the release is not ready or the repository contains changes whose ownership is unclear, stop and report the issue before committing.

## 4. Finalize and publish on master only

Perform the following operations in order:

1. Switch to the existing `master` branch after verifying its identity and current state.
2. Integrate the verified `v2.4.0-rc.7` release changes into `master` without losing user changes.
3. Set the stable application version to `v2.4.0`, following the repository's existing versioning conventions.
4. Update the changelog and release documentation to identify `v2.4.0` as the stable release.
5. Run the required final build and regression tests.
6. Create an appropriately descriptive release commit on `master`.
7. Create an annotated Git tag named `v2.4.0` pointing to that exact release commit.
8. Push the `master` branch to the existing intended remote.
9. Push the `v2.4.0` tag to that remote.

**Git restrictions:**

- Push the release commit to `master` only.
- Do not push to `dev`.
- Do not merge the release into `dev`.
- Do not create or push a replacement `dev` branch.
- Do not force-push or rewrite published history.
- Do not delete existing branches or tags.
- Do not overwrite an existing `v2.4.0` tag without investigating and reporting the conflict.
- Do not claim a push or tag operation succeeded unless Git confirms it.

## 5. Create the next development branch

After the stable release commit and tag have been successfully published:

1. Create a new branch named `online_improvement` from the finalized `master` release commit.
2. Switch the working tree to `online_improvement`.
3. Verify that its starting commit is exactly the `v2.4.0` release commit.
4. Leave the new branch ready for future online-search improvements.

Create this branch locally only. Do not push `online_improvement` to the remote, because the release-push requirement is limited to `master`.

Do not start implementing online improvements as part of this release-finalization task.

## 6. Final verification and report

Save the execution report as:

`historical_prompt\v2.4.0-rc-stable-ag.md`

Include:

- Starting branch and commit.
- Release verification and test results.
- Final stable version metadata.
- Release commit hash.
- Annotated tag name and target commit.
- Confirmation of the `master` push.
- Explicit confirmation that `dev` was not pushed or modified by this workflow.
- Creation and starting commit of `online_improvement`.
- Final working-tree state and current branch.
- All files created or modified.
- Any blocked, skipped, or unsuccessful operations.

Distinguish verified results from assumptions. Never fabricate Git output, test results, or release success.
