# v2.4.0-rc.6 — agent report

Implementation prompt: `historical_prompt/v2.4.0-rc.6.md`. Application version stays **2.4.0** (versionCode 213).
`rc.6` is an internal implementation-prompt identifier, not a version.

## A. Summary

Two defects were fixed by correcting the *model* they came from, not by patching symptoms.

1. **The Detected status** (`Bug A`) is now computed against the mapping a worksheet reads **without** the pending
   edit (`baselineColumnsFor`), so applying an unchanged mapping stores nothing and the chip stays blue, while a
   real change or a differing profile turns it grey.
2. **Saving a profile** (`Bug B`) no longer copies the worksheet on screen onto the others. A profile is a
   **per-worksheet snapshot** (`ColumnMappingProfile.sheets`), and saving builds it from the configuration in
   effect: the inspected worksheet contributes the draft, every other worksheet contributes its own mapping (the
   selected profile's entry, the edit applied to it, or its own detected headers).

Along the way the profile model itself was corrected, which is what the prompt asked for in §2 and §6: selecting
**Detected** or a saved profile is now a **view switch** (`selectProfileView`), not an implicit apply. It changes
which configuration is displayed and read; it copies, merges and rewrites no profile in either direction.

## B. Bug A — Detected Status

### Confirmed root cause

rc.5 had already replaced the old pair of state flags with a semantic comparison, but the comparison was made
against the wrong baseline: `applySheetMapping` compared the applied columns with `detectedMappingColumns` **and
then** wrote (or removed) an override, while `effectiveMappingColumns` preferred the override. Two consequences:

* With a profile selected, the applied columns were compared against **detection** rather than against the
  profile's entry, so applying a profile's own (unchanged) mapping stored an override that changed nothing and the
  chip still reported "not detection" for a mapping the user had not touched.
* After a real change had been applied, restoring the detected assignments compared them against the *override*
  (`activeColumnsFor`), which still differed, so a second override was written — equal to detection, but present,
  and `isDetectedMapping` then read through it. The chip only went blue when the entry happened to be removed.

Nothing here was object identity or Compose state: the entries were stored as immutable values and the status was
recomputed on every read. It was a **baseline** defect — the comparison target and the storage target disagreed.

### Implementation

```
baselineColumnsFor(sheet) = selectedProfile?.columnsFor(keyOf(sheet)) ?: detectedColumns(sheet)
activeColumnsFor(sheet)   = sheetMappingOf(sheet)?.columns ?: baselineColumnsFor(sheet)
isDetectedMapping         = MappingEquality.sameColumns(effectiveMappingColumns, detectedMappingColumns)
applySheetMapping(cols)   = if (sameColumns(cols, baselineColumnsFor(mappingSheet))) remove else store
```

`MappingEquality.sameColumns` is unchanged (blank = unassigned, headers normalized as `ColumnMappings.resolve`
does, a field on one side only is a difference), so an independently built but equivalent map is still equal.

### Behaviour after Apply mapping

| Scenario | Status | Stored |
|---|---|---|
| Detected view, mapping applied unchanged | blue | nothing |
| Equivalent mapping rebuilt as a new object and applied | blue | nothing |
| The same detected assignments picked by hand, applied | blue | nothing |
| One assignment changed, applied | grey | one edit for that worksheet |
| All changes restored to the detected values, applied | blue | edit removed |
| A detected assignment cleared, applied | grey | one edit (the field is absent from it) |
| Custom profile selected whose mapping differs from detection | grey relative to Detected | nothing |
| Back to Detected | blue | nothing |
| Profile selected whose mapping equals detection | blue (the profile chip is the selected view) | nothing |

### Tests

`DetectedStatusTest` (14, all passing) covers that matrix: applied unchanged, equivalent objects, manual selection

independence, navigation and restored state, and the profile-equals-detection case (now through

## C. Bug B — profile creation

### Confirmed root cause

rc.5 introduced per-worksheet *state* (`sheetMappings`) but left the **profile data model** as one column set.
`saveProfile` therefore stored `ColumnMappingProfile(name, columns = draft)` — a single set taken from the
worksheet on screen — and selecting the profile used that same set for whichever worksheet was inspected next. Any
worksheet entered through the profile was resolved with `LIST`'s header names; its own detected mapping was lost,
and `LIST`'s blank fields became "unmapped" everywhere. The rc.5 reading ("a profile must not carry untouched
worksheets forward") was the wrong diagnosis: the leak was the *model*, not the inheritance.

### Exact change

* `ColumnMappingProfile` gained `sheets: Map<worksheetKey, Map<CatalogField, String>>` (schema 2). The old single
  set survives as `columns`: what a schema-1 file contains, and the fallback for a worksheet a profile names no
  entry for.
* `WorkbookCommentsUi.profileSnapshot(name, tables)` builds what **Save profile** writes:

  | Worksheet | Entry written |
  |---|---|
  | the one on screen | its draft, blanks dropped (a cleared field is simply absent) |
  | any other | the edit applied to it, else the selected profile's entry, else **its own** detected headers |

  A source profile whose single column set names no worksheet is **narrowed** to the headers that worksheet really
  has (`narrowedColumns`) before being inherited.
* `WorkbookCatalogBuilder` asks the profile for that worksheet's entry only, so a profile with no entry for a
  worksheet is not applied to it (`columnsFor` returns null and detection answers).
* After saving, the new profile becomes the selected view and the per-worksheet edits are dropped: everything the
  user confirmed now lives in the profile, shown once.

### Worksheet identity, empty values, independence

Identity is `SheetScope.keyOf(partPath, name)` — the worksheet's package part — already used by the scopes and the
stored mapping. Two workbooks can hold worksheets of the same name without colliding, and a renamed worksheet
keeps its identity because its part does not change. Empty values live inside one worksheet's entry and are never
merged by field name: only the worksheet whose draft was cleared loses the assignment. All state is immutable
(`withSheet`/`withoutSheet` return new maps, `copy` returns a new state), so no two worksheets, profiles or views
share a mutable mapping.

### Tests

`WorksheetMappingIsolationTest` (11) — three worksheets (`LIST` Japanese headers, `DATA` `Title`/`Circle`/`説明`,
`NOTES` `書名`/`サークル`/`備考` plus an unrecognised `Reference`):

* Scenario A: modify `LIST` → the snapshot has `LIST` modified, `DATA` `Title`, `NOTES` `書名`; nothing of
  `LIST`'s edit appears on either sibling; `Reference` is not invented into a mapping.
* Scenario B: several assignments changed → only `LIST`'s entry differs; `DATA`'s entry equals its detection.
* Scenario C: no modification, saved from `LIST` → all three entries equal each worksheet's own detection (the
  inspected worksheet is not a template).
* Scenario D: `LIST`'s Title cleared → absent from `LIST`'s entry, `DATA` and `NOTES` keep theirs; through the
  catalog, `LIST` shows `DESCRIPTION` unmapped while `DATA` still reads `説明`.
* Scenario E: saving while `DATA` is inspected, then while `NOTES` is — each correct, and `NOTES`'s hand-mapped

## D. Profile view-switching verification

Everything below is asserted by `ProfileViewSwitchingTest` (7 tests) and `WorksheetMappingIsolationTest` against
the **resolved catalog** (`WorkbookCatalogBuilder.build(…, profile = selectedProfile, sheetMappings)`), i.e. the
mapping the reports actually read — not a UI flag. Fixture: `LIST` (タイトル/サークル/通し番号), `DATA`
(Title/Circle/説明); Custom A maps `LIST`'s Title from サークル, Custom B from 通し番号.

| Operation | Displayed/read mapping for `LIST` | Displayed/read for `DATA` | Saved data |
|---|---|---|---|
| Select Detected | `タイトル` (detection) | `Title` (detection) | no profile touched |
| Select Custom A | `サークル` | `Title` (A's own entry) | A unchanged, Detected not stored anywhere |
| Switch back to Detected | `タイトル` | `Title` | A still `サークル` |
| Switch back to Custom A | `サークル` | `Title` | Detected still computed |
| Switch to Custom B | `通し番号` | `Circle` (B's own entry) | A unchanged |
| Switch back to Custom A | `サークル` | `Title` | B unchanged |

Also verified, in the same suite:

* The **draft** follows the view (`サークル` under A, `通し番号` under B, `タイトル` under Detected).
* A name that no profile has falls back to Detected instead of showing nothing.
* After visiting A → B → Detected → A the `profiles` list is **value-equal** to the one it started from.
* An edit applied on top of A (`Title` ← `通し番号`) is in effect for `LIST` only, leaves A's object untouched, and
  is dropped when the view switches — no stale edit survives.
* A draft edit that was never applied is not written into any profile by switching.

## E. Profile inheritance verification

The workflow of §2.4, on the same fixture (`WorksheetMappingIsolationTest`, Scenario A/B/C/D/E):

| Operation | `LIST` | `DATA` | `NOTES` |
|---|---|---|---|
| Select Detected | detected `タイトル` | detected `Title` | detected `書名` |
| Modify `LIST` (Title ← サークル) | draft `サークル` | unchanged `Title` | unchanged `書名` |
| Save profile "Custom A" | `サークル` | inherited `Title` | inherited `書名` (and no `Reference`) |
| Select Detected | `タイトル` again | `Title` | `書名` |
| Select Custom A | `サークル` | `Title` | `書名` |
| Derive "Custom B" after editing `DATA` | `サークル` (from A) | `Circle` (the edit) | A's own entry, unchanged |

Saving with **no** modification from `LIST` produces entries equal to each worksheet's own detection — the
inspected worksheet is not a template. Clearing `LIST`'s Title leaves `DATA`'s `Title` and `NOTES`'s `書名`
untouched, and the same holds in the built catalog (`LIST` reports `DESCRIPTION` unmapped while `DATA` still reads
`説明` and `NOTES` still reads `備考`). Only unit tests were run: no manual/on-device verification is claimed.

## I. Outstanding issues

1. **No on-device pass.** The chip colours, the Save-profile dialog, the Fields **Change/Clear/Use detected**
   buttons and the cell dialog were compiled and are covered at state/model level; the project still has no Compose
   UI-test dependency, so no screen was driven. The audition should confirm the two-chip case (a selected profile
   whose mapping equals detection) reads clearly.
2. **Switching drops applied but unsaved edits.** Deliberate (they are the previous view's session state) and
   documented; the safeguard is the message under the chips plus **Save profile**. A confirmation dialog was
   judged unnecessary redesign.
3. **Profiles are not portable across workbooks by matching headers.** A profile covers the worksheets it was saved
   with (by package part); a worksheet it does not know is detected rather than borrowing another worksheet's
   columns. Reuse on another workbook therefore needs one save per workbook — the deliberate trade that prevents
   cross-worksheet contamination.
4. **A schema-1 profile stays a single column set**, applied per worksheet (narrowed to each worksheet's own
   headers) until it is saved again; it is not expanded into per-worksheet entries on load, because it never said
   which worksheet its columns belonged to.
5. **A profile's name is still its identity** (saving under an existing name replaces that profile); renaming and
   reordering profiles remain out of scope, as before.
