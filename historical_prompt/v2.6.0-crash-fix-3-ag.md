## 3. Shields.io investigation and the verified root cause

Traced the whole path: `README → AuthorUrls.resolve → HttpAuthorRemote → AuthorFileCache → AuthorImageDecoder.decode
→ AndroidSVG → Compose badge row`.

* The badges are **SVG** (1 258–3 484 bytes; the Java badge is `width="53" height="20"`) delivered by `img.shields.io`.
* They are drawn at a **fixed 20 dp height** (crash-fix 1), which on this 420 dpi device (density **2.625**) is
  **139 × 52 px**.
* `AuthorImageDecoder.rasteriseSvg` computed `scale = min(maxWidth/w, maxHeight/h, 1f)` — the trailing `1f` capped
  every vector at its **intrinsic** size, so a 53×20 badge was rasterised at **53×20 px** and then enlarged **2.6×**
  by the compositor.
* Nothing else degraded it: the document arrives intact, `SvgEmbeddedImages.prepare` resolves the icon (crash-fix 2),
  the cache stores the original bytes, and the sizing rule did not change.

**Root cause: a vector rasterised far below the size it is drawn at, with the enlargement left to the compositor.**
That is exactly a small bitmap stretched — soft edges, a wide antialiasing band, washed-out strokes — while the
badge's background and text (large flat shapes and hinted glyphs) still looked acceptable.

## 4. The icon-quality fix, and before/after device evidence

`AuthorImageDecoder.decode(bytes, maxWidth, maxHeight, density)` now takes the display density (supplied by
`MainViewModel` from `resources.displayMetrics.density`) and rasterises **vectors** at the pixels they occupy:

```kotlin
val target = density.coerceIn(1f, MAX_VECTOR_SCALE)      // 4× ceiling
val scale  = minOf(target, maxWidth / intrinsicWidth, maxHeight / intrinsicHeight)
```

Rasters are untouched: `decodeRaster` still only ever **subsamples**, so the 3840×2160 banner is never enlarged.

Measured on the emulator's Java badge, same scroll position, same badge, icon column (left 34 % of the badge):

| | Solid icon ink (near-white) | Antialiasing band | Distinct shades |
| --- | --- | --- | --- |
| Before (`cf2-badges-after.png`) | 37 | **525** | **637** |
| After (`cf3-badges-after.png`) | **105** | **212** | **350** |

Nearly three times as many solid ink pixels, a blur band less than half as wide, half as many intermediate shades —
the signature of a vector rendered at its display size rather than an enlarged thumbnail. Instrumented tests assert
the same two things without a screenshot: the decoded bitmap is **≥ 139 × 52 px** at density 2.625 (and exactly
53 × 20 at density 1), and its antialiasing band is narrower than the same bitmap enlarged.

## 6. The dark graph theme, and why it is the source's own

The README does not offer one graph — it offers two, inside a `<picture>`:

```xml
<source media="(prefers-color-scheme: dark)"  srcset="…/pacman-contribution-graph-dark.svg">
<source media="(prefers-color-scheme: light)" srcset="…/pacman-contribution-graph.svg">
<img alt="pacman contribution graph"          src="…/pacman-contribution-graph.svg">
```

Crash-fix 2's parser resolved a `<picture>` to its `<img>` **fallback**, which is the light variant — a white canvas
dropped into a dark page. `Parser.readHtml` now takes the `prefers-color-scheme: dark` `<source>` when a picture has
one and falls back to `<img>` otherwise, emitting exactly one image block per picture. The rule is about the media
query, not about this picture, so any `<picture>` with a dark variant is handled the same way, and a picture with only
a light source is unaffected (asserted).

The dark document is a real, animated asset (84 944 bytes), not a recolour:

| Element | Colour | Where it comes from |
| --- | --- | --- |
| Canvas | `#0d1117` | `<rect width="100%" height="100%" fill="#0d1117"/>` |
| Empty day cells | `#161b22` | `fill="#161b22"` × 371 |
| Month / weekday labels | `#8b949e` | `<text … fill="#8b949e">`, 26 text elements |
| Maze walls | `#ffffff` | `fill="#ffffff"` × 59 |
| Contribution ramp | `#0e4429` → `#161b22` | the `<animate>` values that eat a cell |
| Animation | 53 `<animate>` + 6 `<animateTransform>`, `dur` 29 000 ms, `frameRate` 5 | `<metadata><info>` |

So the background, the labels, the cells and the walls are all explicitly defined by the generator's dark theme —
nothing is overridden by Compose, and no light-theme text can end up on a dark canvas, because neither is chosen by
this app. The rest of the application is untouched: this is the graph's own presentation, not a global theme change.

## 8. The animation timing pipeline, and the identified bottleneck

| Stage | Before | After |
| --- | --- | --- |
| Declared duration | 29 400 ms (`dur="29400ms"`) | unchanged |
| Declared rate | 5 fps (`<frameRate>5</frameRate>`) | still read, but no longer the display rate |
| SMIL sampling | step for every animation | `calcMode` honoured: `discrete` steps, `linear` interpolates |
| Frame interval | `1000/5` = 200 ms, **plus** the render time | `1000/18` = 55 ms, with the render *inside* that budget |
| Frame generation | one document rewrite + one `AndroidSVG` parse + raster per frame | same, at the display width, skipping ticks where nothing can change |
| Compose state | updated every tick | updated only when a frame was actually produced |
| Effective rate | **≈4.4 fps** | **≈15.6 fps** |

Two defects were found in the timing, not one:

1. **The loop waited a whole period *after* rendering.** `delay(period)` came after the render, so the real interval
   was `render + period`; at 5 fps that cost ~40 % of the intended rate. The loop now measures the work and waits only
   the remainder.
2. **The source's 5 fps was treated as a ceiling.** The generator writes one Pacman position every 200 ms, but its
   `translate`/`rotate` declare no `calcMode`, and SMIL's default is **linear** — so an instant *between* two keyTimes
   has a real value. `SmilAnimation` now interpolates those (numbers, numeric lists and `#rrggbb` colours) while the
   cell animations, which explicitly declare `calcMode="discrete"`, stay a step. The page can therefore sample the
   same timeline at 18 fps without moving Pacman any faster: the loop length, the positions and the speed are
   untouched.

**Bottleneck:** the render itself. `AndroidSVG` exposes no way to change an attribute of an already-parsed document,
so a new instant costs one 85 KB document rewrite plus one parse and rasterisation of ~1 030 elements: **32 ms at the
50th percentile, 53 ms at the 90th** on this software-rendered emulator. That is why the achieved rate is 15.6 fps
against the 18 fps the clock asks for, and the task's "report the measured rate rather than claiming the target" case
applies.

## 14. Remaining limitations and unverified behaviour

* **15.6 fps, not 18.** The clock asks for 18; the renderer delivers 15.6 on this emulator because a frame costs
  32–53 ms. Every rendered frame is a genuine new instant, so the motion is smooth, but the figure is measured, not
  claimed. A GPU-backed device has not been tested.
* **A parse per frame remains.** `AndroidSVG` cannot mutate a parsed document, so each new instant re-parses the
  85 KB document. The requirement to "avoid repeatedly parsing the entire SVG on every frame" is met only in the
  weaker sense that no frame is rendered when nothing can change (discrete-only documents, hidden page, paused app);
  removing it entirely would mean either a frame cache (0.5 MB × 529 frames) or drawing the cells and Pacman by hand,
  which would replace the real asset.
* **The dark theme is the generator's dark variant.** A repository that stops publishing it, or renames it, falls
  back to the light graph — which would look like the old white panel. The rule is media-query based, not a recolour,
  so no app-side palette is ever applied to a light document.
* **Icon crispness is capped at 4× density** (`MAX_VECTOR_SCALE`); no current device exceeds that.
* **Untested:** a physical device; a display density other than 2.625; the surrounding page under an Android *light*
  system theme (the graph's own colours are fixed, so its canvas is unaffected — but that combination was not
  re-captured); playback beyond the several minutes exercised here.
