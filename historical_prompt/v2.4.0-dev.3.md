## 4. Patch A — Fix incomplete worksheet column display

### 4.1 Problem

The worksheet browser does not display all available worksheet columns.

For example, the sample workbook's `LIST` worksheet includes:

- `ツイッター`
- `ツイッター (ユーザー名)`
- `ミスキー`
- `ミスキー (ユーザー名)`

These columns, and potentially other columns farther to the right, are not fully visible in the application.

The problem must be investigated at both the data-processing and UI layers.

Do not assume that this is only a screen-width problem.

### 4.2 Investigate the complete data path

Trace:

1. Workbook worksheet metadata extraction.
2. Header and column discovery.
3. Maximum column detection.
4. Blank or partially populated column handling.
5. Record extraction.
6. Data model representation.
7. UI table or worksheet-browser column generation.
8. Horizontal layout, scrolling, and clipping.

Determine whether columns are being lost during parsing, model construction, filtering, or UI rendering.

Do not patch the display while leaving the underlying worksheet data incomplete.

### 4.3 Requirements

The worksheet browser must:

- Represent every supported worksheet column.
- Display columns beyond the initial visible screen width.
- Support horizontal scrolling where appropriate.
- Keep column headers correctly associated with their values.
- Avoid silently truncating the available column list.
- Support long Japanese and multilingual headers.
- Handle variable column widths.
- Avoid forcing all columns into a narrow fixed-width layout.
- Preserve vertical scrolling and record navigation.
- Handle large worksheets without rendering the entire dataset unnecessarily.

Where useful, provide a column-visibility or column-selection control, but do not hide columns by default without a clear, discoverable way to access them.

If the user switches worksheets, the displayed columns must update to the selected worksheet's actual structure.

### 4.4 Data-integrity requirements

- Preserve source column identity.
- Do not reorder columns arbitrarily.
- Do not confuse a display index with the original source column index.
- Preserve empty or unmapped columns when the workbook structure requires them for correct column alignment.
- Avoid interpreting a blank header as proof that the column does not exist.
- Ensure column mappings remain associated with the correct source columns.

### 4.5 Acceptance criteria

Using the supplied sample workbook:

- All 24 `LIST` columns can be accessed.
- `ツイッター` and `ツイッター (ユーザー名)` are available.
- `ミスキー` and `ミスキー (ユーザー名)` are available.
- Columns near the right edge are not lost.
- Horizontal navigation works correctly.
- Header-to-value alignment remains correct.

Also verify with an independent workbook containing a different number of columns and a different column order.

## 5. Patch B — Manually configurable Published and Acquired timeline dates

### 5.1 Problem

The Published and Acquired timeline features are currently unavailable or cannot be configured adequately.

The user wants to choose which source column represents each date.

Do not rely on automatic header detection as the primary configuration mechanism.

### 5.2 Required configuration

Provide a manual date-column assignment workflow with two independent settings:

**Published timeline**
- User selects the source column representing publication/release date.

**Acquired timeline**
- User selects the source column representing acquisition/purchase date.

The two assignments must be independent.

The user may select:

- A different column for each date type.
- The same column for both only if they explicitly choose to do so.
- No column for either timeline.

Do not automatically assign a column merely because its header resembles a known date field.

### 5.3 Sample workbook as a test case

The supplied `LIST` worksheet currently has:

- `出版日付` — a publication-date candidate.
- `購入日` — an acquisition-date candidate.

These are useful sample values for testing manual configuration.

However, the application must not automatically assume that every workbook uses these headers.

The user should be able to manually select these columns in the sample workbook, but the implementation must also work with entirely different names and column positions.

### 5.4 Configuration interface

Implement a clear configuration screen or dialog consistent with existing UI conventions.

For each timeline:

1. Display the timeline type.
2. Display the selected workbook and worksheet where relevant.
3. Provide a selectable list of available source columns.
4. Display the current assignment.
5. Allow clearing the assignment.
6. Preview representative source values from the selected column.
7. Validate whether the selected column contains usable date values.
8. Allow the user to confirm or change the assignment.

Do not silently interpret invalid or ambiguous dates.

If the user selects a column that contains mixed or malformed values, explain the issue and show the affected values or a summary.

### 5.5 Date parsing

Reuse existing date-normalization logic where possible.

Support actual date values and the text formats the application can reliably parse.

Handle:

- Excel date serial values.
- Native date/datetime values.
- Recognized textual date formats.
- Empty cells.
- Invalid date strings.
- Ambiguous date formats.

Do not silently guess ambiguous date interpretations.

### 5.6 Persistence and scope

Persist the Published and Acquired mappings using the existing persistence architecture.

Determine the appropriate scope:

- Per workbook.
- Per worksheet, where required.
- Per mapping profile, if that provides a consistent and understandable configuration model.

Avoid making a profile-specific date assignment unexpectedly affect unrelated workbooks.

When the source worksheet or its columns change, detect stale mappings and ask the user to reconfigure them.

### 5.7 Timeline behavior

Once configured:

- Published timeline uses only the configured Published date column.
- Acquired timeline uses only the configured Acquired date column.
- The two timelines must not substitute dates for one another.
- Unknown dates must remain unknown.
- Invalid dates must be identifiable.
- Users must be able to distinguish publication date from acquisition date.
- Filtering and chronological sorting must use the selected date field.

If a timeline has no assigned date column, show a clear setup state explaining how to configure it rather than displaying an empty or misleading timeline.

### 5.8 Acceptance criteria

Using the sample workbook:

1. User manually selects `出版日付` for Published.
2. User manually selects `購入日` for Acquired.
3. Both timeline features become available.
4. The timeline results use the appropriate date values.
5. Restarting the app preserves the assignments.
6. Changing the mapping updates the relevant timeline.
7. Clearing a mapping returns the timeline to its setup state.

Also verify that a second workbook with differently named date columns works without hardcoded special cases.

## 7. Patch D — Fix Insights gallery scroll-position behavior

### 7.1 Problem

In the Insights directory under the Workbook comments section, the gallery does not return to the top when its displayed item order changes.

Instead, it retains the previous scroll position.

The user has confirmed that the displayed order did change, so this is not simply a sorting failure.

The issue is specifically that the gallery remains at an old scroll position after its displayed dataset/order changes.

### 7.2 Investigate the root cause

Inspect:

- Lazy grid/list state.
- `rememberLazyGridState` or `rememberLazyListState` usage.
- State ownership and composable lifetime.
- Dataset identity.
- Sorting and filtering state.
- Stable item keys.
- Whether the gallery is reused across different data sets.
- Whether a sort or filter operation updates the items without updating the corresponding scroll state.
- Whether navigation retains an old gallery state unintentionally.

Do not apply a superficial workaround that simply recreates the entire screen on every recomposition.

### 7.3 Required behavior

When the displayed Insights gallery order changes due to an explicit sorting or ordering change:

- Reset the gallery's scroll position to the top.
- Ensure the first item in the new order is visible.
- Avoid showing an item from the previous scroll position as the starting point of the new order.
- Keep the new order intact.
- Avoid unnecessary resets when unrelated state changes occur.

When the user merely opens and closes an item without changing the gallery's ordering, preserve the expected browsing state.

When the user changes filters, determine whether the resulting dataset is materially different. If so, apply a consistent and predictable scroll-reset policy.

### 7.4 Implementation guidance

Use stable keys for gallery items wherever possible.

Associate the gallery scroll state with the appropriate dataset or ordering state.

Use a controlled state-reset mechanism when the actual displayed ordering changes, rather than triggering a reset on every recomposition.

Avoid unstable key generation or random IDs.

Ensure asynchronous image loading does not repeatedly reset scroll position.

### 7.5 Acceptance criteria

Test the following:

1. Scroll the Insights gallery down.
2. Change the sort order.
3. Confirm the gallery displays the first item of the new order at the top.
4. Change the sort order again.
5. Confirm the gallery again starts at the top.
6. Open an item and return without changing the ordering.
7. Confirm the expected browsing state is preserved.
8. Trigger unrelated recomposition.
9. Confirm the gallery does not jump unexpectedly.

The fix must address the actual scroll-state lifecycle and dataset-order relationship.
