## 2 · Exact root cause

The integration had been completed **at the abstraction layer only**. Three defects, all on the
product surface, made READ THE COVER a Lens-only experience:

1. **The selector was compiled out of release builds.** `BuildConfig.DEBUG` gated the only control
   that could select PaddleOCR, so in every release APK the choice could not be made at all — the app
   always ran Chrome Lens.
2. **Every READ THE COVER string named Google Lens / `chrome-lens-py`**, including the running
   label and the result line, so even a debug build that *did* run PaddleOCR reported itself as Lens.
   Selection, availability and “what actually ran” were indistinguishable in the UI.
3. **The request's engine was not captured or logged.** The running label was a constant, the result
   state carried only a library version string, and no log line recorded which engine a request was
   routed to — so no evidence existed either way.

Not the cause (verified, not assumed): the JNI layer, the native engine, the model store, the
switching source and the preference plumbing were all present and functional, and are unchanged by
this task apart from being wired to the corrected UI/identity layer.

## 6 · Final execution routing

```
Online tab
  └── OcrEngineSection            (Chrome Lens | PaddleOCR, persisted)
        └── OnlineSearchController.readCover()
              ├── engine = OcrEngineChoice.fromId(prefs.ocrEngine)   ← fixed for this request
              ├── log: ocr engine request id=<id> bytes=<n>
              ├── bridge.recognise(bytes …)                           (OcrTextSource)
              │     └── SwitchingOcrTextSource.delegate()             ← resolves the preference per call
              │           ├── Chrome Lens → ChromeLensPyBridge → lens_bridge.py → chrome-lens-py
              │           └── PaddleOCR   → RustOcrTextSource → JNI → libbc_ocr.so (PP-OCRv6 Medium)
              ├── log: ocr engine result id=<id> ok/failed …
              └── OcrUi.Done(text, …, engine) → OcrQueryExtractor → catalogue search (unchanged)
```

* The same `OcrTextSource` contract serves both engines; no parallel OCR path and no demo screen.
* The engine is captured **before** the coroutine starts, so a switch during a running request does
  not relabel its result. The next request resolves the new selection.
* Failures propagate as `OcrException` with the selected engine's category. Nothing retries on the
  other engine, and a failure never changes the stored preference.
