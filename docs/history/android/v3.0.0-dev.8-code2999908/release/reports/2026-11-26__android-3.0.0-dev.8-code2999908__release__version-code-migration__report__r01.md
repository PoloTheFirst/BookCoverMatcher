# Android archive version-code migration validation

## Archive context

Project release evidence for the deterministic Android version-code migration. The [release index](../../../../../reference/RELEASE_INDEX.md) lists original releases by publication date.

## Outcome

All 44 additional APKs passed publisher signature and manifest checks. They cover 35 releases and 43 source tags. Keep each original download at its existing name. The new APK filename includes the Android version code. The [artifact manifest](../../../../../../tools/archive-rebuild/artifacts.json) records the original and rebuilt SHA-256 for every edition.

## Scope and baseline

The owner requested all releases and confirmed an empty Play draft with no uploaded bundle. The original dev.8 builds used code 234. The rebuilt BCM and BCM Plus dev.8 APKs share code 2999908. The earliest WebView project used a different Android package name. Its two release-name exceptions retain their original packaged names.

## Changes and decisions

The current branches share a validated version-name input for Gradle and the documentation checker. Stable versions and dev.1 through dev.99 have deterministic codes. Historical RC records remain in the archive. Code 234 remains registered for frozen dev.8 records and code 2999908 has its own registry entry. Policy revision 2026-11-26.2 and application data practices remain applicable to both dev.8 builds.

The archive uses the exact existing tag for each edition. The reconstruction helper applies the release code and the two XML comment repairs needed by the three earliest builds. The stable v2.5.0 source correction removes a misplaced UTF-8 byte-order mark before a Kotlin package declaration. It restores historical model and native inputs from the verified original APK and supplies the Python dependency constraints for the tagged build.

## Verification and evidence

- Verified the signed files with Android Build Tools, checked their original application IDs and version names, and compared every expected code. The archive includes both v2.0.0 full/lite APKs and both editions of dev.1 through dev.8.
- Checked all 43 source tags against the version calculator. For each actual diff, reconstructed the final Gradle file from the tag and checked its SHA-256. Valid and invalid version vectors and source aliases are covered by `python3 -m unittest discover -s tools/tests`.
- Compared model and native-library member names, sizes and CRCs against the preserved originals and compared the packaged Python distributions. Tested a separate source reconstruction for v2.4.0-dev.1 and v3.0.0-dev.1. All 474 and 386 DEX, manifest, resource, model and native entries respectively matched their corresponding archive builds by SHA-256. Compression, Python packaging and signing can yield different whole-file hashes for independent builds.
- Processed the current Play and GitHub release manifests with Gradle. Both reported `com.bookcovermatcher`, `3.0.0-dev.8` and `2999908`. Ran the documentation refresh and consistency checks in both source trees.

## Outstanding work and risks

23 original APKs use a different signer from their rebuild. The [rebuild guide](../../../../../reference/ARCHIVE_REBUILDS.md) identifies the 3 original debug APKs whose release builds omit Android Studio’s exported preview activity. Higher historical rebuild codes can make older software appear upgradable over an original installation. No device or cloud-runtime testing was performed for this archive migration.

## Next action and references

Use the [historical rebuild guide](../../../../../reference/ARCHIVE_REBUILDS.md) and the artifact manifest to verify individual downloads. GitHub upload receipts are recorded separately from this build-validation report. The Play submission remains under owner control.
