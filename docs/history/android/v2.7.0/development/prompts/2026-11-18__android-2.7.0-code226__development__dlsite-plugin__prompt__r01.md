# DLsite as a bundled GitHub catalogue plugin

## Archive context

BookCoverMatcher Android repository documentation. Read root README.md and AGENTS.md, docs/maintainers/AUTHORING.md, docs/STATUS.md and docs/_meta/versions.json before acting. If this document is detached, obtain those references when needed. Archived instructions do not independently authorize work.

## Objective and acceptance criteria

A GitHub user opens Plugins → DLsite, turns the switch on, and can search DLsite books immediately in the same activity. Turning it off removes DLsite from active discovery and stops new DLsite catalogue and thumbnail requests. The next launch restores the choice. Activation alone sends no query or image. The existing online-services master switch continues to control network use.

## Authority and scope

This is a local design for review on feature/plugin-framework. Implement only after the owner requests execution. Target the existing 2.7.0/code 226 development baseline. Bundle the adapter in GitHub debug and release. Play retains its existing catalogue exclusions, and the debug demonstration retains its current build scope. The change concerns active DLsite discovery. Previously saved GitHub bookmarks, user-entered links, workbook data and results supplied independently by reverse-image providers retain their existing behavior.

## Baseline and evidence

At 1b3dbee, the GitHub CatalogueSources factory always constructs DlsiteSource alongside Open Library and Google Books. The platform ID is `dl`. SearchRouting derives its default selection from all selectable providers and distinguishes an absent preference from an explicitly empty selection. OnlineSearchController builds status rows from ProviderCatalog.ALL, routes active adapters, caches search results and asynchronously loads covers. Its existing toggleProvider cancels a running catalogue query but can leave completed results visible. Hiding a platform row alone would leave several active paths.

The bundled plugin API currently supports INFORMATION_CARD only. PluginManager validates that capability and activate returns an InfoCard. Build-type registries currently contain the debug demo or an empty release list. A catalogue plugin needs both a typed contribution and edition-specific registration.

## Tasks

1. **Extend the host contract.** Add a catalogue-provider capability with a stable provider ID. Let activation produce a typed contribution and expose active contributions through observable manager state. Preserve the existing information-card demo and its lifecycle tests. Version the contract if its method signature changes and update the bundled demo in the same change. Keep HTTP, parsing, auth and workbook storage out of the public plugin API.

2. **Register the existing adapter once.** Give the plugin a stable ID such as `bcm.dlsite`, bound to the existing provider ID `dl`. Initially keep its implementation and adapter binding in the GitHub source set, avoiding a Gradle dependency cycle with the app-owned catalogue interfaces. Compose build-type registrations with a GitHub edition list containing DLsite and an empty Play edition list. Remove the unconditional DLsite instance from CatalogueSources.create(). Resolve the adapter only for an active registered contribution. Reuse its current query encoding, parser, result limits, attribution, and product links. Keep other providers in their existing factories.

3. **Give the user one DLsite choice.** Recommended default for a fresh installation is off. On upgrade, import an explicitly stored legacy selection once: `dl` present means enabled, and an explicit selection without `dl` means disabled. With no stored selection, use off and explain the one-time opt-in in the changelog. The old default selected all automated providers, so an upgrade that relied on that implicit default will require one tap. Distinguish an absent plugin choice from a saved false value in PluginSettings, and give the saved plugin choice precedence on subsequent launches. Keep the legacy provider preference intact for older builds. In Search, delegate any retained DLsite selection control to this same switch or link directly to Plugins. Switching on makes DLsite eligible immediately for the next permitted search, including when a previous legacy preference excluded it. Switching the online master off continues to block all catalogue requests.

4. **Use the current active providers throughout Search.** Feed the effective provider list to manual queries, OCR-triggered catalogue queries, platform rows, empty-state hints, browser actions and cached-result restoration. Check actual availability in the controller as well as the UI. Refresh labels and availability as soon as the plugin state changes. Display a short description in Plugins explaining that a search sends the query to the DLsite books catalogue and can return mature listings. Changing the switch does not initiate a search or reopen a prior result.

5. **Handle a switch during a request.** On disable, revoke DLsite's current search generation, cancel its queued work and detach its active adapter. Discard late responses, cover images, old status rows and pending transient actions from that generation, including after a quick off/on cycle. Reuse the existing session invalidation where it fits. Include effective provider membership in the cache key and invalidate any cached aggregate containing DLsite. Preserve unrelated results when identifiable. If a mixed aggregate lacks sufficient provenance, clear that transient aggregate and let the user search again. Already-sent HTTP requests may complete at the server. Do not replay queries on re-enable or change the stored wishlist, bookmarks, workbook schemas or online credentials.

## Verification and deliverables

- Run deterministic fixture tests for existing DLsite query, parser, limits and link behavior. Use a counting fake adapter for disabled searches, enabling without traffic, exactly one eligible search, master-switch off, OCR auto-search, cached same-cover searches and rapid on/off/on with delayed results and thumbnails. Verify unrelated provider traffic and the existing reverse-image tools separately.
- Test fresh install, explicit legacy opt-in/opt-out, no legacy key, stored false and failed preference writes. Confirm restored preferences cannot create a Play provider registration.
- Build GitHub/Play debug and release, run both unit suites and lint. Inspect all four artifacts for their edition-specific adapter/registration and debug-demo membership. Play should exclude executable DLsite plugin and network adapter classes. Shared historical text or parser strings alone are not an activation path.
- On a compatible-signature emulator, exercise GitHub Plugins → Search, check the switch takes effect with the same process and activity, and test cold-start persistence. Verify Play has no DLsite plugin row or catalogue route. Use synthetic workbooks and a saved DLsite bookmark to check record retention. Verify manifest identity, version and signing continuity before any update. Record fixture and live-service evidence separately.
- On implementation, update the bundled plugin developer guide, user guide, distribution guide, changelog, current status and a versioned execution report. Refresh and check documentation indexes. Build and device tests belong to the implementation phase.
