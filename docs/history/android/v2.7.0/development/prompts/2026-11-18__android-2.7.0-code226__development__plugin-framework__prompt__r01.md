# Bundled plugin framework with immediate toggles

## Archive context

BookCoverMatcher Android repository documentation. Read root README.md and AGENTS.md, docs/maintainers/AUTHORING.md, docs/STATUS.md and docs/_meta/versions.json before acting. If this document is detached, obtain those references when needed. Archived instructions do not independently authorize work.

## Objective and acceptance criteria

Plan a bundled plugin framework for Android 2.7.0/code226, with settings-style switches in the existing Plugins tab. Switching a compatible bundled plugin on or off updates its available features and visible UI without restarting the app. This means activation/deactivation of code already packaged with the app, not replacing executable code while running.

The owner approved this bundled framework on 18 November 2026. The [execution record](../reports/2026-11-18__android-2.7.0-code226__development__plugin-framework__report__r01.md) documents implementation and verification. The original planning and acceptance scope follows.

Acceptance for the subsequent implementation:

- Both editions retain Plugins immediately after More, with the puzzle icon.
- A bundled debug-only demonstration plugin proves activation, deactivation, persisted preference and immediate UI refresh; it performs no network or workbook operation.
- No provider registration, selection/default, request routing, reverse-image behavior, stored record or cloud account behavior changes.
- The existing application ID, signing configuration, version226/2.7.0 and storage formats remain unchanged. Local/remote main and google_play are not rewritten during feature development.
- No import/download/install buttons imply an unsupported feature. Production remains honestly empty until a real bundled plugin is separately approved.

## Development files and future import format

Use `.kt` for Kotlin implementation and `build.gradle.kts` for module configuration. Prefer Gradle project dependencies while developing in this repository. An Android library can build an `.aar`, which includes Android code/resources and is linked into the app during its build. A pure Kotlin/JVM API module can build a `.jar`. Neither a raw `.kt` nor an `.aar` is an end-user hot-install format supported by this plan.

For a future file-picker import, reserve `.bcmplugin` as a possible BCM-specific extension, not an existing standard or an implemented feature. One candidate is a versioned ZIP containing a JSON manifest and declarative resources/settings. Such a data-only package can use capabilities already implemented by the host; it cannot add arbitrary Kotlin behavior. New executable Kotlin plugins would need a separately designed delivery/isolation model. Do not disguise DEX/JAR/native code inside a ZIP or treat a renamed file as a sandbox or policy exemption.

Future import UX, outside this phase: choose file, validate content and compatibility, display author/capabilities, confirm import, show an initially-off row, then activate with its switch. Import and activation are separate actions. The exact extension/container/schema and supported payload types remain uncommitted design choices until that phase is approved.

Android's library documentation describes AARs as app-module dependencies. Android recommends avoiding unnecessary dynamic code loading; Play restricts outside-Play executable downloads and requires interpreted code to remain policy-compliant. These constraints also mean a plugin system does not resolve the retained reverse-image content review.

Sources checked 18 November 2026:

- [Android library modules and AAR](https://developer.android.com/studio/projects/android-library)
- [Android dynamic code loading guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading)
- [Google Play code-loading policy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en)

## Tasks

1. **Small plugin contract.** Add a `:plugin-api` Kotlin/JVM module with stable identifiers, descriptor/version, supported host API range, declared capabilities and lifecycle interfaces. Keep Android Context, workbook repositories, authentication tokens and raw filesystem access out of the contract. Plugin API versioning is independent of the Android version code. Start with one minimal host-rendered contribution type, such as a read-only information card, rather than an unrestricted UI API.

2. **Explicit bundled registry.** The app composes a registry from known factories at build time. Reject duplicate IDs and incompatible API versions before activation. Each edition selects its own registrations; a preference, imported identifier or descriptor cannot enable something excluded from that build. No reflection-based discovery, dynamic class loader, network registry or package scanner. Existing providers remain outside this registry throughout this phase.

3. **Runtime and lifecycle.** Add an app-owned manager exposing a StateFlow of descriptors, requested enabled state, actual state, error and active contributions. States: Disabled, Enabling, Enabled, Disabling, Failed and Unavailable. Serialize changes per plugin; make repeated requests idempotent. Give each active plugin its own coroutine scope and generation token. Enabling validates compatibility and initializes once; disabling removes contributions immediately, cancels tasks, detaches listeners and ignores late callbacks from older generations. Bounded cleanup must prevent an unresponsive plugin from freezing the UI or overlapping with a re-enabled instance. Ordinary initialization failures affect that plugin, not the rest of the UI; do not claim protection from fatal native crashes or malicious in-process code.

4. **Persist only plugin preferences.** Use a separate small preferences store keyed by stable plugin ID, leaving all existing keys/databases unchanged. New plugins default off. Commit enabled preference after successful activation; failures stay off with an actionable error. Record off before teardown so process restart cannot silently reactivate a disabled plugin. Handle persistence failures explicitly and keep UI consistent. On process recreation, reconcile saved choices against the edition's available compatible plugins; preserve unknown-plugin preferences without activating them. Any future data-clear/reset action must be explicit and separate from disabling. No workbook/cache/bookmark deletion or cloud-session change follows a toggle.

5. **Reactive settings UI.** Use grouped rounded rows with plugin icon, name, short description, status and a trailing pill switch, styled consistently with BCM while resembling the familiar iOS Settings arrangement. Use Compose Switch semantics, a labeled accessible hit target, clear on/off state and large-font support. Opening details is a separate action. Show Enabling while work runs; prevent conflicting repeated taps. After activation succeeds, state emission refreshes the tab and any registered host UI immediately—no force-stop, activity restart, manual refresh or automatic rerun of an unrelated search. Turning off hides contributions immediately while preserving their stored preferences/data. Missing approval/configuration shows Needs setup rather than pretending the plugin is active. This phase's demo needs neither permissions nor credentials.

6. **Debug-only proof.** Add a small `:plugins:demo` library using `.kt` and project dependencies, registered only in debug variants. It contributes a deterministic local card that appears/disappears with its switch. Keep its examples neutral. Do not relabel or wrap existing providers as plugins to create demo content. Release registries remain empty and show the current accurate placeholder. This proves the lifecycle before a real feature is chosen.

7. **Document extension development.** Add a concise maintained developer guide covering module layout, host API compatibility, descriptor IDs, coroutine cleanup, expected toggle behavior and how to add a bundled implementation. Explain that trusted bundled modules run in the host process: narrow interfaces are architectural boundaries, not an Android security sandbox. External/untrusted plugin isolation and package verification require a separate design before import is implemented.
